## A · 协作与流程经验

### A1. 用户报的是现象，不是根因（2026-10-31）

用户原话"点退出游戏就崩"。字面像是关闭流程写错了，实际根因是**同一份 `glfw.dll` 被加载了两份实例**，MC 侧在自己的空链表上摘窗口节点。

**做法**：拿到报障先复现、先看最原始的现场（崩溃日志/堆栈/寄存器），再谈"是什么导致的"。把用户描述直接当诊断结论，会朝着错误的方向改一堆无关代码。

### A2. 没有 crash-report 的崩溃，先去翻 `hs_err_pid*.log`（2026-10-31）

MC 的 `crash-report` 只覆盖 Java 层未捕获异常。JVM **原生崩溃**（`EXCEPTION_ACCESS_VIOLATION`）不会生成 crash-report，只会写 `hs_err_pidXXXX.log`，而这份文件里的**已加载模块列表**和**寄存器状态**往往直接就是答案。

**判断特征**：用户说"没有崩溃报告，游戏直接没了" → 先找 `hs_err`，别在 `crash-reports/` 里空转。

### A3. 盘点项目现状必须以代码为准，文档声称的完成度不算数（2026-10-31）

本轮做 AG 总计划重梳理，按"以代码为准"的口径盘点，一次性发现：8 个 `Fabric*Mixin` 从未注册进 `mirage.mixins.json`（导致 Fabric 三层桥接运行时根本不可达）、IR 只解析不重放（全仓库无 `.ir.` 读取点）、更新日志声称"已登记两个 Mixin"但文件里没有。

**结论**：任何"重新规划/评估进度"的动作，先跑一次代码级盘点，并把**"文档有、代码无"**单列成表。否则后面所有计划都建在假地基上，而且这类缺失通常**不报错**（见 C1），不会自己浮出水面。

### A4. 目标互斥时，摆出冲突让用户裁决，不要自行降级（2026-10-31）

`<3MB` 体积目标（当前 2.68MB）与"原生承载 KubeJS 转译"在技术上互斥。这类冲突不能悄悄砍功能或悄悄放宽指标，要明确写成待裁决问题（本轮整理出 Q1/Q2/Q3/Q5/Q9）交给用户。

### A5. "跑通"必须先落成可验证判据（2026-10-31）

"把 X 跑通"是本项目最高频也最含糊的验收语。不先定 L1/L2/L3 之类的分层判据，每轮收尾都会在"这算不算完成"上扯皮，且容易把"能启动"当成"功能可用"。

### A6. 「完善 X」类需求：先量化现状 + 找真实痛点，再动手（2026-10-31）

**背景**：用户只说「完善日志输出（不仅限于LS）」，没说什么算"完善"。

**判断路径**：
1. **先量化**：`grep -c` 统计裸输出分布（238 处 / 12 个模块），确认改造面。
2. **再找证据**：翻真实 `latest.log` 里 Mirage 的行，找"这行信息不足"的实例。这一步是决定性的——它把"统一格式"这种自嗨目标，换成了"异常 cause 被吞掉"这个真问题（`事件处理错误: null`、`InvocationTargetException` 只有类名）。
3. **然后才定方案**：门面 + 分级是手段，**展开异常链**才是目的。改造后那三行原本无解的问题立刻给出了根因。

**结论**：用户给的是方向词（"完善""优化""整理"），不是验收标准。**先量化和取证，把方向词翻译成一个具体缺陷**，再动手。否则容易做成"改了一层皮，问题还在"。

**边界**：取证要用真实产物（日志、崩溃报告、复现），不能凭读代码想象痛点——本轮若只看代码，会误判成"格式不统一"这个次要问题。

### A7. 「测试全绿」不等于测试有效——用变异检验确认它有牙齿（2026-10-31）

**背景**：给日志门面补 `scripts/verify_logging.ps1`，首轮 41 项全绿。但一个新写的测试全绿，既可能是"代码没问题"，也可能是"断言根本没测到东西"。

**做法**：把被测实现**故意改坏一处**，确认对应断言会红。本轮把 `summary()` 里的 `unwrap(t)` 改成 `t`（正是改造前的原始形态），重新编译运行，输出立刻退化为

```
[Mirage] ERROR ERR-CHAIN 注册失败: java.lang.reflect.InvocationTargetException
[Mirage] ERROR ERR-INIT 类初始化失败: java.lang.ExceptionInInitializerError
```

——与改造前线上日志一字不差，3 条断言必然失败。测试有牙齿，才算补完。

**结论**：新增验证脚本后，**至少做一次变异（一条即可，挑最核心的那条断言）**，把改动成本压到 1 分钟。
反过来也说明一件事：断言要盯**改造前的病态输出**（类名裸露、`null`、无 message），而不是盯"有没有打印"。

**边界**：变异只需证明"断言能感知差异"，不必覆盖全部断言；也不需要把变异引入 CI（凭空多一份维护成本）。


### B1. 原生崩溃的定位链（2026-10-31，可复用）

1. `hs_err` 读三件事：**崩溃线程名**、**崩溃 PC 落在哪个模块+偏移**、**寄存器指向的内存是否全零**；
2. 解析该 dll 的 **PE 导出表**，把 PC 偏移落到具体导出函数（本例 `glfw.dll+0x77a0` → `glfwDestroyWindow`）；
3. 反汇编第一条访存指令，判断是空指针解引用还是野指针（`mov rax,[rcx]` + `rcx=0` = 空链表头）；
4. **对比 hs_err 的模块列表**——同一路径族里同名 dll 出现两份，是"双实例"的强信号；
5. 最后才回 Java 栈找调用方，确认是哪一条路径调的。

顺序很重要：先拿决定性证据，再看代码。

### B2. "大部分功能正常，只有某个操作崩" → 优先怀疑同一原生库被加载两份（2026-10-31）

双实例的典型特征：只碰**传入结构体指针**的 API（`glfwSetWindowTitle`/`PollEvents`/`SwapBuffers`）全部正常，因为两份同版本库内存布局一致；只有访问**进程级全局状态**（窗口链表、单例、静态计数器）的 API 才炸。

**推论**：这类 bug 不会在启动、渲染、交互阶段暴露，只在销毁/关闭/枚举这类"要遍历全局表"的路径上出现。

### B3. 静态穷举调用点，比反复加日志收敛得快（2026-10-31）

本轮靠三条静态结论直接砍掉了大半可能性：全 MC jar 里只有 `Window.close()` 调 `glfwDestroyWindow`、只有 `Minecraft.close()` 调 `glfwTerminate`、`Minecraft.close()` 本次只执行一次。先把调用点穷举干净，再决定要不要插桩。

### B4. 修复原则：谁创建谁销毁；跨实例句柄按创建方分派（2026-10-31）

### B5. 判断「是不是我的改动引入的」→ 同命令跑旧 jar 做 A/B 对照（2026-10-31）

**现象**：改完 200+ 处日志后冒烟，游戏启动 9 秒就自己 `Stopping!` 退出。第一反应是"我把日志改坏了"——如果照这个假设去翻改动，会白查很久。

**判断**：把改动前的 jar 换回去，**用完全相同的命令**再跑一次。旧 jar 同样 9~12 秒自行退出 → 与本次改动无关，是验证方式本身的副作用（`cmd //c` + stdin 重定向到 `/dev/null`，非交互环境下 MC 会退出）。

**结论**：任何"改完就出现的新症状"，先做 A/B 对照再开始排查。成本是一次重启（几十秒），收益是直接排除或锁定整个改动面。**注意对照必须同命令同环境**，否则引入新的变量（比如这次若顺手去掉 stdin 重定向，就会得出"改了就好了"的错误结论）。

**边界**：只在能完整回退部署产物时适用（jar / 二进制）。纯源码改动要先 stash 再重建。


不要指望"让使用方直接调原生 API 也能对"。正确做法是加一层按句柄归属分派的入口（本例 `MirageEarlyWindow.destroyWindow(long)`：是早期窗口 → 用创建方 GLFW 销毁并置 `NULL` 保幂等；其他句柄原样透传），并在字节码层把 `Window.close()` 的 `glfwDestroyWindow` 改道过去。**同时覆盖所有间接路径**（本例还包括"GPU 后端重试 → 关窗"）。

## C · 工程踩坑

### C1. Mixin 静默失效：`defaultRequire: 0`（长期有效，详见 `AGENTS.md` 技术注意事项 §2）

注册了但 jar 里没有对应 `.class`，Mixin 不报错、只静默跳过。表现为"配置加载成功、游戏正常、功能就是不生效"。**任何 `mirage.mixins.json` 改动，都要 `jar tf` 核对类名是否真在 fat jar 里。**

### C2. `dumpbin` 在 Git Bash 下会被路径转换破坏（2026-10-31）

需要 `MSYS_NO_PATHCONV=1`。另外 **PE 镜像基址不一定是 `0x400000`**（本例 `0x180000000`），RVA → VA 的换算不能写死，否则反汇编地址全错、会误判崩溃点。

### C3. `glfwSwapInterval` 在没有 current GL 上下文时会报 `GL ERROR 65538`（2026-10-31，未处理）

`handoff()` 里对 MC 侧的 `GLFW_NO_API` 窗口调 `glfwSwapInterval(0)` 就会触发。**无害但污染日志**，后续清理时注意：这类窗口上不要调任何依赖 current context 的 GL 函数。

### C4. 文档漂移是慢性病，"改完就登记"要核文件不能凭记忆（2026-10-31）

更新日志写"已登记两个 Mixin"，实际 `mirage.mixins.json` 条目数与文件对不上。**登记动作要当场 `grep` 一次文件确认**，否则文档会稳定地撒谎，而且撒的谎会在几周后变成"计划地基"（见 A3）。

### C5. 工作区长期挂着 WIP 时，提交只 add 自己的文件（2026-10-31）

### C6. 批量改日志必须做「括号感知解析」，不能用字符串替换（2026-10-31）

**现象**：把 238 处 `System.out.println` 换成日志门面，看似是机械替换，实际有三个陷阱：

1. **多行拼接**：`System.out.println("[Mirage] xxx: " + a` 换行继续 `+ b + c);`，按行替换会截断语句。
2. **异常参数**：`"...失败: " + e` 里的 `e` 需要变成 `error(msg, e)` 的第二个实参，否则堆栈丢失（这是本轮改造的核心目的，丢掉就白干）。
3. **前缀重复**：门面自带 `[Mirage] `，原消息里的 `"[Mirage] "` 必须剥掉，否则出 `[Mirage] ERROR [Mirage] xxx`。

**判断**：判断"能不能机械替换"的信号——**同一模式是否跨行、参数里是否有非常量**。有就上结构化处理。

**做法**：写一个按字符扫描的小解析器：定位调用起点 → 括号计数（跳过字符串字面量与转义）→ 取出实参文本 → 用正则抽 `"[Tag] "` 前缀得到通道、抽尾部 `+ t` 得到异常变量 → 重新生成调用。比逐条手改可靠，也比 sed 安全。做完必须**抽样 grep 校验**，并跑一次编译。

**边界**：只适用于语法规整的旧代码。若原代码本来就有副作用（如 `println` 里嵌了赋值），要先人工确认再批量处理。

### C7. 日志门面不能缓存 `System.out` 引用（2026-10-31）

**现象**：`Launcher` 在 main 早期把 `System.out/err` 换成 tee 流（旁路喂 HUD 日志节选）。如果门面在类初始化时 `private static final PrintStream OUT = System.out;`，之后所有日志都绕过 tee —— 控制台照常有输出，但 **HUD 上看不到任何新日志**，且没有任何报错。

**结论**：日志门面每次写都要重新取 `System.out` / `System.err`。同理，任何"标准输出替身"必须晚于 `System.setOut` 之后再取引用。

**边界**：反过来，若某处**需要**拿到原始流（如 tee 自身），必须在替换前保存——这两件事逻辑相反，写的时候要明确是哪一种。

### C8. BOM 的两个反向陷阱：`.ps1` 必须有，`.java` 必须没有（2026-10-31）

**现象一**：新建的 `.ps1` 用工具写成无 BOM 的 UTF-8 → `powershell -File` 直接报一堆语法错
（`"("后面应为表达式`、`字符串缺少终止符`），且报错里中文全是乱码。原因是 **Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI(GBK) 解码**，中文被拆成非法字节把解析器带偏。

**现象二**：同一个脚本把自己生成的 `.java` 用 `Set-Content -Encoding UTF8` 写出（PS5.1 会**加** BOM）→ `javac` 报 `error: illegal character: '\ufeff'` + 后面全线 `需要 class、interface、enum 或 record`。原因是 **javac 不剥 UTF-8 BOM**。

**结论**：两件事方向相反，写脚本时一起记：
- `.ps1` 落盘用 **带 BOM** 的 UTF-8：`[System.IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($true)))`
- 脚本内生成的 `.java` 落盘用 **不带 BOM**：`... UTF8Encoding($false)`

**边界**：`pwsh` 7+ 默认按 UTF-8 读脚本，第一条不成立；但项目按 PS5.1 跑（`powershell -File`），照做。

### C9. `Start-Process` 在重复的大小写环境变量下会直接抛异常（2026-10-31）

**现象**：脚本里 `Start-Process -FilePath java ... -RedirectStandardOutput` 抛
`已添加项。字典中的关键字:"http_proxy"所添加的关键字:"HTTP_PROXY"`。

**根因**：本机环境里同时存在 `http_proxy` 与 `HTTP_PROXY`。Windows 的进程环境块大小写不敏感，
`Start-Process` 复制父环境时会往不区分大小写的字典里插第二个键 → `ArgumentException`。
与脚本逻辑无关，是环境特性。

**绕过**：用 .NET 直接起进程，不经过 `Start-Process` 的环境复制：

```powershell
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.UseShellExecute = $false; $psi.RedirectStandardOutput = $true; $psi.RedirectStandardError = $true
$psi.StandardOutputEncoding = [System.Text.Encoding]::UTF8
$proc = [System.Diagnostics.Process]::Start($psi)
$outTask = $proc.StandardOutput.ReadToEndAsync(); $errTask = $proc.StandardError.ReadToEndAsync()
$proc.WaitForExit()   # 先起异步读，避免缓冲区写满卡死
```

顺带解决另一个老问题：**不要用 `& cmd 2>&1`**——PS5.1 会把原生 stderr 变成 `NativeCommandError`，
配合 `$ErrorActionPreference="Stop"` 会直接终止脚本。分离取两个流反而更干净。

**边界**：这是本机环境的坑，换台机器可能不复现；但 `RedirectStandardOutput/Error` + 显式 `UTF8` 编码是跨机器都该这么写的（否则中文输出解码随控制台代码页漂移）。

### C10. 给日志写断言前，先确认它走哪条流、栈帧来自哪（2026-10-31）

**现象**：首轮验证 40/41，唯一红的是一条自己写错的断言——用 stdout 去匹配 `[Mirage] ERROR`，
而 ERROR 按设计走 stderr。

**两条容易踩的**：
1. **流**：`MirageLog` 里 WARN 及以上走 stderr、其余走 stdout。断言写错流 = 永远红；反过来，
   若断言"ERROR 不该出现在 stdout"没写，级别流向变了也测不出来。
2. **栈帧来源**：验证程序的异常若在 `main` 里 `new`，栈里只有验证程序自己的帧；这样
   **测不到**"项目帧（`io.mirage.` / `net.minecraft.` 等）在预算内被保留"这条 smart 策略。
   把验证类放进 `io.mirage.*` 包（本轮放 `io.mirage.api.log.check`）+ 造一条深递归栈，
   才能同时验到"项目帧保留"和"超预算折叠为 `... N more`"。

**结论**：写断言前先明确「这条输出应该出现在哪个流、它的栈帧会是什么形状」，再落正则。
匹配整段输出容易跨条误判，用"取从 marker 行到下一个行首非空白行"的块截取更准（本轮 `Get-Block`）。

**边界**：仅适用于自带流向/格式约定的日志门面；普通 `println` 调试不受此限。


本轮开工时工作区有 15 个改动 + 17 个未跟踪文件（上一轮的早期窗口/Fabric 特性 WIP）。这种情况下 `git add -A` 会把别人的半成品一起固化，`git checkout .` 会直接毁掉别人的活。**只暂存本轮自己的文件，并在提交信息和更新日志里注明"工作区另有 WIP 未一并提交"。**

### C11. `io.mirage.*` 强制 app 加载的白名单，会连坐它引用的 `net.fabricmc.*`（2026-10-31）

**现象**：Fabric 服务端 mixin 一注册，进世界就崩，`java.lang.LinkageError: loader constraint violation:
loader 'app' wants to load abstract class net.minecraft.server.MinecraftServer. A different abstract class
with the same name was previously loaded by 'MirageClassLoader'`。崩在 `ServerLifecycleEvents.<clinit>`
→ `FabricLifecycleBridge.fireServerStarting`。

**判断链**：`MirageClassLoader.loadClass` 对 `io.mirage.*` 直接 `ClassLoader.getSystemClassLoader().loadClass()`。
所以 `io.mirage.fabric.runtime.FabricLifecycleBridge` 是 **app 定义**的；JVM 解析符号引用用「引用方所在类的
定义 loader」，于是它引用的 `net.fabricmc.fabric.api.*` 也由 app 解析；而 stub 的静态初始化里有
`MinecraftServer` 的类引用 → app 从 `-cp` 上的 `26.2.jar` 自己 `defineClass` 一份 → 与 mcl 那份冲突。

**结论**：凡是被 mixin 织入代码调用、且自身引用 `net.minecraft.*` / `net.fabricmc.*` 的 MG 侧 helper，
必须排除在「强制 app」白名单之外。本轮按既有 `io.mirage.neoforge.` 先例加了 `io.mirage.fabric.`。
**边界**：只对"被 mcl 侧字节码调用"的类成立；纯 app 侧工具（Launcher、MirageDebug）仍应走 app，
否则早期窗口会拿到两个单例（见 `已知bug.md` 该条）。

### C12. `:launcher:mirage-launch:build` 会把 fat jar 覆盖成瘦 jar（2026-10-31）

**现象**：照 `build` 命令构建后 `build/libs/mirage-launch-0.1.0.jar` 从 2.6 MB 变 67 KB，部署后启动即
`NoClassDefFoundError`，但 `jar tf` 看着"有类"——只是没有依赖。

**原因**：`build` 会跑标准 `jar` 任务，与 `fatJar` 共用 `archiveClassifier=""` 的输出名，谁后跑谁覆盖。

**结论**：部署前一律用 `:launcher:mirage-launch:fatJar`，并核对产物大小（~2.6 MB 量级）与
`unzip -t` 通过。**边界**：只跑 `fatJar` 时它 `dependsOn(runtimeClasspath)`，子模块 jar 仍会重建，不会打包旧字节码。

### C13. 判定「注入成功」要看两个层次：`[MODIFIED]` 只证明改了字节码（2026-10-31）

**现象**：`transform … [MODIFIED]` 一出现很容易当作收工，但 `MirageMixinBootstrap.transform` 的 catch 会吞异常
返回原字节码；反之 `[MODIFIED]` 也可能只是别的 mixin 改了同一个类。

**做法**：在 bridge 的 `fire*` 里放**每种事件首次触发打一行**（高频事件用 `Set.add` 去重），
用日志证明"回调真被调到"。本轮靠这行才发现 `CLIENT_PLAY_DISCONNECT` 一直没触发（客户端自己退出不走
`onDisconnect`），而不是想当然认为"注册了就会 fire"。

**边界**：打点必须是"首次一行"，否则 tick 类事件会把日志刷爆、淹没其它线索。

### B6. 要改字节码，先读 `loadClass` 确认类到底在哪一层被定义（2026-10-31）

**现象**：想给沙盒里的 mod 类加改写，直觉是重写 `defineClass`，结果一行都不生效。

**判断**：`URLClassLoader` 的默认路径是 `loadClass`（parent-first）→ 父找不到才进本 loader 的
`findClass` → 由**继承的** `findClass` 读资源并 `defineClass`。自定义 `defineClass` 只有在自己的
代码里显式调用时才被经过。所以挂点必须是 `findClass`。

**做法**：先读 `loadClass` 的 override（本项目 fake 包走 `findFakeClass`，其余走 `super.loadClass`），
确认目标类实际落在哪条分支，再决定改哪里。**验证**：改写后必须看到"改写了几处"的日志/计数，
而不是"类能加载"就当作生效。

**边界**：接管 `findClass` 后 `defineClass` 的默认保护域没有 `CodeSource`，靠
`getProtectionDomain().getCodeSource().getLocation()` 定位自己 jar 的 mod 会变成 NPE——要显式构造
`ProtectionDomain`（见 C15）。

## C · 工程踩坑（续）

### C14. `jar:file:/x.jar!/…` 的 `getPath()` 不能直接喂 `new File(...)`（2026-10-31）

**现象**：P0 的 fake 包枚举写了 `new File(u.getPath())`，在 Windows 上路径是
`file:/D:/x.jar!/mirage/sandbox-fake/`，`File` 构造抛异常，而外层是 `catch (Exception ignore) {}` →
**静默失败**，一直靠写死的 `net.minecraft./net.neoforged.` 兜底，看起来"一切正常"。

**做法**：`u.getPath()` 只取 `!/` 之前的 `file:/D:/x.jar`，再 `URI.create(...).toURL()` →
`new File(url.toURI())`。更稳的定位方式是**用本类自己的 code source**
（`SandboxRecorder.class.getProtectionDomain().getCodeSource().getLocation()`）再判断 jar/目录。

**识别特征**：功能"靠兜底能跑"，但一旦需要**按内容判定**（本轮是算 fake 表面指纹）就立刻暴露为
`none`/空集。所以凡是"扫描类路径资源"的代码，都要有一个能被证伪的观测点（指纹、计数），
否则永远不知道它在不在工作。

### C15. 替换调用时保持栈形状，就不要碰 `COMPUTE_FRAMES`（2026-10-31）

**做法**：把 `System.exit(I)V` 换成静态 `exit(I)V`、把 `Runtime.halt(I)V` 换成静态
`halt(Ljava/lang/Runtime;I)V`（接收者当第 0 参），操作数栈净效应完全一致 ⇒
`new ClassWriter(reader, 0)` 原样保留 StackMapTable 即可，**不需要**重算帧。

**为什么值得强调**：本项目有过"ASM 改过的类再交给 Mixin 转换就失败"的历史（`AGENTS.md` 技术注意 §9），
重算帧会让 class 进入"被 ASM 深度重写"的状态，更容易与后续转换打架。**边界**：一旦改写要新增分支、
改变局部变量表或栈深度，就必须 `COMPUTE_FRAMES`（并自己传 `getCommonSuperClass` 的 loader，
否则会拿到错的公共父类）。

### C16. 验证脚本"按前缀取行"时，一个前缀只能对应一行（2026-10-31）

**现象**：P2 脚本里 7 条缓存断言共用一个 `CACHE` 前缀（`CACHE fresh …` / `CACHE incompleteStored …` …），
而取值函数是"返回第一行以该前缀开头的" ⇒ 7 条断言全拿到同一行，6 条立刻变红，看起来像实现全坏了。

**做法**：每个用例一个**唯一前缀**（`CACHE-FRESH` / `CACHE-TMP` / `CACHE-TMPONLY` …），
或者在 harness 里统一加序号（`CASE-1-a`）。判据：断言读到的文本里必须包含该用例的特征键，
不能只靠"前缀匹配成功"。

**顺带**：PowerShell 的 `-match` 默认**不区分大小写**，所以断言里写 `True` 而 Java 打 `true` 也能过——
别把这当成"格式被校验过了"。

### C17. 缓存"无变化不写"要用 mtime 验，"原子写"要验"只剩 .tmp 时读不到"（2026-10-31）

- **无变化不写盘**：不能比内容（内容本来就一样），要在两次写之间 `sleep 60ms` 再比
  `Files.getLastModifiedTime`；NTFS 时间戳精度足够，同毫秒也不会误判成"重写了"。
- **原子写**：真正的判据不是"有个 `.tmp`"，而是**只剩 `.tmp`（模拟 kill -9）时 `lookup` 必须返回 null**。
  实现侧靠"`isCacheFile` 只认 `.json` 后缀 + `ATOMIC_MOVE`"，测试侧就验这条。

### C18. 两条采集链路合并数据：并集，而不是"新的覆盖旧的"（2026-10-31）

沙盒（fake 表面全量）与被动捕获（自有入口）看到的**不是同一个集合**，谁都不是全集。
所以 `MidCache.merge` 取并集 + 计数取大值；相应地，**diff 的比较对象必须是合并后的结果**，
否则"上次沙盒录到一批、这次被动录到另一批"会被报成大面积删除，diff 报告直接变成噪音。

### C19. 「只把状态塞进队列」的 API，不能用"没报错"证明它生效（2026-10-31）

**现象**：加载界面把文字从「AWT 光栅化 + fill」改回 `gge.text(Minecraft.font, ...)` 后，
红底、内存条、两条进度条全对，**一条文字都没有**，`latest.log` 里连 WARN 都没有；
代码上"看起来没毛病"——反射解析到了方法、`font` 非 null、调用没抛异常。

**判断路径**：
1. 先排除"画错位置/被盖住"：同一帧里 `fill` 画出来的条是可见的 ⇒ 管线、坐标、alpha 都正常，
   问题只可能在文字这条支路。
2. 读 MC 字节码（`javap -p -c`）：`GuiGraphicsExtractor.text(...)` 全链路只有一句实质操作——
   `guiRenderState.addText(new GuiTextRenderState(...))`，参数非空才入队，**不画像素、不抛异常**。
   于是"调用成功"这件事**没有任何验证价值**。
3. 再看原版自己怎么用：`LoadingOverlay.extractRenderState` 只做 `fill` + logo `blit`，
   **一个 `text()` 都不调**。原版不用的东西，在同一个时点上大概率是不能用。
   结论指向字形图集——LoadingOverlay 显示期正是首次资源重载进行中，字形提供器还没装载，
   每个字符解析不出字形 ⇒ 静默画空。

**结论**：判断"某绘制 API 是否生效"只能看**目标像素**，不能看返回值/异常/日志。
凡是"只登记状态、延后出图"的 API（`text`、deferred render state 一类），
"没报错"和"没画出来"是兼容的。同理，**原版在同一处不用某个 API，本身就是最强的反面证据**。

**边界**：`gge.fill` / `blit` 在重载期可用（进度条、logo 都是证据），所以该阶段的文字只能走
「AWT 光栅化成像素块 + fill」。

### C20. 像素字"糊成马赛克"多半是光栅化尺寸没对齐，不是像素字本身不行（2026-10-31）

**现象**：上一版把文字画成马赛克后，结论被写成"像素字必然糊"，于是转去用 `text()`（撞上 C19）。

**真因**：固定按 12px 光栅化，再在 GUI 空间按 `sx = guiWidth/854` 缩放绘制。
`sx < 1` 时相邻两列字形像素被压进同一个 GUI 像素、另一列被跳过，边缘必然锯齿糊死。
**正确做法**：先按**目标 GUI 像素尺寸**光栅化（`px = round(设计字号 × sx)`），再 1:1 落 GUI 像素，
每个字形像素恰好占一个 GUI 单位——和 MC 自带位图字体在 `guiScale > 1` 时的放大方式一致。

**实测数值（Consolas 无抗锯齿）**：12px 墨迹 Cap 高约 6px、14px 约 7~8px（≈ MC 字体 9 GUI 单位的视觉大小）、
"Loading mods" 14px 宽 98px、"Memory: …/…MB (…%)  CPU: …%" 14px 宽约 310px（854 宽画布居中不越界）。
判据：`fill` 块数（854×480 下 445 个）与墨迹总面积（1212 px）都可离线断言，
不需要开游戏就知道字到底画没画出来——见 `scripts/verify_forgestyle_text.ps1`。

### C21. `latest.log` 里没有 S1–S3 —— log4j 接管之前的 stdout 根本没落盘（2026-10-31）

**现象**：MSR P2 实机冒烟，按清单去 `latest.log` 找 `[Sandbox] 录制` / `[MID] 被动捕获`，一行都没有，
差点被判定成"P2 没生效"。同一份日志的第一行就是 `[LS] stage S4 RegistryMerge done`。

**根因**：log4j 直到 Minecraft 启动后才接管日志并写 `latest.log`。在那之前的 banner、早期窗口、

3. 回归脚本 `scripts/verify_launch_log.ps1`：反射调 private `Launcher.installLogTee(Path)`，

### C24. Gradle 报 `Unable to delete file '…/build/classes/java/main'` 时，先试重命名（2026-10-31）

### C28. `MirageClassLoader` 的 parent 是 platform loader：第三方库会"被"双份加载（2026-10-31）

**现象**：进世界后视角转不动。WASD、左键挖、滚轮全正常，光标隐藏、`mouseGrabbed=true`，
但 `MouseHandler` 的 `ignoreFirstMove` 永远 `true`、`accumulatedDX/DY` 恒 0——
**`onMove` 一次都没被调用**；而回到主菜单光标立刻正常。关「原始输入」无效。

**定位法**：`FabricClientTickBridge` 里加一次性探针（反射读 `MouseHandler` 字段 +
`glfwGetInputMode`/`glfwGetCursorPos`），实机跑一轮看哪个判据先变。
`ignoreFirstMove` 只有 `onMove` 真被调用才会置 `false`，它是"回调有没有到"的最干净判据。
（探针源码会被并行分支覆盖，**要留证据就趁 jar 还在时 grep 日志**。）

**真因**：`TransformStage` 用 `new MirageClassLoader(urls, ClassLoader.getSystemClassLoader().getParent())`
创建 MCL——parent 是 **platform loader**（不含 lwjgl），`urls` 却是整条游戏 classpath。
于是 MCL 走 `super.loadClass` 时在**自己的 URL** 里找到 `org.lwjgl.glfw.GLFW` 并 define 出**第二份**。
铁证两条：①`lwjgl-unsafe-agent` 的 `Successfully transformed MemoryUtil` 打印 **2** 次
（AppClassLoader 一次、MCL 一次）；②探针 `Class.forName(GLFW)` 与
`ClassLoader.getSystemClassLoader().loadClass(GLFW)` **不相等**。

后果是经典的「两份 glfw.dll 模块」：早期窗口（AppClassLoader 的 GLFW-A）`CreateWindow`，
MC 的 `glfwSetInputMode(GLFW_CURSOR_DISABLED)` 打在 GLFW-B 上，只置 **B** 的
`_glfw.win32.disabledCursorWindow`；真正处理 `WM_MOUSEMOVE` 的是 **A** 的 WndProc，
它查 A 的该全局（仍 NULL）直接 `break`——所以**只有光标位移被吞**，
`WM_LBUTTONDOWN`/`WM_KEYDOWN` 不查这个标记，点击键盘照常。
（同因还造成过退出期 `glfwDestroyWindow` 崩溃，见改动登记表 10-31 那行。）

**修法**：与 `io.mirage.*` 完全同构——`org.lwjgl.*` 也强制 `ClassLoader.getSystemClassLoader().loadClass`，
两份 GLFW 合一、`_glfw` 全局共享。`MirageEarlyWindow.shareLwjglNatives()`（统一
`org.lwjgl.librarypath` 到同一个 native 目录）作为兜底仍保留，但它**解决不了 Java 类双份**，
单用它修不掉这个 bug。

**判据（修复后实测）**：`sameGlfwClass=true`；`MemoryUtil` 只重写 **1** 次；
`acc=(20,18)(-32,0)(-14,0)…` 真实累计、`ignoreFirst` 翻 `false`。

**通用教训**：MCL 的 parent 是 platform loader 这件事意味着**任何第三方库**（lwjgl/netty/asm/…）
只要被 MCL 和 app 同时引用，就是两份类、两份 native 静态状态。新增第三方依赖时先问一句
"这个库有没有进程级单例/原生全局状态"，有就必须进 `loadClass` 白名单。

### C29. 加载界面文字的「AWT 光栅化」必须放在渲染线程之外（2026-10-31）

**铁律**：渲染线程（`LoadingOverlay` 的 `ForgeStyleOverlay.draw()`）**严禁碰 AWT**。任何 `BufferedImage` / `Graphics2D` / `FontMetrics` / 系统字体枚举都只能放在启动早期主线程的 `prewarm()` 一次性做完，渲染线程只查缓存拼装 + `fill`。

**踩过的坑**：第一版在 `draw()` 里每帧光栅化整串文本（内存行每帧变 → 缓存 key 永不命中 → 每帧重跑 Java2D 字体管线）→ GLFW 消息泵被占住 >5s → Windows 判「未响应」。中间版整串**异步**光栅化（守护线程）首帧必然无字、MIN_PRIORITY 守护线程还可能被加载繁忙饿死。

**终版做法**：**字符级预渲染**——`prewarm()` 把 ASCII 32–126 字形一次性光栅化进 `GLYPH_CACHE`（等宽字体按字符步进拼装）；渲染线程只查表 + `fill`，零 AWT、首帧即有字、任意动态串（Memory/CPU）即时出图。字号在 GUI 空间取固定 `GUI_TEXT_PX=10`，**绝不**按 `guiWidth/854` 缩放（否则 GUI 427×240 下算出 7px，笔画细到断笔）。

**配套回归**：`scripts/verify_forgestyle_text.ps1`（须先 `prewarm()` 再 `draw`；现场 javac 编译 + 假 `GuiGraphicsExtractor`，断言字形块数/墨迹面积/不越界/内存文字居中/版本号右对齐/四文字带各有字 + 源码守卫禁 `drawTextSafe`/反射 `text`）。

### C30. 修「主窗口无文字」顺手根除 `[Probe]` 临时诊断刷屏（2026-10-31）

`FabricClientTickBridge` 里两处 `[Probe]` 临时诊断（`fireEndTick` 内 `probe` + `fireStartClientTick` 内 `noteMove`/`noteGlfwIdentity`，视角回归遗留）每 10~20 tick 打一行 INFO，是"日志刷屏"元凶之一。这类临时诊断定位完必须**整段删除**（含私有字段与 helper），否则既刷屏又留 dead code；删除按行号精确切除后 `grep [Probe]` 验证无残留。

**顺带踩的打包坑**：fatJar 配置已 `dependsOn(configurations.runtimeClasspath)`，但 `from(configurations.runtimeClasspath.get().filter{...}.map{...})` 在**配置阶段**就把 FileCollection 物化成普通 List——若中途 `rm -rf` 某子模块 build 再跑 `:launcher:mirage-launch:fatJar`，配置阶段解析时该 jar 已被删 → 被静默排除出 fat jar，产物悄无声息缺模块（曾让 fabric-compat 没打进去、jar 小 58KB）。**改完代码后不要 `rm` 子模块 build，直接增量 `:fatJar` 即可。**

### C31. Mixin 关键失败被 `catch` 降级 = 功能静默消失，比崩溃更难查（2026-11-01）

`MirageMixinBootstrap.transform` 原来对**所有**异常一律 `catch → 打一行 warn → 返回原字节码`。
这个降级看起来稳妥，实际制造了最阴的一类故障：**配置加载成功、字节码没报错、游戏照常能玩，
只是某个功能永远不触发**，且日志里只有一行"转换 X 失败"，事后很难还原现场。

关键失败必须**致命化**：识别 `InjectionError` / `InvalidInjectionException` /
`InvalidTargetException` / `TargetNotFoundException` / `CriticalInjectionError` /
`MixinApplyError` / `MixinTransformerError`，直接抛 `Error`（不是 `RuntimeException`——
上层大量 `catch(Exception)` 会把它吞掉），让启动崩。判定用**类名字符串**而非 `instanceof`，
避免对 mixin 包内多个子包的编译期依赖，也避免 mixin 升级换包名后编译失败。

打日志时必须拼**完整异常链**（`describeChain`）：「目标方法 + mixin 名」只写在 Mixin 内层
异常的 message 里（`Injection failed into the target method 'onDisconnect' in the mixin
'FabricClientDisconnectMixin'`），只打最外层异常就丢掉这段，等于没定位到具体注入点。

**更根本的一层**：光靠运行期致命化不够——等它炸说明已经漏过去了。必须配**构建期离线校验**
对着真实字节码查（`scripts/verify_mixin_registry.ps1`）。注入点失效有三种形态，全都能静态查：
① **漏注册**（源文件不在 `mirage.mixins.json` 里）——检查要**双向**，只查"json 里有源文件"
抓不到这一半；② **目标方法不在目标类里**（F1 的 `onDisconnect` 实际在父类）——查方法时要
**沿父类链**找；③ **目标类/字段/被调方法不存在**——用 `javap` 对着原版 jar 查。

### C32. 解析 `javap` 输出与 PowerShell 正则的两个坑（2026-11-01）

- **构造器在 `javap` 里没有返回类型**：形如 `public net.minecraft.commands.Commands(A, B);`，
  与普通方法 `public void tick(X);` 结构不同。而 `@Inject(method = "<init>(...)V")` 注入的正是它，
  必须单独识别成 `<init>`，否则构造器注入点会被误判成"方法不存在"。
- **正则里带尾随空格的可选分组，后面不能再要求 `\s+`**：写成
  `^(?:public |private )\s+(\w+)\(` 时，前缀组已经吃掉了那个空格，`\s+` 永远匹配不上，
  表现为"正则看起来对但一条都不中"。写 `(?:public|private)\s+` （空格移出分组）才对。
  这类"看起来没道理就是不中"的正则，先单独把样本行拿出来测，别在脚本整体里猜。
- **注入方法名有两种写法**：裸名 `"tick"` 与带描述符 `"tick(Ljava/util/function/BooleanSupplier;)V"`，
  提取时统一剥到标识符部分；`<init>` 要单独放行。

### C33. 测试「输出流向」要按消息内容判定，不要按前缀判定（2026-11-01）

验证 MEL 的分流时写了「stdout 里不应出现 `[MG-WARN]`」，结果误报：检查程序自己打印的 `MirageException.toString()` 本来就含 `[MG-WARN]` 前缀，它是合法输出。改成按**消息内容**判定（如「stdout 不含 warn-case」/「stderr 不含 ignore-case」）后通过。

教丝：**判定「这个流里有没有某类输出」要按内容特定字符串，不要按前缀（前缀很容易被其他合法输出带出）。** 另：测试自身的输出也是被测对象，断言前先看一眼测试程序自己打了什么，避免自岁a。

### C34. 性能测量先分阶段，一次就能看出靶子（2026-11-01）

原计划只有一个「启动时间」指标，实测出来端到端 23.6~70.3 秒、波动 3 倍，无法判断是哪里慢。拆成分阶段后一眼看出：**S4 RegistryMerge 占 6.8~25.9 秒，是唯一的大头**；而 S1+S2+S5+S6 合计仅 0.6~1.1 秒。且 S4 的波动远大于其他阶段，说明它大概率是**等待**（如等 tick 推进注册窗口）而不是计算。

推论：**测量粒度应当先拆到阶段，再看哪个阶段大；只看总数的话，无法引导行动。** 同理，面向用户的指标（「点开游戏到能玩」）与面向开发者的指标（「MG 自己开销多少」）要分开计量——S7 Loaded done 是「mod 管线结束」，不等于「TitleScreen 就绪」，后者目前没有锚点，得补。

**【已过时·2026-11-01 · 被 C35 修正】** 上面「S4 是唯一的大头」是**误判**：当时只抄了 S1~S6、只抄了 6 个会话里的 4 个，**整段漏掉了 S7 Loaded**（实测 23.6~68.1 秒，比 S4 还大），还漏掉了 S4 = 40 213 ms 的那个会话（把上界记小了 55%）。「S4 大概率是等待而不是计算」这个推论同样未经证实——S4 内部的大头是 `Bootstrap.bootStrap()`，那是 **MC 原版**的成本。同段末尾「后者目前没有锚点，得补」也已过时：锚点已于 2026-11-01 补上（`MiragePerf.mark("titlescreen")`）。

### C35. 手抄的性能基线会漏阶段——必须由脚本从日志生成（2026-11-01）

C34 结论里的「S4 是唯一的大头」被证伪。写 `scripts/measure_startup.ps1` 把 8 个会话全量解析一遍后发现两处漏：

1. **整段漏掉 S7 Loaded**（实测 23.6~68.1 s，比 S4 还大）。当时把 `S7 Loaded done` 当成「终点」而不是「一个阶段」，于是占大头的它根本没进表。
2. **漏掉 8 个会话里的 3 个**（含 S4 = 40 213 ms 的那个），S4 上界被记成 25 918 ms，比实测小 55%。

根因不是「抄错数字」，是**抄的时候只看了自己当时关心的阶段**——人抄的表会被当时的关注点污染，而且事后看不出漏了。

对策：把测量写成脚本，`docs/perf-baseline.md` 只留脚本生成的表 + 指向脚本的用法；脚本要**如实报告哪些维度测不了**（缺锚点就列出来），不要填 0 糊过去——「0 ms」会被读成「这段不花时间」，是假数据。

### C36. 变异检验的第二个作用：发现测试**没测到**的地方（2026-11-01）

给 `measure_startup.ps1` 做变异检验时，第一种变异（把段定义里的锚点名 `s4.version` 改成 `s4.versionX`）**退出码仍是 0**。原因：段定义共 10 条，自检只断言了其中 5 条的值，被改的那条**没有任何断言盯着**，于是它算出的 `null` 没人看——**测试全绿，但测试是残的**。

修法：加一条「段定义表自洽」断言（样本里每条定义的 from/to 锚点都必须存在，且每段算不出耗时就必须为 `null` 而不是 0），再补渲染层断言（缺锚点的段在报告里必须显示「缺锚点」，不能显示「0 ms」——报告给人看时，假数据比空值更有欺骗性）。

推论：**变异检验不只用来证明「测试有效」，也用来证明「测试覆盖完整」。** 一个变异打不红，往往不是变异无效，而是**那个位置根本没被测**。判据：故意破坏后退出码必须变红；变绿就说明该处缺断言。

### C37. PowerShell 的 `cd` 不改 .NET 的当前目录（2026-11-01）

在 PowerShell 里 `cd D:\xxx` 之后，`Copy-Item ".\a.ps1"`、`powershell -File .\a.ps1` 都能找到文件，但 `[System.IO.File]::ReadAllText(".\a.ps1")` 报「未能找到路径的一部分」——因为 .NET API 用的是 `[Environment]::CurrentDirectory`，它**不随 PowerShell 的 `cd` 变**。

后果：同一段脚本里两种路径语义不一致，且**报错信息是「文件不存在」**，极易误判成「文件真没了」或「替换逻辑写错了」——本轮就因此把三次变异检验全跑成了「替换未命中」。

对策：脚本里凡是用 .NET API 读写文件，一律传**绝对路径**；或者在脚本开头用 `$PWD.ProviderPath` 取绝对路径。

### C38. PowerShell 里 Markdown 反引号是转义符（2026-11-01）

脚本要生成 Markdown，习惯性写了 `` "> 数据来源：`" + $LogPath + "`" ``。PowerShell 的反引号是转义符，双引号字符串里的反引号会吃掉后面的字符，解析器报「方法调用中缺少 `)`」，而**报错位置指向那一行、看不出真正原因是反引号**。

对策：含 Markdown 反引号的字符串一律用**单引号**字符串（单引号里反引号是字面量）：`'> 数据来源：`' + $LogPath + '`'`。另：`.ps1` 必须带 UTF-8 BOM（否则 PS 5.1 按 GBK 读，中文乱码且直接语法错），但 `.ps1` 里**生成的 `.java` 不能带 BOM**（C8）。

### C39. multi-catch 不能捕获有继承关系的两种异常（2026-11-01）

写 `catch (JsonParseException | RuntimeException e)` —— **这是编译错误**，javac 报「multi-catch 中的异常类型之间有继承关系」。因为 `JsonParseException extends RuntimeException`，Java 不允许在 multi-catch 里同时列一个类及其父类。

坑在它长得太像「冗余但无害的写法」，而且**平时不写 multi-catch 的人不会想到**。本轮它是离线回归第一次运行时被抓出来的（javac 直接报错），比 gradle 构建早一步——说明「把纯逻辑拆出来单独编译」这件事本身就顺带抓到了构建期错误。

对策：只捕 `RuntimeException`（它已包含 `JsonParseException`）；若要区分处理，用两个 `catch` 分支或 `instanceof` 判别。

### C40. Gradle 9 移除了 `archivesBaseName`，而它在本项目里本来就是多余的（2026-11-01）

三个模块的 `build.gradle.kts` 里写了 `archivesBaseName.set("mirage-config")`，Gradle 9.1 构建直接失败：`Unresolved reference 'archivesBaseName'`（该 API 在 8.x 起废弃、9.x 移除）。

更值得记的是**它根本不需要**：gradle 默认就用项目名做 archiveBaseName，而 `settings.gradle.kts` 里 `include(":modules:mirage-config")` 的项目名就是 `mirage-config`，产物本来就是 `mirage-config-0.1.0.jar`。

推论：加构建脚本配置前先问一句「默认行为是不是已经是我要的」。凡是「把名字再声明一遍」式的配置，要么是历史迁移残留，要么是**用配置掩盖了真实的隐含依赖**——本例里 `ModuleRegistry.moduleJar` 按「文件名以模块 id 开头」匹配，**项目名必须等于模块 id**，这是条隐含依赖，值得写进注释而不是写一行冗余配置。

### C41. 在测试里重写一遍生产算法 = 测副本，不是测代码（2026-11-01）

给 G9 写离线回归时，我在**检查程序里**重写了一份依赖闭包算法（因为 `ModuleRegistry.collectClosure` 是包级可见、检查程序在子包下够不着）。跑出来 23 断言全绿，看着很稳。

但它测的是**检查程序里那份副本**，不是生产代码。生产代码若算错了，测试照样全绿——这正是「全绿的测试可能根本没测到东西」的典型形态（与 C36 同源，但更隐蔽：C36 是断言数量不够，这个是**断言打在被测对象之外的副本上**）。

修法两步：
1. **把纯逻辑抽成不依赖重物的类**：新建 `ModuleGraph`（只依赖 `ModuleDescriptor` 与纯 POJO `ModManifest`），`ModuleRegistry` 委派给它。这样闭包算法能离线编译。
2. **检查程序直接调生产代码的 public 静态方法**，不再重写副本。

推论：写测试时先问「**我这条断言打在谁身上**」。如果答案是「我刚写的一份等价实现」，那这条断言的价值是零。生产方法因为访问修饰符够不着而无法直接调用时，**该改的是生产代码的结构（抽类），不是测试的做法**。

### C42. PowerShell 取子进程输出：Write-Host 捕获不到、StandardOutput 只能读一次、必须先读流再 WaitForExit（2026-11-01）

写 `verify_module_loading.ps1` 时连踩三个坑，症状都是「脚本跑了但看不到任何输出」：

1. **`Write-Host` 走信息流**（PS 5.0+），不是标准输出。父进程里 `& powershell -File x.ps1 2>&1 | Out-String` **捕获不到**，而 `2>&1` 只合并错误流。→ 对策：脚本把明细**落盘成报告文件**，父进程读文件；这顺带对 CI 有用。
2. **`Process.StandardOutput` 只能读一次**：它返回的是 `StreamReader`，第二次读拿到的是**剩余空串**。本轮原本读了两遍（一次打印、一次拿去正则匹配计数），于是计数合并**静默失效**——不报错，只是永远匹配不上。→ 对策：`ReadToEnd()` 一次，存变量复用。
3. **必须先读流再 `WaitForExit()`**：反过来在子进程输出超过管道缓冲时会**死锁**（父进程等退出、子进程等写入）。

另：`[Diagnostics.Process]::Start` / `Start-Process` 在部分执行通道里被安全策略拦截（但**写在 `.ps1` 文件里**再执行则放行），遇到「命令被拦」时先考虑换个落盘/委托方式，别在同一条路上反复试。


### C43. 一项能力被文档归到多个实现类时，逐个 grep 调用方——死代码会让完成度虚高（2026-11-01）

**现象**：缺口清单把「fabric.mod.json 解析」写成 `FabricModManifest` + `ModsJsonParser` 两个类并列；盘点时 grep 发现 `ModsJsonParser`/`OutputModel`（fabric-compat 包下那对）**全仓无任何调用方**——是硬解码器早期遗留。更隐蔽的是：`ModsJsonParser` 里解析了 `accessWideners`/`mixinConfigs`，让"accessWideners 是否已解析"的存疑项看起来接近完成——**死代码里的已实现 ≠ 运行时已实现**。

**判断路径**：`Grep ModsJsonParser|OutputModel` 全仓 → 命中只有文档与自身 → 定案死代码；再对照 `ModDiscoverer` 确认运行时唯一解析路径是 `FabricModManifest`。

**结论/边界**：盘点完成度时，"文档说有"和"代码里有"都不算数，要找**从入口可达的调用链**。删除死代码前先 grep 一次并留档（本轮只标注未删除，与 WIP 收口策略一致）。

### C44. 模块搬迁后，旧文档的引用不会自己搬家（2026-11-01）

**现象**：LS 拆分把 entrypoints/DIST 逻辑从 `Launcher` 迁到 `lifecycle-starter` 后，缺口清单和 AG 总计划仍写 `Launcher.callOnInitialize` / `Launcher.DIST`——按图索骥去 `Launcher.java` 里 grep 什么都找不到。

**结论/边界**：盘点"实现细节在哪个文件"这类问题时，一律以 grep 当前符号为准，不信任文档里的类名/方法名；发现漂移按规则 9「标注原文 + 追加正确内容」。搬迁类改动的验收清单里应含"旧引用是否需要同步"一项。

### C45. "极简 mod 能跑" ≠ "真实 mod 能跑"：结构性缺口按链接期依赖分类（2026-11-01）

**现象**：Fabric 兼容层的实机验证都是"注册 lifecycle/tick 回调"的极简 mod，全绿；但真实 Fabric mod 几乎必然踩三类**链接期**硬伤——① 调 fabric-api 未实现的事件类 → `NoClassDefFoundError`；~~② mod 自带 mixin config 不被加载（`FabricModManifest` 不解析 `mixins` 字段、mixin 引擎只认自家单一配置）→ mixin 派生类型 `NoClassDefFoundError`/`NoSuchMethodError`~~【②的表述已过时·2026-11-01 二次修订，见 C46】；③ accessWidener 未放宽 → `IllegalAccessError`。

**结论/边界**：评估兼容层覆盖面时，把缺口按「链接期炸」（类/方法/访问缺失，mod 完全起不来）与「行为缺口」（跑了但语义偏差）分两档——链接期档优先级天然更高，且**验不出来**（现有极简 mod 冒烟永远不会碰它），只能靠代码盘点暴露。本轮据此把「mod 自带 mixin config」新列为缺口（清单 P1-13），并定案 accessWideners（P2-9）。

### C46. grep "调用方为零"不等于"功能不存在"——先查调用链再下结论；Mixin config 名不带 .json 后缀会被静默吞（2026-11-01）

**现象**：P1-13 第一轮盘点只 grep 了 `MirageMixinBootstrap`，看到 `addConfiguration(c)` 循环就断言"只加载自家单一配置"，据此写进了三份文档。第二轮（用户说"开始"）查调用方才发现 `TransformStage` 早就扫描注册 mod 的 `*.mixin.json`——**功能一直在，但从没生效过**：注册名被 `substring` 去掉了 `.json` 后缀，而 Mixin 0.8.7 的 `Mixins.addConfiguration → Config.create`（javap 取证）对传入名**原样**调 `getResourceAsStream`，查不到抛 `IllegalArgumentException` 被 `createConfiguration` 静默吞掉（"Error encountered reading mixin config ..."，走 Mixin 自家 logger，不进 Mirage 日志）。连带 `MirageMixinService` 剥 `compatibilityLevel` 的后处理分支也从未触发（资源名匹配不上 `endsWith(".mixin.json")`）。

**判断路径**：`MirageMixinBootstrap.init(mcl, configs)` 的 configs 参数 → grep 调用方 → `TransformStage` → 发现既有扫描 → 对比"自家带后缀 / mod 不带后缀"的注册名差异 → javap Mixin 0.8.7（gradle 缓存 jar 解包）逐方法看 `addConfiguration/create/createConfiguration` 三段字节码定案"原样查资源 + 静默吞"。

**结论/边界**：
- **"调用方为零"的判断对象要看清**：C43 判的是"类没有调用方"（死代码）；本轮误判的是"入口方法没人传 mod 的 config"——**入口有调用方，只是参数内容错**。查功能存在性要顺着调用链走到参数构造处，不能停在入口。
- **第三方库"静默吞异常"的坑**：Mixin 对解析失败的 config 只在自己 logger 里打一行（默认 logger 通道很可能不进宿主日志），表现是"注册了、日志没报错、就是不生效"——与 AGENTS 技术注意事项 §2（`defaultRequire: 0` 幽灵 bug）同一形态。给第三方注册表/配置传名字时，先反汇编确认名字的规范化语义（本例：不补 `.json`）。
- **基线被 WIP 打红时的处置**：本轮 `gradle build` 在动手前就红（EarlyFont 的 `q.v1()` 笔误——把自家 record 访问器名误写到 STB quad 上，实际方法是 `t1()`）。语义唯一解的两字符笔误直接修掉并在台账注明，不为它停下来问；整文件半成品则不提交、留工作区。
- 修复后 mod mixin config 第一次真正生效：以 Mojang 映射重编译且 mixin 写错的 mod 会触发 FATAL 政策（预期行为）；intermediary 名的目标类不会被加载、无此风险。


### C47. Fabric depends 里有"永远缺席"的运行时键，透传给硬抛型检查器 = 全体 mod 被误杀（2026-11-01）

**现象**：P1-14 做 depends 检查时发现两条会合流的坑——① fabric.mod.json 的 `depends` 混有 `minecraft`/`java`/`fabricloader` 等运行时键，它们永远不在 mod 容器集里；② 既有 `DependencySorter` 对缺失依赖是**硬抛 IllegalStateException**（NeoForge 路径靠"只放 mandatory 的 mod 间依赖"躲开）。若把 Fabric depends 原样透传进 `manifest.depends`，几乎每个真实 Fabric mod 都会在发现阶段被炸死。

**结论/边界**：
- 依赖键要按"由谁满足"分桶，不是按"在不在容器集"二分：运行时键由加载器本体满足（过滤+debug），mod 依赖才进拓扑排序。
- **硬抛还是 WARN 要看语义建模完整度**：Fabric `provides` 聚合语义（`fabric-lifecycle-events-v1` 实际由 fabric-api 聚合 jar 提供）没建模前，对"缺失"硬抛/WARN 跳过都会误杀实际能跑的 mod——本切片选 WARN 不阻断，把升级硬抛与 provides 支持绑定在一起。
- 同文件混改时用 git status 的 WIP 名单圈禁区：本轮 UI 会话挂着 `DiscoveryStage`/`ParseStage` 等 WIP，依赖检查全部收敛在 `core/mirage-loader`（两阶段检查放发现收尾而不是 LS 阶段，就是为了绕开）。
- PS1 双引号串里 `\"` 不是转义（M4 变异源串解析炸），含双引号的字面量用 PS 单引号串。

### C48. 同一套布局常量喂两个渲染器，"y 是行盒顶还是字形锚点"必须分开命名（2026-11-01）

**现象**：加载界面双窗口（早期 GL 直绘 / 主窗口像素字）共用 `ForgeStyleLayout`。给早期窗口镜像主窗口的绘制代码时，直接用了 `memoryTextY()` / `totalTextY()` / `stageSummaryY()`，结果整块文字与阶段摘要**比预期低约 8px**，摘要挤到步骤条第一行上。

**判断**：`ForgeStyleLayout` 里 `*Y()` 系列是**MC 字体锚点**（`TOP + MC_TEXT_OFFSET(8)`），因为 MC 字形几乎贴锚点；而早期窗口 `EarlyFont.drawText` 的 y 是 STB 布局的**行盒顶**，Monocraft 24px 墨迹从 `y+9` 才开始。两者恰好差 8，视觉上像"手滑写错一个数"，实际是两个坐标系。

**结论/边界**：
- 布局类里同时暴露 `X_TOP`（行盒顶/几何顶）与 `xY()`（MC 锚点）时，**按渲染器取对应的一套**，不要让早期窗口也用 `*Y()`。
- 需要"方块与文字对齐"时（步骤条状态块），早期窗口要自己补 `EARLY_INK_OFFSET = 9`，主窗口直接用锚点即可。
- 新增纵向常量时先算墨迹区间（行盒顶 +9..+26）再排下一块，别只看常量数字是否递增——本轮 `TOTAL_BAR_TOP=36` 就是"数字上在内存文字(28)之下、实际压在墨迹(37..54)里"。

### C49. `EarlyGl` 的颜色是 ABGR（`0xAABBGGRR`），非对称色照抄 ARGB 会变色而红/灰看不出来（2026-11-01）

**现象**：早期窗口"进行中"状态块写成 `0xFF000000 | (0xFF<<16) | (0xFF<<8) | 0x55`，本意黄色，实机/推演都是**青色**。

**判断**：`EarlyGl.vertex` 的打包约定与 Forge `ColourScheme#packedint` 一致，是 `0xAABBGGRR`（低字节是红）。同一份代码里红色 `0xFF3D32EF`、灰色 `0xFF555555` 都"看起来对"，是因为这两类颜色的 R/B 相等或对称——**只有非对称色（黄/青/紫）才会暴露打包顺序错误**。

**结论/边界**：早期窗口里凡是"只有一处特别鲜艳"的颜色，先按 ABGR 复核：黄 = `0xFF55FFFF`，青 = `0xFFFFFF55`。主窗口的 `pack(alpha, rgb)` 是 ARGB，两套打包**不可互相抄**。

### C50. 像素字高度是固定 GUI 像素、不随 `sy` 缩放 → 高 guiScale 下相邻设计行会垂直重叠（2026-11-01）

**现象**：回归脚本在 guiScale=2（GUI 427×240）下报"内存文字没居中"，量到的中心偏右 53px；进一步查是把右上角**版本号**的字形块算进了内存文字那一带。

**判断**：文字字号固定 10 GUI 像素（`GUI_TEXT_PX`，刻意不跟设计空间缩放），但坐标按 `sy = guiHeight/480` 缩放。guiScale=2 时 `sy=0.5`，设计空间相距 16px 的两行（版本 20 / 内存 36）只差 8px，而字形本身高 10px → **垂直方向实测重叠 2px**。写"取某一行文字"的断言时，用「整块落在带内」过滤必然串行。

**结论/边界**：
- 断言按**块中心**落带判定，而不是整块包含；
- 需要更严的区域（水平居中这类），再加一条**水平上限**把角落元素排除；
- 这是固定字号 + 缩放布局的固有现象，肉眼通常不可见（两元素水平相距很远），但**测量代码必须先承认它**，否则会得到一个稳定复现的假红。
- 另：`bandExtent()` 返回的是 `[minX, maxX]`，要"底边"必须另写 `bandBottom()`——本轮把 X 当 Y 用，S2 下拿到 195 去和 156 比，看起来像布局崩了。

### C51. STB 图集里没打包的字**不会报错，只按字宽留白**——中文 UI 必须显式给全集（2026-11-01）

**现象**：早期窗口日志面板标题写「日志（实时）」，实机前推演发现会显示成「日志（ ）」——`LOADING_CJK_SOURCE` 里有「日志」「（）」，但没有「实时」。

**判断**：`EarlyFont` 对图集里查不到的码位只做 `cursor += FONT_SIZE`，不绘制也不告警（这是对的，否则一个生僻字能把整行画崩）。但反过来说，**中文界面的字表必须显式覆盖**，靠"应该都有吧"必然漏。

**结论/边界**：
- UI 固定字串用 `LOADING_CJK_SOURCE`（小集合，两窗口预打包）；
- **日志面板**要显示任意日志，中文面广得多：早期窗口额外打包 `LOADING_CJK_LOG_SOURCE`（594 字，全仓库字符串字面量扫描所得），主窗口则由 `ensureRasterized` 按需光栅化，不需要大全集；
- 600 字规模的 STB 打包要**一次 `PackFontRanges` 传码位数组**，逐字调用会分配上千个 native 缓冲；打包后用空四边形判定缺字/图集溢出。

### C52. `stbtt_PackFontRanges` 第三参是 **font_index（TTC 内索引）**，不是字节偏移——传错直接原生崩溃，`catch` 兜不住（2026-11-01）

**现象**：加载界面改版后第一次实机启动，4.3 秒闪退，控制台最后一行是「早期窗口 OpenGL: 4.6.0 - Build 31.0.101.4146」。`hs_err_pid*.log` 显示 `EXCEPTION_ACCESS_VIOLATION` at `lwjgl_stb.dll+0x39015`，Java frames 唯一线索是 `EarlyFont.<init>` → `stbtt_PackFontRanges`。`latest.log` 里没有任何 WARN/异常，看起来"跟字体无关"。

**根因**：把 `offset = stbtt_GetFontOffsetForIndex(data, 0)`（msyh.ttc 上是 **32**）当第三参传给了 `stbtt_PackFontRanges`。但该参数是 **font_index（TTC 集合内索引）**，STB 内部会自己再调一次 `stbtt_GetFontOffsetForIndex(fontdata, 32)`：msyh.ttc 只有 2 个字体 → 返回 **-1** → `data-1` 去解析表头 → 越界读。`hs_err` 寄存器是铁证：`R13=RDX=RAX=0xFFFFFFFF`，故障读地址 = `RBX + 0x100000003`（即 `data + (-1) + 4`）。

**为什么第一次看着"没问题"**：`stbtt_InitFont` 的第三参**确实是**字节偏移，用它做前置校验会正常返回 `true`，于是"字体加载成功"的假象成立；ASCII 那条路径一直写字面量 `0`，永远碰不到这个坑。

**结论/边界**：
- `stbtt_InitFont(info, data, offset)` → **字节偏移**；
- `stbtt_PackFontRanges(pc, data, fontIndex, ranges)` → **TTC 内索引**（通常 0）；
- 两者语义不同，别共用一个变量"顺手传"。
- **这类崩溃 `catch (Throwable)` 兜不住**：`MirageEarlyWindow.initWindow` 的 try/catch 只对 Java 异常生效，原生段崩溃直接结束进程。所谓"早期窗口失败就降级回原版窗口"**不覆盖 STB 参数错误**——只能靠离线用例守。
- 同上：`stbtt_PackBegin` 返回 false 时不检查、继续 `PackFontRanges`，也会因 pack_info 为空而原生崩溃。两个 `PackBegin` 现在都检查返回值。
- 回归 `scripts/verify_earlyfont_stb.ps1`：静态从 `EarlyFont.java` 抽出 `PackFontRanges` 的**实际第三参**（要求名字含 `Index`、值为 0、不是 `offset`），再用仓库自带 lwjgl-stb **以该参数值真跑 594 字打包**（参数取自源码，不是测副本）。两种改坏方式（改成 `offset` / 值写成 32）均红。

**证据链（离线、不启游戏）**：直接用 lwjgl-stb 调同一套 API —— 传 `offset=32` 崩；传 `0` 得到 `init=true offset=32 fontIndex=0 total=594 nonEmpty=594 packOk=true`。1024×1024 图集装 594 个 24px 汉字绰绰有余。

### C53. 「进度条没参考价值」的根因是**分母是编的**，不是配色/尺寸；参考实现必须反汇编当前版本，别拿旧源码对照（2026-11-01）

**现象**：用户看完上一版加载界面（三层描边条 + S1–S7 步骤条 + 总进度百分比 + 16 行日志面板）说「我要进度条，不是单纯的色块……不是单纯的 S1 s7，这样没有参考价值」。

**判断**：
- 第一层误读是"嫌丑/嫌小"，去调颜色和宽度——那是没用的。
- 真因在数据：`MirageDebug.progress` 全是**手写常量**（3/8/14/22/32/42/72/85/92/95/100）。S4 的 `Bootstrap.bootStrap()` 实测 **6.8~40.2s**、S7（MC 建窗口 + 资源重载）**23.6~68.1s**，这两段里屏幕上的数字**一动不动**。一根只有固定阶梯、不随工作量变化的条，本质上就是装饰用的色块——用户说"没有参考价值"是准确的。
- 第二个真因：日志面板的准入是**前缀白名单**（`[Mirage/[LS/[Loader/[MidCache/[Mirage-Mixin`），mod 自己的日志与 MC 原版在 S4/S7 的行一条都进不来 → 长等待期间面板静止，屏幕"看起来卡死"。

**做法（参考 NeoForge 实际实现）**：不要凭印象，反汇编当前版本：
```bash
unzip -o .../fancymodloader/earlydisplay/11.0.16/earlydisplay-11.0.16.jar -d /tmp/edx
javap -p -c /tmp/edx/net/neoforged/fml/earlydisplay/render/elements/ProgressBarsElement.class
javap -p -c /tmp/fmlx/net/neoforged/fml/loading/progress/StartupNotificationManager.class
```
得到三条可直接借用的语义：
1. `ProgressMeter.steps == 0` ⇒ **不定进度（游标）**，`>0` ⇒ `current/steps` 比例条；渲染侧**最多只画 2 根**；
2. 主条（`DisplayWindow` 构造时 `addProgressBar("", 0)`）**恒为不定**，label 由 `updateProgress()` 换成「Loading bootstrap resources / Discovering mod files / Loading language providers / Loading mods」——**Neo 自己也不给主条百分比，因为它也不知道总步数**；
3. 事件流 `getMessages()` 只取**最新 2 条**、按 age 淡出，四类 `MessageType`(MC/ML/LOC/MOD) 各带颜色——是"刚刚发生了什么"，不是完整日志。

**不能照抄的两条**：① `addModMessage` 里 `CharMatcher.ascii().retainFrom(s)` 会把中文整条删空（我们日志几乎全中文，照抄等于面板全空）；② 只显示 2 条 —— 24px 中文字宽下一行才 29 个汉字，2 条看不出趋势。

**边界/坑**：
- 参考实现要**认准当前版本**：`refs/forge/fmlearlydisplay/` 是旧结构（`RenderElement`/`PerformanceInfo`/`ElementShader`），26.2 的 NeoForge 已换成 `theme/*.json` + `elements/*`。拿旧源码对照，会得出"Neo 只有两根硬编码条"这种错结论；`theme-default.json` 里才有真坐标（`progressBars left:220 top:250`、`labelGap:4 barGap:5`）。
- 反过来这也解释了我们几何为什么本来就对：`MEMORY_BAR_TOP=10`/`BAR_LABEL_TOP=250`/`BAR_HEIGHT=20` 就是从这套坐标来的——**问题从来不在几何，在数据**。
- 凡是"分母不可得"的阶段（MC 的 `Bootstrap.bootStrap()`、资源重载），**只能画不定条 + 秒表**；给个漂亮百分比就是自欺，而且会让用户以为卡住了。

### C54 · 「进度条没参考价值」要把阶段分成两档，只改一档等于没改（2026-11-07）

**现象 → 判断**：用户否决旧加载界面后，逐阶段过一遍「真实分母到底能不能拿到」，结果天然分成两档：① **分母可得但没接**——S1 候选 jar 数、S3 挂 jar / 收集 mixin config、S4 解冻注册表（先数一遍 `REGISTRY`）、S6 每 mod / flush / BlockState 集合；② **分母不可得**——MC 的 `Bootstrap.bootStrap()` 与首次资源重载，**恰恰是耗时最长的两段**（6.8~40.2s / 23.6~68.1s）。只把 ① 接成确定条，屏幕上最卡的两段仍是死数字。
**结论**：② 用不定条游标 + `elapsedMs` 实时秒表，且文案要每帧会变（本轮 `view()` 200ms 一采 + `elapsedMs` 现算）；① 才画 `current/steps`。秒表只回答「等了多久」，**不要把它换算成百分比**。
**边界**：长驻不定条必须有明确收尾点，本轮是 `TitleScreen.init` 织入的 `MirageDebug.onTitleScreenShown() → LoadProgress.finish()`；否则游戏都进主菜单了条还在走。

### C55 · 换 UI 形态时，把旧形态留成运行时开关，别把旧断言改绿（2026-11-07）

**现象**：既有 `verify_forgestyle_text.ps1` 的 45 条断言全部绑在「S1–S7 步骤条 + 日志面板」的坐标上；一旦换成仪表盘，断言会集体变红。最省事的写法是「把断言改成新布局」，但那等于把上一轮的回归覆盖抹掉，回滚也没参照。
**结论**：旧渲染留在 `OLD_STEPPER` 分支（`-Dmirage.ui.oldStepper=true`，两个窗口同开关），脚本用**同一份编译产物跑两个进程**：旧断言对旧进程、新断言对新进程。本轮 45 + 38 = **83/83**，同时白得一个回滚开关。
**边界**：开关必须是**运行时读系统属性**（`Boolean.getBoolean`），不能是编译期常量 `static final boolean = false`——后者 javac 会内联掉分支，一次编译跑不出两套形态。

### C56 · 早期窗口新增颜色用转换函数；STB 字表要测「实际打包的并集」（2026-11-07）

**坑 1（C49 的复发点）**：`EarlyGl.quad` 收 **ABGR**，主窗口 `pack()` 是 **ARGB**；红/灰因分量对称看不出错，黄/青一抄就反。本轮新加的一批状态色不再手写 `0xAABBGGRR`，一律 `abgr(0xRRGGBB)` 由位运算转换，两窗口共用 `ForgeStyleLayout.COLOUR_*`。
**坑 2（C51 的延伸）**：`MirageEarlyWindow` 传给 STB 的是 `LOADING_CJK_SOURCE + LOADING_CJK_LOG_SOURCE` 的**并集**，而 `verify_earlyfont_stb.ps1` 原先只抽 `LOG_SOURCE`（594 字）——给 UI 加新词时，脚本照样全绿，早期窗口却可能静默留白。改成从源码抽两个常量拼接、交给 harness 去重打包后实测 **598 字全部入图集**。
**结论**：native 侧「打包了什么」要以生产调用点的实参为准，不能只测看起来最大的那一份字表。

### C57 · 变异检验要挑「断言不跟随的量」（2026-11-07）

**现象**：新像素断言大量直接读 `ForgeStyleLayout` 的坐标常量算文字带。若拿某个 Y 常量做变异（例如把 `EVENT_LINE_TOP` 抬 24），断言会跟着一起移动 → **改坏了仍然全绿**，变异检验成了假阴性。
**结论**：挑画布边界 / 容量 / 条数这类断言不跟随的量。本轮把 `EVENT_VISIBLE_LINES 4→5`，第 5 行墨迹顶到 496 > 480，两个 guiScale 场景各红 **136 / 142 个越界块**；恢复后 83/83。配套：`verify_loadprogress.ps1` 把 4 个变异点做成脚本内自动跑（每次复制源码到临时目录改一处再编译），原版全绿 + 4 红才算过。

### C58 · 「相对启动时间」必须只有一个零点，且要传值而不是各取一次（2026-11-07）

**现象**：`LoadProgress` 的 `totalElapsedMs()` 用 `START_NANOS`（**类初始化时刻**），`MiragePerf.elapsedMillis()` 用 `baselineNanos`（`Launcher.main` 第一行 `resetBaseline()` 时刻）。两处都由 `System.nanoTime()` 取，看起来都是「相对启动」，UI 的 `t` 与日志 `[LS] perf t=` 却可能对不上，差值取决于 `LoadProgress` 何时被首次触碰（`MirageDebug` 静态引用了它的 `STAGE_COUNT` / `PHASE_NAMES`，类加载时机不可控）。验收 D3「UI 耗时与日志可对账」因此不成立，而且这类偏差**不会报错、不会崩溃**，只能靠人工对照两串数字发现。
**判断**：追「谁定义了零点」而不是「谁取了 nanoTime」。全仓 grep `resetBaseline|elapsedMillis|totalElapsedMs` 后只有 `Launcher.main` 一处真正代表进程起点，其余都是消费者。
**结论**：`MiragePerf.resetBaseline()` 里**只取一次** `long now = System.nanoTime()`，既写自己的字段，也把同一个 `now` 传给 `LoadProgress.resetBaseline(now)`；后者同时把 `stageStartNanos` 挪到 `now`（否则首个 `view()` 会把「类加载到 Launcher 入口」算进 S1 秒表）。传参而不是在被调方再取一次，是为了把「同一把尺子」写成类型签名里的硬约束，而不是靠调用顺序维持的隐式约定。
**边界**：这只统一了**时间零点**，不统一「阶段起止的定义」——`stageElapsedMs()` 仍由 `stage()` 重置。新增任何计时基准都从 `MiragePerf` 取值，别再起一次 `nanoTime()`。验证方式：`javap -c` 看 `resetBaseline` 字节码必须只有一条 `invokestatic nanoTime` 且 `lload_0` 被两处复用。

### C59 · 源码守卫的正则要行首锚定，否则「注释掉的代码」算接线还在（2026-11-07）

**现象**：给 D3 加源码守卫 `$perf -match "LoadProgress\.resetBaseline\(now\);"`，然后做变异检验把那行改成 `// LoadProgress.resetBaseline(now);`。预期变红，**实际全绿**——正则照样在注释里匹配到了这串文本。守卫本身是空转的，若不是顺手对守卫也做了变异，这个洞不会暴露。
**结论**：断言「某行代码存在」一律用 `(?m)^\s*<调用>;` 行首锚定；注释行以 `//` 开头就不会命中。更一般地：**守卫也要被变异检验覆盖**（本轮 G1 删调用 / G2 改成另取一次 `nanoTime`，两者都必须至少红 1 条），只验行为断言、不验守卫，等于信任了一组没人验证过的正则。
**边界**：行首锚定只排除「整行注释」；`/* ... */` 块注释或字符串字面量里出现同名文本仍会误命中，涉及这类场景要改用词法级检查而不是正则。

### C60 · 「不要像素风格文字」不等于「换回字体 API」：只能在 fill 通道里换光栅化（2026-11-07）

**现象**：用户实机截图反馈主加载界面是点阵字，要求「不用使用像素风格文字」。截图里的硬边点阵来自 `MirageDebug.rasterizePixelText`：`VALUE_TEXT_ANTIALIAS_OFF` + `alpha>=80` 二值阈值，把 AWT 字拆成一堆 1px 实心矩形；主窗口又用 Consolas 等宽小字号，笔画在小尺寸下进一步粘连。
**判断**：最直觉的「换成正常字体」= 改回 `gge.text(Minecraft.font, ...)`，但这是本仓已钉死的禁区（C19 / 已知限制 #30）：LoadingOverlay 显示期正是首次资源重载进行中，`text()` 只入 `GuiTextRenderState` 队列，字形图集未装载 → **一条字都不画且日志无异常**；第二直觉「渲染线程用 Java2D 现画」则会占住 GLFW 消息泵 → 窗口「未响应」（C19 二次修复）。所以可用的只有 `fill` 矩形通道，问题变成「怎么让一堆矩形看起来不是点阵」。
**结论**：`rasterizeSmoothText` 开抗锯齿 + `VALUE_RENDER_QUALITY`，逐像素 alpha 量化到 1..4 档（`<16` 的噪声丢弃），同档水平相邻像素合 run、上下同 x/宽/档再合竖块，字块变成 `(x,y,w,h,coverage)` 5 元组；`drawText` 按档把前景**预混进所在背景的 RGB** 再 fill。**关键取舍：不用半透明 alpha 表达字形灰度**——MC 渲染状态是否走 blend 是未知量，把灰度烘进 RGB 就不依赖它，而界面淡入淡出的整体 alpha 仍由 `pack(alpha, rgb)` 承担。量化成 4 档正是为了把 fill 次数压在与二值方案同一量级（实测每帧小矩形 3.3k~5.0k，未回到「未响应」）。字体顺带从等宽换系统 UI 无衬线，逐字步进改用单字符 `stringWidth` 的真实 advance（比例字体才不会错位）。
**边界**：只改主窗口（原生 MC `LoadingOverlay` 期间那一屏）。HUD 的 `pixelText` 仍用旧二值方法、早期窗口 `EarlyFont`（STB 图集）一行未动；三条铁律不变——禁用 `gge.text()`、渲染线程零 AWT、字符级预渲染只在 `prewarm()`。`gge.text()` 在 TitleScreen 之后是可用的，别把这条禁区外推到整个 GUI 生命周期。

### C61 · 字形盒高 1~2px 的差要按画布裁剪，不要改布局常量；守卫假绿换了个马甲又来（2026-11-07）

**现象**：C60 换抗锯齿后 `verify_forgestyle_text.ps1` 在 guiScale=2 场景红了 8 个越界块，坐标全是 `y=240..241`（画布高 240）——抗锯齿字形盒比二值点阵高 1~2px，事件流末行顶出底边。另一处：内置变异 M1（把 `VALUE_TEXT_ANTIALIAS_ON` 改回 `OFF`）行为断言正确变红，但「对应源码守卫应同时失效」那条**仍绿**——Javadoc 注释里写了 `{@code VALUE_TEXT_ANTIALIAS_ON}`，简单 `-match` 又把它算成「接线还在」（C59 的第二次复现，这次是块注释/文档注释而不是整行 `//`）。
**判断**：越界块是「渲染越界」不是「布局算错」，改 `EVENT_LINE_TOP` / 行距会让所有文字带断言跟着常量一起移动 → C57 那种假绿；守卫假绿同理，正则必须只认真实代码行。
**结论**：① `draw()` 每帧写 `canvasW/canvasH`，`drawText` 把画布外的矩形裁掉（不是丢弃整块，是 clamp 边界），布局常量一个没动；② 守卫统一改成 `(?m)^\s*<真实代码行>`，例如 `(?m)^\s*java\.awt\.RenderingHints\.VALUE_TEXT_ANTIALIAS_ON\);` —— 注释行以 ` * ` / `//` 开头就不命中。③ 变异检验补一类**纯守卫变异**（M4：往 `drawText` 插一行 `java.awt.Graphics2D dummy = null;`，行为完全不变），专门验证「渲染线程零 AWT」守卫不是空转。
**边界**：画布裁剪是渲染兜底，不解决 C50 那条「字形固定 10 GUI px 不随 sy 缩放导致高 guiScale 下行距挤/分隔线压字」的观感问题；截图里那类重叠需要单独改文字锚点或布局节奏，本轮按需求边界未动。预混色判据 `isKnownColour()` 要跟着新增的纯色常量更新，否则新颜色会被误判成渐变色、断言假绿。

### C62 · GitHub 安全开关不能凭端点名猜 HTTP 方法，写完必须独立复核（2026-11-07）

**现象**：本轮按直觉用 `PATCH /repos/{owner}/{repo}/private-vulnerability-reporting` 加 `-F enabled=true` 去启用私有漏洞报告，返回 404；同一轮 `PUT .../vulnerability-alerts` 与 `PUT .../automated-security-fixes` 都是 204 成功。
**判断**：404 不是权限问题（同一 token 有 admin 权限，其它端点都成功），而是方法不存在。查 REST 文档后确认：私有漏洞报告是 **PUT 且请求体为空**；`GET` 返回 `{"enabled": false}` 很容易让人以为要 `PATCH` 同名 body。三个「启用」端点散落在文档不同小节，方法并不统一。
**结论**：改服务端开关前先查该端点的 method + body；启用后用**独立 GET / HEAD 复核**，不要只看写请求返回码（204 只说明请求被接受）。本轮复核：`vulnerability-alerts` 204、`automated-security-fixes` 200、`private-vulnerability-reporting.enabled=true`、`security_and_analysis.dependabot_security_updates=enabled`。
**边界**：`automated-security-fixes` 曾一度返回 502（GitHub 临时故障），此时以 `GET /repos/{owner}/{repo}` 的 `security_and_analysis` 字段为准，别把 502 误判成「没开」而重复提交。

### C63 · README 写了许可证 ≠ 仓库有授权文件；shade 产物会静默丢掉依赖 LICENSE（2026-11-07）

**现象**：`README.md` 写「MIT 开源」，但 `GET /repos/...` 返回 `license: null`，仓库内无任何 LICENSE / NOTICE / THIRD_PARTY 文件。同时 `fatJar` 把 `runtimeClasspath` 与 `mirage-deps` 里的 ASM / Mixin / Gson / Guava / Log4j 全打进单个约 2.9MB jar。
**判断**：public 仓库没有 LICENSE 文件 = 法律上「保留所有权利」，README 的自述不构成授权。更隐蔽的是 `fatJar` 里 `exclude("META-INF/maven/**")` 配合 `duplicatesStrategy = EXCLUDE`，会让各依赖自带的 LICENSE / NOTICE 在打包时被静默丢弃，构建不报错、产物里也看不出来。
**结论**：补 `LICENSE`（只把 README 既有声明落成文件，**不擅自改变授权选择**）+ `THIRD_PARTY_NOTICES.md`（集中列组件 / 版本 / 许可证 / 是否入产物），并写明「正式发行前须逐项核对产物内许可证原文」。涉及 LGPL 2.1 的兼容层，clean-room 边界一并写清，最终授权口径留给用户拍板。
**边界**：本轮不改任何 `.java` / 构建脚本，不动 `fatJar` 的排除规则，因此产物里 LICENSE 原文缺失的问题**仍在**，靠声明文件兜住而不是根治；若将来兼容层真的引入 LGPL 源码，整体授权需要重新评估，不是加个声明文件能解决的。

### C64 · 「脚本生成的报告」与「只标不删的台账」是两种文件，`-OutFile` 会把后者抹掉（2026-11-07）

**现象**：`docs/perf-baseline.md` 头部写着「本文件的唯一数据源是 `scripts/measure_startup.ps1`」，但正文里同时有 §1 测量口径、§5 Q9 结论与建议、§7「更正记录（只标不删）」、§8 变更记录——这些是人工写的、脚本根本不产出。按派单执行 `measure_startup.ps1 -OutFile <该文件>` 后，`WriteAllText` 整体覆盖，人工段落**全部消失**，且不会报错、退出码 0、报告内容看着完全正常。
**判断**：这类「自动生成 + 人工附录」的混合文档，冲突点不在解析逻辑，而在**写盘的语义是覆盖还是合并**。项目规则 9 的「只标不删」管的是台账内容，不会自动约束脚本的 `WriteAllText`。所以「确认无缺锚点后写盘」这一步必须先问：目标文件里有没有不可再生的历史内容？本轮答案是「有」，于是写盘前先从 `git show HEAD:docs/perf-baseline.md` 取回旧版全文，写盘后作为「附录：原文保留 · 只标不删」追加回去，并加一节人工核对说明。
**结论**：① 对混合文档跑 `-OutFile` 前，先判目标文件有没有人工段落；有就必须**先备份再覆盖再追加**，并在追加节里写明「下次再 `-OutFile` 会再次抹掉这两节」；② 报告里的「本次测不了的维度」是**全量模式对所有历史会话的聚合**，埋点部署前的旧会话必然缺锚点，把它读成「本次实机缺锚点」是误判——看单次干净视图用 `-LastSession`；③ 「到 TitleScreen」取 `Get-AnchorMap` 的**首次** `titlescreen`（同帧第二行只作旁证）；④ 体积行读的是**运行时磁盘上那一份 jar**，与产生该会话数据的 jar 可能不是同一份构建产物，别当成该会话实测体积。
**边界**：本轮纯观测，不改脚本、不改 `.java`。因此 `-OutFile` 会抹掉人工附录这个**根因仍在**——根治要么把历史段落拆到独立 `.md`，要么给脚本加「追加模式/保护区块」，两者都要改代码，留给用户裁决。另外堆峰值 488 MB 是 JMX 堆池峰值之和（近似值），**不等于**进程 `PeakWorkingSet64`，后者仍需 `-PeakMemoryPid` 采样。

### C65 · 「加载器契约」类缺口：目录必须**先于** mod 构造存在，且失败不能升级成 FATAL（2026-11-07）

**现象**：四次实机启动都复现 `java.io.FileNotFoundException: config\expore-common.toml (系统找不到指定的路径)`，栈顶是 `ExpOreConfig.saveConfig` ← `ExpOre.<init>`（mod 构造函数里直接 `new FileWriter("config/expore-common.toml")`）。mod 没崩，退化为默认配置继续跑，所以这条 bug 在"能启动"的假象下挂了 7 天。
**判断**：这不是 mod 的 bug，是**加载器语义契约**没兑现——NeoForge 保证 `<gameDir>/config` 在 mod 构造之前就存在，Mirage 的 S6 直接开始 new mod 实例。它属于"行为缺口"档而不是链接期炸，因此极简 mod 冒烟永远验不出，只有真实 mod 在构造里写配置才暴露；同时它也不会自己"好起来"——每次启动的堆栈一模一样。
**结论**：① 纯路径逻辑抽成 `io.mirage.loader.GameDirs`（纯 JDK），`ModInitStage` 在 mod 循环**之前**调 `ensureConfigDir(ctx)`；抽类的理由是 `ModInitStage` 引了整条游戏依赖链、纯 JVM 加载不了，抽出来才能对着生产代码跑离线断言（与 C41 同一条方法论）。② 必须用 `Files.createDirectories` 而不是 `createDirectory`：`--gameDir` 指向的目录本身也可能还不存在。③ **失败只 WARN 不 ERROR**：修复前的现实是"目录缺失 ⇒ mod 退化继续跑"，若把建目录失败（只读盘 / config 被同名文件占用）交给 `StageSupport.guard`，就变成整个启动 FATAL——为了修一个低危降级把可用性搞没，是本末倒置。守卫断言因此要同时钉住"必须 warn"和"不得 error"。④ `ParseStage` 的 `setConfigDirectory` 与本处共用 `GameDirs.CONFIG_DIR_NAME`，并加守卫禁止字面量 `resolve("config")` 复活——否则将来改目录名只改一处，两处悄悄分叉。
**边界**：日志里是**相对**路径，这次能被救是因为启动 bat 里 `cd /D <gameDir>`、进程 CWD 正好等于 gameDir。若更换启动器导致 CWD 与 gameDir 不一致，建 `gameDir/config` 救不了相对路径写盘，得另外把 CWD 固定住（本轮未做）。

### C66 · 变异检验脚本自己也会骗人：无 BOM 的 `.ps1` 里中文比对静默失效（2026-11-07）

**现象**：自动变异 harness 对 5 个变异逐个跑回归并统计"预期断言是否命中"，输出 `M1: hit 0/1`、`M3: hit 0/1`、`M5: hit 0/2`，看着像三个变异"逃逸"了。但同一份报告里 FAIL 行明明就在：`[FAIL] 守卫6 建目录发生在 mod 构造循环之前`。
**判断**：harness 是用编辑器直接写的、**没有 BOM**；Windows PowerShell 5.1 解析无 BOM 的 UTF-8 脚本时按 ANSI（GBK）读 ⇒ 脚本里的中文字面量 `"守卫6"` 变成乱码 ⇒ `$fails.Contains("守卫6")` 永不命中。变异本身是红的（exit=1、FAIL 行齐全），坏的是**判定用的那根尺子**。这是 C8（`.ps1` 要 BOM）在"工具脚本"上的复现，而工具脚本最容易被当成一次性的随手写。
**结论**：① 变异检验脚本要么带 BOM，要么**只用 ASCII 锚点**做匹配（本轮 `A10` / `守卫9` 是 ASCII 反而命中了，正好对照）；② 判断"红没红"先看退出码和 FAIL 行数，再看自制的命中计数；③ 机器判定与打印输出**都要看**——只看 verdict 列会把工具故障误判成"断言没覆盖"，然后白改一轮断言。
**边界**：本轮靠人眼看 FAIL 行发现；M4 的补丁更是因为搜索串含中文而"没打上"（同样是无 BOM 造成），补做时改用 ASCII 锚点 `private static void ensureConfigDir` + `MIRAGE.warn(` 定位才成功。所有变异做完都从备份整文件还原并用 `grep` 逐条核对，不能只信脚本说的"restored"。

### C67 · 同一个值有两种合法形态时，硬比字面量只会在一条路径上失效（2026-11-07）

**现象**：已知 bug #3 挂了 7 天，6 次实机全部复现 `AssertionError: Missing intrusive holder for ResourceKey[minecraft:creative_mode_tab / expore:expore]`，栈顶在 `MappedRegistry.register`。台账里的"根因"写着"清理逻辑没覆盖 item/block 之外的注册表"，看着很合理，于是没人再往下查。
**判断**：**报错位置不等于出错位置**。`DeferredRegister.registryPath()` 有两种合法取值——① NeoForge 兼容层显式带入的注册表 key 路径，是蛇形 `creative_mode_tab`；② 拿不到时退化为 `type.getSimpleName().toLowerCase()`，是无下划线的 `creativemodetab`。而创建 intrusive holder 的分支写的是 `'creativemodetab'.equals(path)`，只认第 ②种 ⇒ 恒 false。最强证据不是日志里有什么，而是**日志里缺了什么**：如果 `createIntrusive` 抛过异常，catch 会打 `createIntrusive 失败` 的 WARN，六次启动一条都没有 ⇒ 代码根本没进分支。这类"应有告警缺失"比"出现异常"更能定位到"没执行"。
**结论**：① 一个参数有多种合法形态时，别在调用点逐个写 `equals`，先归一（`RegistryPaths.normalize`：去下划线 + 逐字符 `Character.toLowerCase`，不用 `String.toLowerCase` 以免 locale 参与）；② 归一目标写成常量，并配源码守卫**禁止字面量比较回归**（守卫2/4 钉的就是 `"creativemodetab".equals(...)` 与 `"item".equals(...)`）；③ 行为断言必须同时覆盖两种形态，否则只修好一半——「简单名形态」那条路径仍会静默跳过；④ 改动 MC 内部行为前先 `javap -c` 把语义钉死（这次确认 `register` 是 `unregisteredIntrusiveHolders.remove(value)`、取不到即断言失败），否则很容易把"先塞 holder 再注册"的正确路径当成 bug 改掉。
**边界**：`docs/已知bug.md` 里 #3 原来的"根因"一栏是**错误假设**，按「只标不删」保留原文并在状态栏标注更正——别为了好看删掉错的那段，它正好记录了 7 天没人查下去的原因。另：`DeferredRegister.registryPath()` 的退化分支用的是无 locale 的 `toLowerCase()`，土耳其语环境下 `Item` 会变成 `ıtem`；目前只影响"没有显式路径"的注册表查找，已记入待核对清单，未修。

### C68 · 双窗口同源字形要靠共享常量在编译期钉死；GLFW 窗口交接期必须持续泵消息（2026-11-07）

**现象**：用户实机两张启动截图，配色/进度条/布局完全一致，唯一差异是文字字形——早期窗口（第一张）是 Monocraft 细等宽，主窗口（第二张）是 Segoe UI/微软雅黑圆润无衬线，观感跳跃；同时窗口交接瞬间 Windows 判定「未响应」。

**判断**：
- 同源本来靠 `ForgeStyleLayout` 注释「唯一基准是早期窗口」做约定，但约定管不住代码——主窗口此前已被换成系统 UI 字体。`ForgeStyleLayout` 只约束红底/布局，约束不到字体源。把"同源"从文档约定升级成**编译期约束**：抽 `LoadingFonts` 共享常量类（`ASCII_RESOURCE="/Monocraft.ttf"` + `findCjkFont()` 候选表），两个窗口都引用同一常量，回归脚本再断言两边读的是同一个资源字符串，才算真同源。这是 C44（模块搬迁引用不自动搬家）的延伸——`findCjkFont` 候选表从 `MirageEarlyWindow` 搬进 `LoadingFonts` 后，STB 回归仍抽旧文件才会红，所以脚本额外断言"早期窗口委托还在"。
- 交接未响应根因：`handoff()` 依次 `tryAcquire(3s)` + `awaitTermination(2s)` 合计最多 5 秒；`handedOff=true` 后渲染线程不再 `glfwPollEvents`，而交接线程在两次阻塞等待里也不抽窗口消息——正好踩中 Windows 判定"未响应"的阈值。把"等待期间持续泵消息"抽成可测签名：`HandoffPump.await(timeoutMs, ready, pump)`，每次先判条件、再 `pump.run()`、再 park 1ms；`pump=GLFW::glfwPollEvents`。上限从 3s/2s 降到 800ms/500ms，分片调用天然避阈值。

**结论**：① "X 必须以 Y 为准"这类约定，凡能在编译期用共享常量钉死的就别留作文档约束——文档约束会随后续改动静默失效，编译期约束让回归能断言；② GLFW 窗口在交接/等待期间只要句柄还存活就得持续 `glfwPollEvents`，否则任何超过数秒的阻塞都会触发 OS 级"未响应"（macOS 也有类似的 beachball 判定）；③ 把隐式时序约定抽成纯 JDK、可离线单测的等待器，比埋在 `handoff` 里的 `tryAcquire` 更好测——变异点能精确挑"删掉 `pump.run()`"这种断言会跟随的量。

**边界**：主窗口**不能**改成 STB 纹理通道——LoadingOverlay 期字形图集未就绪，`gge.text()` 静默无字（已知限制 #30 / C19），渲染线程碰 AWT 会占住 GLFW 消息泵（C60）。所以主窗口留在"AWT 预光栅化 + fill 矩形"通道，本轮只换字体源、不动渲染通道；CJK 同源也走到 `C:/Windows/Fonts/msyh.ttc` 同一文件（不是同家族不同文件）。

### C69 · 早期窗口交接「硬切」→「淡出溶解」靠渲染线程收尾，不在交接线程碰 GL（2026-11-07）

**现象**：用户录屏反馈「到主界面过渡动画衔接有问题」。逐帧取证（ffmpeg 抽帧 + 视觉读图）定位：交接瞬间 f776→f778（25.87s→25.93s）从满屏调试仪表盘直接跳到 Minecraft 居中 Mojang Logo，无渐变/黑闪/双窗口/尺寸跳变 = 硬切。窗口句柄是同一份（handoff 把早期窗口原样交还 MC），最后一帧是密集仪表盘，之后冻结到 MC 启动完成才被 Logo 覆盖，所以衔接生硬。

**结论**：① GL 上下文是线程绑定的隐式资源，跨线程 makeCurrent + 绘制是原生崩溃/"No context"的高危区；把"收尾渲染"放在已持有上下文的渲染线程里，比在交接线程新开一段 GL 安全得多。② "过渡生硬"常可归结为"前后两帧内容差太大"，在最后一程把前帧内容溶解到与后帧同色的背景，比硬做跨系统合成更稳。③ 又一次印证：把可测纯逻辑（状态机/颜色计算）从 GL 绘制里剥出来离线单测 + 变异检验，比把整段绘制搬进 headless GL 现实得多。

### C72 · 「过渡还是硬切」先分清是哪一段的硬切：同色背景前面各有一段，别把已修好的那段当成没修（2026-11-07）

**为什么不能在遮罩里修**：`LoadingOverlay` 自己是会淡出的（`fadeOutStart` 后 1s，再 1s 线性到 0，`javap -c` 确认过），我们的 `overlayAlpha` 也照着写了。但它靠**反射读 MC 私有字段**，跨 classloader `setAccessible` 失败会被 `catch` 静默回退成 255（不透明）——正是「读了但读不到，代码看起来完全正确」的典型。**收尾不能押在只能反射读的状态上**。

**守卫**：`lastDrawnAlpha >= 200` 才补溶解。MC 若某天真把遮罩正常淡出了（alpha 已接近 0），我们不补——否则会**反过来制造一次「Logo → 仪表盘」的跳变**。补硬切之前，先想清楚「修好了会不会造成新的跳变」。

**回归脚本**：新增 `scripts/verify_exit_dissolve.ps1`（31 断言 = 行为 15 + 守卫 10 + 变异 6，X1–X4 全红）。踩到两个小坑：① 跨 CRLF 文件的行尾 `$` 锚定在 .NET 正则里会失效，改跨行匹配并顺带断言填充色更严格；② `step("x", () -> f(...))` 外层多一层 `)`，正则漏写一个 `)` 就永远匹配不上——**守卫不匹配时先数括号，别怀疑中文编码**。

### C74 · PowerShell 两个会让工具脚本「看起来跑通、实际测错」的包装坑

**坑 1：`@(函数调用)` 会给返回数组再包一层**。函数 `return ,$arr` 本身是对的（防止管线摊平），但调用侧写成 `missing = @(Get-Missing ...)` 就变成「单元素数组，元素是那个数组」——后续 `@($r.missing).Count` 恒为 1、`foreach` 拿到的是整个数组。正确写法是**先赋值再使用**：`$m = Get-Missing ...; missing = $m`。识别特征：两个明显不同的缺失类被拼成一条字符串（PowerShell 字符串拼数组时用空格连接）。

**坑 2：`powershell -File script.ps1 -ModJars $array` 会把数组摊平成多个位置参数**。脚本只接到第一个路径，其余路径按位置绑到后面的参数上——本轮实测 `-Reference` 被绑成 cloth-config.jar、`-Baseline` 被绑成 ferrite jar，最后 `ConvertFrom-Json` 报 `Invalid JSON primitive: PK`。正确写法：在当前会话里 `& .\script.ps1 -ModJars $array`（同一进程、参数绑定保真），或直接传目录/单个字符串。**旁证**：扫描结果里"参考类总数 632"恰好等于某个 mod jar 的 class 数，就是绑错参数的典型信号。

**附带**：读基线前先判空/容错，`ConvertFrom-Json` 遇到二进制文件会抛异常；`-UpdateBaseline` 分支不应先读旧基线。

### C76 · PowerShell 的 `Get-Content -Raw` / `Set-Content` 往返会把 UTF-8 源码毁成 GBK 乱码——连换行都会被吃掉（2026-11-07）

**现象**：变异脚本改坏源码 → 还原后，文件里所有中文变成 `锛歩nterrupt 鎷﹀緱` 这类乱码；
更隐蔽的是**行数变少**（`SandboxRecorder.java` 损坏版 478 行，正确应为 524 行），
某些行的代码被挤到上一行注释后面，实际被 `//` 注释掉了。

UTF-8 字节被按 GBK 解码成一串 GBK 字符（非法字节落成 `?` 与 `U+E0xx`），
`Set-Content -Encoding UTF8` 再把这串字符编成 UTF-8 写回 ⇒ **往返不是恒等**。
GBK 解码器按两字节一组贪心配对，还会把 `\r` / `\n` 当成某个双字节序列的 trail 吃掉 ⇒ **换行消失**。

**为什么难发现**：
- 乱码只在中文注释里，**代码本身仍是合法 Java**，编译能过 ⇒ 看起来「没问题」；
- 还原校验若只比「编译通过」，会直接放过它；
- `Set-Content -Encoding UTF8` 还会加 BOM（PS 5.1），叠加成第二种损坏。

> 这是**第二次**踩同一个坑（第一次见 C75，另一会话踩的）。本轮三个文件同时中招
> （`NeoForgeModDetector` / `SandboxClassLoader` / `SandboxRecorder`）。

**正确做法**：
- 变异脚本**尽量不碰源码**：只改内存副本（`verify_msr_real_mods.ps1 -SelfTest` 就是这么做的）；
- 真要落盘，就走**字节级**：`[System.IO.File]::ReadAllBytes` 备份 / `WriteAllBytes` 还原；
  读文本用 `ReadAllText($p, [System.Text.Encoding]::UTF8)`，写回用 `UTF8Encoding($hasBom)` 保住原 BOM 状态；
- 还原后必须校验 **byte-identical**，不能只校验「编译通过」。

**顺带**：读源码做断言时同样要显式 UTF-8 —— `Get-Content -Raw` 走 ANSI 会让
**含中文的断言静默失效**（`Contains` 永远 false）。本轮已把 `verify_msr_real_mods.ps1` 的 7 处读取
全改成 `Read-Source`（`[System.IO.File]::ReadAllText(..., UTF8)`）。

### C79 · PowerShell 变量名大小写不敏感 + `[switch]` 是强类型变量 ⇒ 局部变量 `$full` 会撞上参数 `$Full`（2026-11-07）

运行时抛：

```
无法将值"System.String"转换为类型"System.Management.Automation.SwitchParameter"
类型：ArgumentTransformationMetadataException
位置：verify_msr_p3.ps1:279  $full = [System.IO.Path]::GetFullPath([string]$instDir)
```

   再改参数名（`$Full` → `$Zz`）—— 本轮就是改名的瞬间复现/不复现，直接锁定。

**约定**：
- 局部变量**不要**与任何 `param()` 名字同形（不区分大小写地比一遍）；
- `verify_msr_p3.ps1` 已加自检守卫：脚本内不得出现 `^\s*$Full\s*=` / `^\s*$Mutation\s*=`。
- 顺带记一个相邻坑：`Split-Path -LiteralPath X -Leaf` **参数集互斥**（`-Leaf` 只属 `Path` 集），
  会报「无法使用指定的命名参数解析参数集」。取文件名用 `[System.IO.Path]::GetFileName`。

### C81 · 写 26.2 探针 mod 必踩的三个 API 坑（2026-11-07）

**坑 1：注册方向写反，编译期不报错、运行期才炸**

```java
modBus.register(BLOCKS);   // ✗ 命中的是 IEventBus.register(Object)
BLOCKS.register(modBus);   // ✓
```

报错是 `IllegalArgumentException: class DeferredRegister has no @SubscribeEvent methods, but register was called anyway`。
`DeferredRegister.register(IEventBus)` 内部走 `bus.addListener(...)`（字节码里两次，对应两类注册事件），是安全路径。

**坑 2：26.2 的 `Block` / `Item` 的 `Properties` 必须带 id**

```java
BLOCKS.register("probe_block", id -> new Block(
        BlockBehaviour.Properties.of().setId(ResourceKey.create(Registries.BLOCK, id))));
```

漏了 `setId` 会在 `RegisterEvent` 阶段抛 `NullPointerException: Block id not set`（item 同理）。
用 `register(String, Function<Identifier, ? extends I>)` 重载拿 id 最省事。
另注意 26.2 里 `ResourceLocation` 已改名 **`Identifier`**（`Identifier.fromNamespaceAndPath`），
`ResourceKey` 只有 `identifier()` / `registry()`，**没有** `location()`。

**坑 3：game bus 事件不能和 mod bus 事件写在同一个类里**

`modBus.register(this)` 会把该类里**所有** `@SubscribeEvent` 方法都注册到 mod bus；
把 `LevelTickEvent.Post` 这种 game bus 事件也放进去 ⇒ 被拒（mod bus 只收 `IModBusEvent`）⇒ mod 加载失败。
所以 game bus 监听要拆到**独立类**，只注册到 `NeoForge.EVENT_BUS`。

> 这三个坑都不是加载器问题，是 26.2 真实 API 的要求。
> 探针 mod 源码在 `scripts/fixtures/msr-probe-mod/`，构建脚本 `scripts/build_msr_probe_mod.ps1`
> （classpath 走共享的 `scripts/common/NeoClasspath.ps1`，**必须**显式加
> `minecraft-client-patched` 与 `neoforge-universal` 两个 jar —— 它们不在版本 json 的 `libraries` 里，
> 运行时是 FML 靠 `-DlibraryDirectory` 自拼的）。

P3 每一轮录制（基线 + 录制）都要在屏幕上占一个客户端窗口好几分钟，而人不需要看画面。

- **别用 `grep` 直接在 `.jar` 上搜字符串**：条目是 deflate 压缩的，字符串在里面看不见，

### C83 · 单 mod 探针验不出「多 mod 撞同一事件」——P3 的订阅去重键必须带 owner（2026-11-08）

P3 在合成探针（`scripts/fixtures/msr-probe-mod`）上一直是「4 条 diff 全对」，于是记成「P3 已打通」。
一喂**真实 mod** 就露馅：6 个 26.2 mod 跑出来只有 32 条订阅，而 `javap -p -v` 列出 AppleSkin
一个 mod 就有 6 个 `@SubscribeEvent` 方法，diff 里只对上 2 个。

**根因不在插桩，在去重**：`RecorderAgent` 里 `SEEN_SUBSCRIPTIONS.add(eventType)` —— 只按**事件名**建键。
同一事件被多个 mod 订阅是生态常态（实测 `ClientTickEvent$Post` 三个 owner、
`RegisterPayloadHandlersEvent` 三个、`PlayerEvent$PlayerLoggedInEvent` 两个），
先注册的 mod 占位后，后注册的**整条被丢弃**；基线里原版/NeoForge 自己的订阅同样会占位。
单 mod 探针里每个事件只有一个订阅者，所以这条 bug 在探针上**永远不可能显形**。
改成 `owner + "|" + eventType` 后：32 → 51 条（appleskin 4→9、jade 17→20、jei 5→15、mezz 6→7）。

**顺带修掉的插桩盲区**：`EventBus.addListener` 有 8 个公有重载，其中 `addListener(Consumer<T>)`
**没有 Class 参数**，旧插桩器按「带 Class 的重载」筛就会直接跳过它（靠下游私有重载兜着才录到一部分）。
`javap` 看下来真正的汇聚点是私有
`EventBus.addToListeners(Object owner, Class eventType, EventListener, EventPriority)` ——
`addListener` 全部重载与 `@SubscribeEvent` 自动注册（`register` → `new SubscribeEventListener`
→ 构造里 `EventListenerFactory.create`）最终都汇到它，而且 **owner 直接是参数**
（不必靠栈回溯 —— 订阅点上栈里全是平台帧，回溯恒 `unknown`）。
插这一个点同时覆盖两条路，比旧的两个点更稳；旧点保留作跨版本兜底，重复上报由去重吸收。

**验收方式（可复用）**：
- **硬真值来自 `javap -p -v`**：把 `@SubscribeEvent` 方法连同其第一个参数类型全列出来。

  ② 无参注解 javap 打印成 `net.neoforged.bus.api.SubscribeEvent`（**没有 `(`**），
  按 `SubscribeEvent(` 匹配会恒 0 命中，误判成「这个 mod 不用注解」。
- **无幻觉对账**：diff 里每条 `(owner, event)` 都要能在**对应 mod jar 的常量池**里找到该事件类引用。
  jar-in-jar 的 mod（MezzConfig standalone）必须递归进 `META-INF/jarjar/*.jar`，否则「0 引用」是假结论。
- **断言要防「永远为真」**：守卫层用**纯内存变异**（把锚点换回 `add(eventType)` 再跑同一条正则）
  证明它真会判红，不必落盘重编译（C77 的分层）。
- **素材要锁版本 + sha512**：`scripts/fetch_msr_test_mods.ps1` 固定 6 个 jar 的 URL 与 sha512，
  幂等缓存到 `%TEMP%\msr-mods` —— 同 jar 才能复现同一份 diff，否则「昨天对今天不对」无从判定。

### C84 · 用 ASM 造 stub 时，JVM 校验器只认「自洽」不认「像」——P4 撞到的四个硬约束（2026-11-08）

P4 的任务是「给缺失的 NeoForge 类自动生成空壳」，听着像照形状源抄一遍签名就行。
实际是：**生成的 class 只要有一处不自洽，`defineClass` 立刻抛 `ClassFormatError`/`VerifyError`，
而且报错点常常在几百个类之后**，很容易被误读成「某个 mod 太刁」。四个坑全都跟「抄」有关：

1. **接口的字段只能是 `public static final`**。形状源里若写成 `ACC_PUBLIC|ACC_STATIC`（0x9），
   我们照抄就 `ClassFormatError: Illegal field modifiers in class X: 0x9` —— 合法值是 0x19。
   ⇒ 生成成员时按 **owner 是不是接口**（`ifaceLike`）走不同分支，别原样搬 `access`。
2. **判出「这是接口」还不够，必须把 `ACC_INTERFACE` 真写进 class 头**。第一版只把 `ifaceLike`
   用来决定「成员怎么生成」，class 头仍是 `ACC_PUBLIC|ACC_SUPER` ⇒ 生成了一个**同名的普通类**，
   于是别处 `implements 它` 时抛 `IncompatibleClassChangeError: X can not implement Y, because it is
   not an interface`。更麻烦的是**依赖顺序**：先生成成 class、后发现有接口在用它的场景，
   靠运行时 assert 提示是来不及的 ⇒ 生成前先**预扫一遍「谁被当接口用」**
   （形状源的 `interfaces` 数组 + 调用点的 `ownerItf` 标志），一次定盘。
3. **`<init>` 必须调「直接超类」的构造**。写死 `Object.<init>()V` 时，凡是超类不是 Object 的
   生成类（`ClientTooltipFlag extends Record`、`IConfigScreenFactory` 之类）全部
   `VerifyError: Bad <init> method call`。修法是把 `superName` 一路透传到生成构造的地方；
   **这是纯字符串参数的错，编译器一点忙都帮不上**，只能靠门禁把生成物真加载一遍。
4. **enum 不能照抄 `ACC_ABSTRACT`**。真实枚举常见「每个常量一个匿名子类 + 一个抽象方法」
   （NeoForge 的 `KeyConflictContext`、`KeyModifier`），形状源因此带 `ACC_ABSTRACT`；
   照抄后 `<clinit>` 里 `new` 自己 ⇒ `InstantiationError: X`。⇒ 生成前 `access &= ~ACC_ABSTRACT`。
   同源的还有 `ACC_RECORD`：不是 record 却带这个标志，JVM 会按 record 规则校验，一并清掉。

**这四条的共同点：形状源是「能用的类」，不是「能抄的模板」。** 抄之前先问「这几位标志在本 JVM 里
是强制的还是可选的」，强制的按规则重算，可选的才照搬。

**验收方式（P4 的判据，可复用）**：
- **真加载 + 真调用**，不能只看「字节码写出来了」。门禁夹具现造形状源 + 引用方 class，
  `defineClass` 之后还要 `getField` / `invoke` / `getMethod("values")`：接口要 `isInterface()==true`、
  枚举要 `isEnum()` 且 `values().length==2`、方法与构造要抛 **UOE**（抛 `NoSuchMethodError` 说明签名生成错了）。
- **失败分类计数**（`ClassFormatError` / `VerifyError` / `NoClassDefFoundError` / 其它）必须分开打印。
  混在一个「失败数」里，会让「我们生成错了」和「本来就缺 net.minecraft 类」纠缠不清 ——
  前者 0 才是合格，后者是预期。
- **`--verify` 重算缺口**：只打印「生成了 80 个类」毫无意义，必须用「参考 classpath + 刚生成的 pack」
  重新算一遍，要求 `net.neoforged.*` 缺口归零。这是唯一能证明「补的东西真的被用上了」的判据。
- **变异要挑「编译期看不出来」的点**：本轮 4 个变异（去 FINAL / 不清 ABSTRACT / 不写接口标志 /
  构造写死 Object）**全部能编译通过**，只有真加载才炸 —— 这正是它们值得做变异的价值。

**工具链两个老坑又各踩一次**：
- 本轮新建的 3 个 `.ps1` 都是先由编辑器写出、**没有 UTF-8 BOM**，一执行就在中文行上报
  「意外的标记 `}`」之类莫名字法错误（GBK 解码把中文吃成乱码，字符串引号配错）。
  落盘后必须核前三字节 `EF BB BF`（C8/C66 同源，第 N 次）。
- 在 Git-Bash 里拼 `-cp "a;b"` 会被 MSYS 路径转换当成盘符序列改写，表现为
  `NoClassDefFoundError: org/objectweb/asm/ClassVisitor`（类路径整段丢了，但错误信息完全不提）。
  ⇒ 要么 `export MSYS2_ARG_CONV_EXCL='*'`，要么全用反斜杠 Windows 路径。

**顺带修掉的变异脚本真 bug（当场被自己坑到）**：`verify_msr_mutation.ps1` 的两个缺陷叠在一起，
差点把「源码被留在变异态」当基线：
1. `Build-Core` 漏 `-p $repo`（C82 老坑），cwd 不在仓库根时 gradle 直接失败；
2. 变异体**没有 `try/finally`**，所以第 1 条一失败，脚本就带着**已落盘的变异**崩掉，
   源码在工作区里过夜（本轮实测留下 `String kind = "ctor_failed";` 与 `if (t != null) return …` 两处）。
   下一轮再跑时，`$backup` 读到的就是**变异态**，于是锚点全找不到 —— 若只看「`[SKIP]` 后仍 exit 1」
   很容易误判成「断言失效」而不是「基线脏了」。
⇒ 定两条规矩：**变异体一律 `try { … } finally { Restore-Bytes }`**；**动手前先预检全部锚点在不在**，
少一条就立刻报「工作区可能还留着上一次变异，先 `git checkout --`」，绝不带着脏基线往下跑。

### C85. 「按需生成」绝不能先裁窄 `missing`——`resolveSuper` 要靠完整缺口集合判定 mc 超类回落 `Object`（2026-11-11）

**现象**：P4b 把「全量生成」升级为「按需（白名单）生成」后，`-FromMid` 门禁第 (5) 步 `按需 pack 与全量 pack 对 M 中每个类逐字节相同` 报 FAIL。类集合一致（80=80）但 `ClientTooltipFlag` / `FluidTintSource` / `PartEntity` / `FluidSlotDisplay` / `FluidTagSlotDisplay` 共 5 个类字节不同。

**根因**：调用方在传 `FakeStubGenerator.generate` 之前先 `missing.retainAll(whitelist)`，把 `net.minecraft.*` 缺口从 `missing` 里剔掉 → `missingAll` 只剩 neo → `resolveSuper` 对「mc 超类」走到「返回真实 mc 名」分支（本应回落 `java/lang/Object`），于是生成物把不存在的 mc 超类写进 `superName`。链接期直接 `NoClassDefFoundError`；而 `--verify` 只查资源存在、不查 `defineClass`，门禁侥幸过关——**这是比「红」更危险的「假绿」**。

**结论/边界**：
- 把「裁窄生成集合」与「完整集合供解析」彻底分离：`generate` 拆出 `whitelist` 参，`missingAll` 永远保完整（neo+mc），`toGenerate` 才 `retainAll(whitelist)`。接口判定 / 超类递归 / mc 回落与全量模式**必须逐字节一致**，否则就是「另造了一套」埋雷。
- 验收「按需 == 全量」不能只看类集合相等，必须逐字节比对（`verify_msr_p4.ps1` 第 (5) 步就是这道关）。缺这一步，门禁会假装全绿、实际生成的类加载即崩。

### C86. PowerShell 变量名大小写不敏感：`$m` 会悄悄覆盖 `$M`（2026-11-11）

**现象**：`foreach ($m in $modJars) { ... }` 之后，脚本里原本存着 80 元素集合的大写 `$M` 被改成了循环变量 `$m` 的**最后一个元素**（一个字符串）。后续 step 6 取 `$M[0]` 拿到的是单字符 `'C'`（`[System.Char]`，于是报「`[System.Char]` 不包含名为 `Replace` 的方法」）。`$m` 与 `$M` 在 PowerShell 里是**同一个变量**。

**结论/边界**：
- 凡是在同一作用域里既用 `$M` 又要用临时循环变量，**循环变量换个不撞名的**（如 `$modJar` / `$ml`），绝不要靠大小写区分。
- 取集合元素做字符串处理时，先断言类型：`[string]$M[0]` 显式转型 + `.GetType().Name` 自检，能在开发期立刻暴露「这货怎么变成 Char 了」。

### C87. PowerShell `&` 调用运算符会把未加引号的 `-Dk=v` 当主类参数（2026-11-11）

**现象**：`& $javaExe -cp "$a;$b" -Dmirage.msr.fakepack.home=$dir probe.X` 报错「找不到或无法加载主类 .msr.fakepack.home=…」。`-D` 段被当成了主类位置参数传给 java，而不是 JVM 选项。

**结论/边界**：
- `&` 运算符会把裸的 `-Dkey=value` 当作「要执行的目标（主类）」解析。凡是 `-D` / `-X` / `-cp` 这类 JVM 选项，**整体加引号**：`"-Dmirage.msr.fakepack.home=$dir"`。路径含空格时更得加。
- 同类坑在 `Start-Process` / 直接 `java` 不带 `&` 时不会复现——只有 `&` 调用运算符有这个歧义，属「必经一处」才撞得到的坑。

### C88. `FakeProvider.findFakeBytes` 的契约是**点分全限定类名**，不是 slash（2026-11-11）

**现象**：探针 `p.findFakeBytes("net/neoforged/fml/event/lifecycle/FMLLoadCompleteEvent")` 返回 `null`，但目录里明明有这个 `.class`。`isAllowed` 用 `name.startsWith("net.neoforged.")` 判域，传 slash 形式直接失配。

**结论/边界**：
- 该方法的契约是 **点分**（`net.neoforged.fml...event...FMLLoadCompleteEvent`），内部自己 `replace('.', '/')` 再拼 `.class` 路径。`isAllowed` 也按点分前缀校验。探针侧一律传点分原样，别手滑传 slash。
- 凡写「内部会转格式」的 API，调用方要按「API 名义契约」传参，而不是按「它内部落盘用的格式」——这个鸿沟最容易在跨模块对接时踩。

### C89. Java 拼 boolean 是小写，PS `-match` 大小写不敏感但 `.Contains()` 敏感 —— 变异脚本会假报「断言无效」（2026-11-11）

**现象**：`verify_msr_p2_mutation.ps1` 首跑 5 个变异，其中 2 个明明已经让门禁变红（`exit=1, M4FAIL=2`），却被判成 `[RED-FAIL] 未按预期变红 —— 断言无效！`。输出里 `实际: M4CLASS missingFake=false ...` 明明白白。

**结论/边界**：
- harness 是 Java，`+ boolean` 拼出来是 **`false`/`true`（小写）**；PowerShell 的布尔文本是 `False`/`True`。
- p2 断言用 `-match`（**默认大小写不敏感**），写 `'missingFake=True'` 能匹配小写，全绿是合法的；但变异脚本里判定「坏值已观测」用的是 `String.Contains()`（**大小写敏感**），照抄 `ExpectBad='missingFake=False'` 必然失配。
- 修法：变异判据一律 `[regex]::IsMatch($out, [regex]::Escape($expect), RegexOptions.IgnoreCase)`，并把 `ExpectBad` 写成 Java 实际小写。**不要在断言文本和变异判据之间复制布尔字面量**。
- 更普遍：分层验证时，「断言侧」和「变异侧」用的匹配语义可能不同（`-match` 是正则+不敏感，`Contains` 是字面+敏感）。变异检验自身也要能被证伪——首跑这 2 个假红恰好证明了判定不是恒真。

### C90. 探针跑 fat jar（不是 `build/classes`）时，行为层变异别全量出包 —— 用 `javac` 单文件 + `jar uf` 覆盖副本 + 编译路径自检（2026-11-11）

**现象**：给 `verify_msr_p2.ps1` 补 M4 行为断言后要做变异检验。C77 要求「行为层必须落盘 + 重编译」，但 p2 的 harness 是 `-cp $Jar` 挂在 **fat jar** 上，改 `RecordingPolicy.java` 后 `compileJava` 只更新 `build/classes`，探针根本看不到变异。每个变异全量 `fatJar` 又慢、还会把部署产物反复覆盖。

**结论/边界**：
- 轻路径：改源码 → `javac -cp <fat.jar> -d <tmp/classes> <单个 .java>`（该类只依赖 jar 里已有的类）→ `Copy-Item fat.jar <副本>` → `jar uf <副本> -C <tmp/classes> .` 覆盖同名 class（本例产出 `RecordingPolicy.class` + `$Decision`/`$Reason` 两个内部类）→ `powershell -File verify_xxx.ps1 -Jar <副本>` 跑。原 fat jar 全程不动，源码 `try/finally` 字节级还原。
- **必须加「编译路径自检」**：未变异源码走同一套 javac + `jar uf` + 副本流程也必须全绿。否则「变异变红」有可能只是副本 jar 被这个流程弄坏了（假红），而不是变异真的生效。
- 双重确认缺一不可：① harness 真的吐出了预期的坏值（证明探针跑到了改坏的类）；② 至少一条目标断言变红（证明断言有效）。只看 `[FAIL]` 总数会被「进程崩了 / jar 坏了」骗过。
- **判绿前核包别只看 mtime**：本轮 fat jar mtime `16:04:32` 早于 M4 提交 `16:10:48`，但 `javap` 证实 jar 字节码里 `Reason` 含 `PREVIOUSLY_UNSUPPORTED`、`decide` 里有 `isUnsupportedByLoader`/`loaderCapabilityChanged` 调用 ⇒ 内容已是 M4 版（构建/提交时间差）。核包要核**内容**（`javap` / `unzip -l`），时间戳只能当线索。沿用「判修复无效前先核包」铁律。

### C91. 进程内单例的「首次预热」会让断言变脆弱 —— 连调三次取稳定态，只钉死最后一次（2026-11-11）

**现象**：M4 的 `RecordingPolicy.loaderCapabilityChanged()` 用 `AtomicReference LAST_STUB_FINGERPRINT` 做进程内单值，**首次调用必返回 true**（「首次认为变了，允许录一次」）。所以对同一个 `missing_fake` prev，第一次 `decide` 落 `ALREADY_RECORDED`，第二次才命中 `PREVIOUSLY_UNSUPPORTED`。若 harness 只调一次就断言 `d3=false:PREVIOUSLY_UNSUPPORTED`，必红；若换个测试顺序（别的用例先触发指纹），又会变成必绿——断言与全局状态耦合。

**结论/边界**：
- 有进程级缓存/单例的判据，断言要与**调用顺序解耦**：连调三次，前两轮用 `(ALREADY_RECORDED|PREVIOUSLY_UNSUPPORTED)` 放宽，只把「稳定态」那一次钉死成精确值。这样无论之前是否被预热都成立。
- 更一般：写断言前先问「被测逻辑有没有跨调用的状态」。有状态就要么显式 reset（本例指纹是 private 无 reset 接口），要么设计成收敛断言，别赌第一次调用的结果。
- 顺带记录一处**计划/实现偏差**（不擅自改判据）：M4 计划写「`ctor_failed` 可重录一次（mod 可能已修）」，但当前 `decide` 的 `prev != null` 一律 `return new Decision(false, Reason.ALREADY_RECORDED)`，没有这个分支。本轮按现状断言 `ctorPrev=false:ALREADY_RECORDED` 并在脚本注释写明；补分支属行为变更，需单独裁决并同步改这条断言。

### C92. 生成物的语义由「为谁生成」决定 —— 沙盒 fake pack 不能原样接进真启动（2026-11-13）

**现象**：评估「把 P4b 的 fake pack 接进真正游戏启动的 `MirageClassLoader`」时，直觉方案是
「在 `findClass` 找不到类时加一级 fallback，读 pack 字节码 `defineClass`」。看似只是把录制端
已有的 provider 链复用一遍，实际有两条硬冲突。取证（`unzip -Z1` + 读源码，纯离线）：

| | 沙盒 `SandboxClassLoader` | 真启动 `MirageClassLoader` |
|---|---|---|
| `net.minecraft.*` 来源 | `mirage/sandbox-fake/` 固定表面（21 类）+ compat stub | `26.2.jar` 里 **10372 个真类** |
| `net.neoforged.*` 来源 | compat stub + pack | fat jar 里 **141 个真 stub**（`net/minecraft` 根路径 0 个） |
| 委派 | fake 包**绝不**委托 parent | 三段前缀不委派，`synchronized(getClassLoadingLock)` 里 `findClass` |

**结论/边界**：
- **形状陷阱**：`FakeStubGenerator.resolveSuper` 对「`missingAll` 里的 mc 超类型」一律回落
  `java/lang/Object`（P4b 那 5 个字节不一致类正是这条）。`FakeGenCli --ref` 传的是
  `mirage-neoforge-compat/build/classes`，**不含 `26.2.jar`** ⇒ 分析器把 mc 类当缺失，
  生成的骨架是「沙盒形状」。真启动里这些 mc 超类真实存在 ⇒ 骨架继承关系与真实类层次不符，
  mod 做 cast / 覆写 / 按超类解析方法就是 CCE / `AbstractMethodError` / `VerifyError`。
  **产物只能在与生成时相同的 `--ref` 基准下使用**；换运行环境必须重算缺口（把真 MC jar 加进 ref）。
- **UOE 骨架 ≠ 实现**：pack 方法体一律抛 `UnsupportedOperationException`，沙盒里它是
  「让 fake pass 跑完、产出 `missing_fake`/`stub_incomplete` 清单」的**测量工具**。接进真启动
  = 把「启动期快速 CNFE」换成「运行期更晚、堆栈更脏的 UOE」＝ C84 明令禁止的**假覆盖**。
  「mod 加载过去了」从此不代表任何兼容性结论。
- **若真要接，三条边界**：① 插入点只能是 `findClass` 里 `readClassBytes(name) == null` 之后、
  `super.findClass` 之前（fallback 语义 ⇒ fat jar 的 compat stub 天然优先，**不会撞名/打瘸**）；
  ② 前缀闸**只认 `net.neoforged.`** —— `FakePackProvider.ALLOWED` 目前含 `net.minecraft.`，
  直接复用会允许遮蔽真 MC 类，必须在调用点收紧或另写窄 provider；③ 由 MCL **自己** `defineClass`，
  不委托 parent（C85/`CompatFakeProvider` 先例），否则与 `NeoCompatBootstrap` 确立的
  「neo 静态态只有 MCL 一份」冲突 ⇒ `LinkageError`。
- **更一般的判据**：接一个「诊断产物」进运行时前，先问三句 —— 它是在哪个 classpath 下造的？
  它的方法体是「干活」还是「抛异常/记账」？它会不会改变失败的**时机和可见性**？
  三句里有一句答不上来就别接，改成「让运行时把缺口说出来，产物回灌到构建期」。
- 落地方案见 `docs/plans/2026-11-13_MSR-FakePack接入真启动类加载器.md`（路线 A 缺口探针 /
  B 诊断 fallback 待裁决 / C 构建期固化）。
  **【已过时·2026-11-13】**「B 待裁决」的前提已随 C93 的规则修订消失：B 的代码实现 +
  headless 门禁可自行做，只有拉 GUI 的完整客户端实机对账仍需用户命令。原文保留备查。

### C93. 启动规则的判据是「是否拉起 GUI」，不是「是不是启动游戏」（2026-11-13，用户裁定）

- **现象**：旧表述「GUI 改动不自行启动游戏 / 任何启动游戏都要用户双击 bat」把
  **headless 纯 JVM 探针**和**完整 MC 客户端**一刀切，结果连离线门禁都被写进「需用户同意」
  的清单 —— W0 计划因此把路线 B 标成「需用户裁决」，其实它连窗口都不创建。
- **判断**：真正影响用户的是**窗口**（占桌面、抢输入焦点、在虚拟桌面留残影），不是
  「启动游戏」这个名词。另外内置工具拉起的 GUI 会落在 AI 宿主会话，窗口/焦点/注册表
  对不上 ⇒ 冒烟白跑 —— 这条旧理由仍成立，但**只适用于拉 GUI 那一支**。
- **结论**：根本判据 = 会不会拉 GUI。(A) 拉 GUI（完整客户端 / `MirageEarlyWindow` / GLFW）
  ⇒ **优先不启动、等用户命令**，写好 `.bat` 让用户双击；(B) 不拉 GUI（纯 JVM 探针、
  `verify_*.ps1` 门禁、gradle、`javap`、P3 沙盒录制已摘 `glfwShowWindow`）⇒ **可自行启动验证**。
- **边界**：判不准就按 (A) 处理；headless 产物只写 `%TEMP%`/仓库内，**不得写 `mc-shili/`**；
  「可自行启动 headless」≠「可自行部署 fat jar」；探针若意外弹窗立即停并报告。
  规则变更只改「谁能拉起进程」，**不改任何技术结论**（例如 C92「pack 不能原样接」照旧）。

### C94. `Out-String` 是 `\r\n`，正则用 `$` 收尾会让整批断言假红（2026-11-13）

- **现象**：W1 门禁首跑 90 条里 58 条 `[FAIL] 期望 KEY=xxx，实得 <MISSING>`，但 6 个 JVM
  全 `exit=0`、`FAKE MODE` 横幅也打出来了 ⇒ 不是生产代码问题，是输出解析。
- **判断**：`& java ... 2>&1 | Out-String` 产出 CRLF；.NET 多行模式的 `$` 落在 `\n` **之前**，
  而 `([^\r\n]*)$` 里的 `\r` 正好卡在中间 ⇒ 永远不匹配。改成
  `(?m)^\s*KEY=([^\r\n]*)`（去掉 `$`）立刻 90/90。诊断时把 `\r` 显示成 `<CR>` 看一眼最快。
- **结论**：从 `Out-String` 抓 `KEY=value`，**绝不要用 `$` 收尾**。附带：整数取值别裸
  `[int](...)`，缺失值会抛 `InvalidCastFromStringToInteger` 把脚本打断；写个 `TryParse`
  的 `Get-ProbeInt` 返回哨兵值，让断言正常变红而不是让脚本崩。

### C95. 守卫正则要钉「代码定义」，说明性注释也会让守卫误红（2026-11-13）

- **现象**：`GUARD B 没有复用含 net.minecraft. 的 ALLOWED` 一条红，但 `RuntimeFakePack.java`
  里根本没有那个数组 —— 命中了 Javadoc 里解释「为什么不复用 `ALLOWED`（它含
  `net.minecraft.`）」的那行。
- **判断**：C59 讲「注释掉的代码会骗过守卫造成假绿」，这里是**反面**：
  `(?m)^\s*.*ALLOWED.*net\.minecraft` 这种「关键词共现」正则对自然语言注释同样成立 ⇒ 假红。
- **结论**：负向守卫要钉**唯一的代码形态**（`private static final String\[\] ALLOWED`、
  `name.startsWith("net.minecraft.")`），别钉关键词。守卫层与行为层都要能被变异打红才可信。

### C96. headless 探针里 pack 目录绝不能挂进 MCL 的 URL（2026-11-13）

- **现象/判断**：W1 的 fallback 只在 `readClassBytes(name) == null` 分支触发。若把 pack 目录
  作为 MCL 的一个 `URL`，`getResource("net/neoforged/.../FakeOnly.class")` 会直接命中，

- **结论**：探针的 MCL URL **只挂 compat classes**，pack 只通过

  改坏的类」的前置条件。
- **附带两条环境观察**：① `MirageMixinBootstrap.transform` 在 Bootstrap 未初始化时会抛 NPE

### C97 · W2 真启动缺口重算：缺口集合与运行时不相关

- **结论**：用「真实启动 classpath」（compat + 真实 MC jar）重算的缺口 M_real，与 P3 沙盒 M_sandbox **逐字节一致**（sha256 相同），都是 80 个 `net.neoforged.*` 类。缺口集合只由 mod 字节码常量池决定，与「运行时有没有真实 mc 类」无关 ⇒ 现有 P4b 生成物对真实启动同样有效，**无需为真启动另造一套**。
- **取证**：真实游戏 jar（本环境 `mc-shili/versions/26.2-NeoForge_26.2.0.90/26.2-NeoForge_26.2.0.90.jar`）含 **10372 个 `net/minecraft/*` 类、0 个 `net/neoforged/*` 类** —— 本加载器里 neo 类只来自 `mirage-neoforge-compat`，真实游戏 jar 只带 mc 类，职责划分与真实运行一致。
- **为什么 pack 不变**：`FakeStubGenerator.resolveSuper` 对 mc 超类「存在则回真实名、缺失则回落 `Object`」。compat 没 stub 的 80 个 neo 类 `shapeOf` 返回 null → `superName` 默认 `Object`；真实 jar 含 0 个 neo 形状源、作 `--shape` 零贡献；作 `--ref` 只让 mc 从「缺失」变「齐全」（mc 本就进 `skipped` 不进 `toGenerate`）→ 仅改善 `--verify` 账目，不改变任何生成字节。这与「加真实 jar 应改变生成物」的直觉相反，别被直觉骗。

- **读真实 jar 只读、不写 `mc-shili/`**：真实 jar 复制一份到 `%TEMP%` 作门禁输入，绝不让生成器/门禁写回 `mc-shili/`；门禁 `-RealJar` 缺省指向 mc-shili 真实 jar，环境无该 jar 时 real-startup 段跳过并告警、sandbox 段照常跑。

### C99 · W3-C 门禁两连 PowerShell 正则坑 + `*.class` 被 gitignore 吞掉有意提交的 stub 资源

- **`Out-File -Encoding ascii` 写 `jar tf` 清单带 `\r\n` 行尾 ⇒ `\.class$` 匹配失败**：`$` 在 `(?m)` 下只匹配 `\n` 之前，行尾的 `\r` 仍留在文本里，`\.class$` 永远对不上。修法：`\.class\r?$`（或先把行尾 `\r` 去掉再匹配）。bash 里 `jar tf` 默认 `\n` 无此问题（`grep` 按行作用），唯独 PowerShell 管道 `Out-File` 才踩。
- **.NET 正则 `(?m)` 下字符类 `[^ ]` 会跨行匹配 ⇒ 类路径计数全废**：`(?m)mirage/fakepack/net/neoforged/[^ ]*\.class$` 的 `[^ ]*`（字符类，不是 `.`）可以吃掉整文件所有换行，greedy 一路吞到文件末再回溯，结果只命中最后一次 ⇒ 80 类的目录清单只数出 1。修法：用 `[^\r\n]*` 把匹配锁死在单行内。教训：在 PowerShell/.NET 里做「逐行数某前缀条目」时，**绝不用 `[^ <空格>]` 当「非分隔符」通配，必须显式排除 `\r\n`**。
- **`.gitignore` 的 `*.class` 全局规则会吞掉「有意提交到仓库的 stub 资源」**：W3-C 把 80 个 P4b 生成 stub 当 fat jar 内嵌资源（`modules/.../resources/mirage/fakepack/**/*.class`），`git check-ignore` 直接命中 `*.class`、状态全绿却一个都 `git add` 不进去——本地构建照常能 shade 进 jar（读工作树），但 clone/build 后 jar 里就没这 80 类，W3-C 特性在别处静默失效。修法：**加 scoped 否定例外** `!modules/mirage-neoforge-compat/src/main/resources/mirage/fakepack/**/*.class`，保留「仓库只放源码」的总策略不变，只对此目录开口；不要散弹 `git add -f`（会让例外规则不可见、后续维护者不知情）。

### C100 · real-shape 的「间接超类悬空」：`--verify` 只查资源存在，不等于能 `defineClass`

- **只换形状源＝退化，不是增强**：给 `FakeGenCli` 喂真实三 jar 作 `--shape`、白名单仍是 80 个 mod 缺口，生成 80 类 `verify` 全 OK，但**全量 `loadClass` 只有 38 OK / 42 `NoClassDefFoundError`**。原因：`FakeStubGenerator.resolveSuper` 里 `if (!missingAll.contains(dotted)) return internal` —— 间接真实超类（`ScreenEvent` / `BaseCapability` / `ParallelDispatchEvent` …）mod 没直接引用、不在 `missingAll`，被当成「确定存在」直接写进 `superName`，但它们既无 compat stub 也没被生成 ⇒ 悬空。**UOE 骨架时代没有形状源，`superName` 恒 `Object`，反而不会踩**。这正是 C92「把启动期 CNFE 换成运行期晚失败」的另一种形态。
- **`--verify` 不是链接期判据**：它只检查「白名单每个类能在 pack 里 `getResourceAsStream` 到」，不 `defineClass`、不解析超类。real-shape 后必须补**全量加载门禁**（逐个 `loadClass` 分类 OK / CNFE / NCDFE / OTHER），否则会拿一堆加载不了的类判绿。本轮加 `AllLoadProbe.java` fixture 锁死 114/114。
- **超类闭包要在数据层算、但不能只改数据**：`toGenerate = neoMissing ∩ whitelist`，间接超类不在 mod 缺口里 ⇒ 光把 34 个类加进 `--only-file` 仍 `generated=80` + 34 条 `verify MISS`。修法选**最小且只碰构建期 CLI**：按需模式在 `generate` 之前 `missing.add(w)`（白名单视为显式请求的缺口），让 `resolveSuper` 递归生成整条链；既有用法（白名单 ⊆ 缺口）逐字节不变。闭包用 `FakeStubGenerator.FileShapeSource` 对三个 jar 做 BFS（`superName` + `interfaces` 里的 `net/neoforged/*`），80→114。
- **间接 mc 超类是同一漏洞**：`DataComponentHolder` 等不在 `missingAll` 的 mc 接口被当成确定存在引用，headless classpath 无真实 MC jar ⇒ 5 个 NCDFE。修法：`dotted.startsWith("net.minecraft.")` 时**无条件**回落 `java/lang/Object`，与 W0「mc 只报告不生成、绝不引用」一致。真形状价值在 neo→neo 链，mc 侧回落 Object 才自洽。
- **形状源带来 protected 字段会炸 `ClassFormatError`**：`emitField` 的 `(access & ~(ACC_FINAL|ACC_PRIVATE)) | ACC_PUBLIC` 没清 `ACC_PROTECTED`，真实形状源的 protected 字段变成 `public|protected`(0x5) ⇒ 7 个类整类加载失败。mask 必须加 `ACC_PROTECTED`。**「形状源是能用的类，不是能抄的模板」**（C84）在 real-shape 下又应验一次：真实 access/成员照抄会带进 JVM 不允许的组合。

### C101 · 探针按字典序挑候选会撞上 compat 原生类 ⇒ DEFAULT 假绿 / B_HITS=0

- real-shape 闭包补进了 `bus.api.Event`、`IConfigSpec`、`IModBusEvent`、`IModFileInfo` 等 **compat 根路径已有**的类，字典序排在最前。`W3CBuiltinProbe` 原本「枚举候选、第一个 `OK` 就 break」，于是 DEFAULT 下也能由 compat 正常加载（`NEO_LOAD=OK:mcl` 而非 CNFE）、BUILTIN_ON 下根本没走 fallback（`B_HITS=0`、无 FAKE MODE 横幅）⇒ W3-C 门禁 6 条断言全红。
- **探针语义要问「我要验的到底是哪个能力」**：本探针验的是「只有内置 pack 能提供、必须走 fallback 的类」，就必须**跳过 compat 根路径已有的类**（从 fat jar 枚举 `net/neoforged/**` 根路径集合，`contains` 就 `continue`）。补一句 `COMPAT_ROOT_COUNT` 输出便于核对。别把这类失败误读成「默认零变化被破坏」——实际是目标选错。
- 同理，real-shape 门禁的 DEFAULT 断言不能写「全 CNFE」，因为 6 个 compat 原生类本就可加载；正确口径是 `B_ENABLED=false` / `B_HITS=0` / `LOAD_OK << 114` / 无横幅。

### C102 · 行为层变异必须让「真正被消费的那份 jar」也变异，否则假红

- `RuntimeFakePack.readFromBuiltin` 走的是 **`MirageClassLoader.class.getClassLoader()`（app loader，即 `-cp` 里的 fat jar）** 读 `mirage/fakepack/` 资源，不是探针参数传进去的那个 jar。删超类的行为变异若只改副本、探针参数指向副本，但 `-cp` 仍是原始 fat jar ⇒ 加载照常成功，只是**枚举列表少 1 个**（`LOAD_OK=113`、`NCDFE=0`），变异断言变红但原因是错的（假红/空转）。
- 修法：跑副本场景时把 `-cp` 里的 fat jar 路径**一并替换成副本**，让 MCL URL 与 app loader 同源。改对后删 `ScreenEvent.class` 精准产生 **29 个 NCDFE**、`LOAD_OK=84`。**做产物变异前先画一遍「探针从哪几处读同一份产物」**。
- Windows PowerShell 5.1 用 `[System.IO.Compression.ZipFile]` / `ZipArchiveMode` 删 jar entry，必须 `Add-Type` **两个**程序集：`System.IO.Compression`（含 `ZipArchiveMode`）与 `System.IO.Compression.FileSystem`（含 `ZipFile`）；只加载后者会 `找不到类型 [ZipArchiveMode]`。
- 另：`msr_p4_generate_fakes.ps1` 的参数 `[string]$Home` 与 PowerShell **只读自动变量** `$Home` 冲突，任何标准会话一进来就 `无法覆盖变量 Home`；本轮直接调底层 `FakeGenCli` 绕过包装器（未改脚本接口，避免影响既有调用方）。`java -cp` 里 ASM 给 `C:/...` Windows 风格路径，`/c/Users/...` 经 Bash 传给 Windows `java.exe` 会 `NoClassDefFoundError: org/objectweb/asm/ClassVisitor`。

### C103 · 「做 X」先量化 X：**输入清单的来源**比数量更决定可行性（2026-11-14）

- **现象**：用户选「推进 W3 完整路线 C 另一半」，W0 原文只有一句「产出的类逐个审成有实现的 stub 合入 compat 源码（N1 路径）」，看着像一个动作。先做差集量化才发现：pack 114 类 / **859 方法**，compat 已有 77 个 `.java`、交集仅 **6** ⇒ 真正待实现 **108 类**；重方法集中在 `ModConfigSpec$Builder`(81) / `IItemExtension`(47) / `FluidStack`(45)。照字面「逐个审」≈ 839 个方法的 clean-room 实现，是 W0 自己说的「N2/N3 规模，须单独立项」。
- **决定性证据不是数量，是清单来源**：W0 另有一句「**A 路线的清单就是 C 的输入**」，而当前 114 类来自 P3 沙盒录制 + 6 个测试 mod 常量池差集；W1 的 `MissingNeoTracker` 从未在真实客户端跑过（完整启动拉 GUI，按 C93 须用户命令）。拿沙盒清单去排实现优先级，可能实现一堆用不到的、却漏掉真客户端缺的。**先查输入从哪来，再估工作量**。
- **结论（规则 1 的补丁法）**：不照字面全量执行，改为「纯文档轮立项 + 三档分期」：A 34 类可做、B 25 类等真清单、**C 49 类明确列为永久缺口而不是待办**（需真实 MC 状态/渲染/流体子系统，半实现＝C84 假覆盖）。批量把 UOE 换成编造返回值会破坏路线 C 在 W0 取舍表里「无假覆盖风险」的唯一前提；N1 原则是未知方法一律 UOE 带类名+方法名。
- **口径坑**：W0 记「fat jar 141 个 neo stub」是 **class 数**，本轮数 `net/neoforged/**/*.java` 是 **77 个源文件**——一个 `.java` 可含多个嵌套类，两个数字都对，别拿差集当「少了 64 个实现」。与 C100 同源：计数口径不同会直接导出错误结论（`--verify` 查资源存在 ≠ `defineClass` 成功）。
- **边界**：本条只适用于「把一句设计描述展开成实现范围」；不推翻 W0 路线 C 的正解地位，也不改变 UOE / FAKE MODE / 默认关闭的假覆盖结论。
