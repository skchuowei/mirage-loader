## A · 协作与流程经验

### A1. 用户报的是现象，不是根因（2026-10-31）

用户原话"点退出游戏就崩"。字面像是关闭流程写错了，实际根因是**同一份 `glfw.dll` 被加载了两份实例**，MC 侧在自己的空链表上摘窗口节点。

**做法**：拿到报障先复现、先看最原始的现场（崩溃日志/堆栈/寄存器），再谈"是什么导致的"。把用户描述直接当诊断结论，会朝着错误的方向改一堆无关代码。

### A2. 没有 crash-report 的崩溃，先去翻 `hs_err_pid*.log`（2026-10-31）

MC 的 `crash-report` 只覆盖 Java 层未捕获异常。JVM **原生崩溃**（`EXCEPTION_ACCESS_VIOLATION`）不会生成 crash-report，只会写 `hs_err_pidXXXX.log`，而这份文件里的**已加载模块列表**和**寄存器状态**往往直接就是答案。

**判断特征**：用户说"没有崩溃报告，游戏直接没了" → 先找 `hs_err`，别在 `crash-reports/` 里空转。

### A3. 盘点项目现状必须以代码为准，文档声称的完成度不算数（2026-10-31）

本轮做 AG 总计划重梳理，按"以代码为准"的口径盘点，一次性发现：8 个 `Fabric*Mixin` 从未注册进 `mirage.mixins.json`（导致 Fabric 三层桥接运行时根本不可达）、IR 只解析不重放（全仓库无 `.ir.` 读取点）、更新日志声称"已登记两个 Mixin"但文件里没有。

**结论**：任何"重新规划/评估进度"的动作，先跑一次代码级盘点，并把**"文档有、代码无"**单列成表。否则后面所有计划都建在假地基上，而且这类缺失通常**不报错**（见 C1），不会自己浮出水面。

### A4. 目标互斥时，摆出冲突让用户裁决，不要自行降级（2026-10-31）

`<3MB` 体积目标（当前 2.68MB）与"原生承载 KubeJS 转译"在技术上互斥。这类冲突不能悄悄砍功能或悄悄放宽指标，要明确写成待裁决问题（本轮整理出 Q1/Q2/Q3/Q5/Q9）交给用户。

### A5. "跑通"必须先落成可验证判据（2026-10-31）

"把 X 跑通"是本项目最高频也最含糊的验收语。不先定 L1/L2/L3 之类的分层判据，每轮收尾都会在"这算不算完成"上扯皮，且容易把"能启动"当成"功能可用"。

### A6. 「完善 X」类需求：先量化现状 + 找真实痛点，再动手（2026-10-31）

**背景**：用户只说「完善日志输出（不仅限于LS）」，没说什么算"完善"。

**判断路径**：
1. **先量化**：`grep -c` 统计裸输出分布（238 处 / 12 个模块），确认改造面。
2. **再找证据**：翻真实 `latest.log` 里 Mirage 的行，找"这行信息不足"的实例。这一步是决定性的——它把"统一格式"这种自嗨目标，换成了"异常 cause 被吞掉"这个真问题（`事件处理错误: null`、`InvocationTargetException` 只有类名）。
3. **然后才定方案**：门面 + 分级是手段，**展开异常链**才是目的。改造后那三行原本无解的问题立刻给出了根因。

**结论**：用户给的是方向词（"完善""优化""整理"），不是验收标准。**先量化和取证，把方向词翻译成一个具体缺陷**，再动手。否则容易做成"改了一层皮，问题还在"。

**边界**：取证要用真实产物（日志、崩溃报告、复现），不能凭读代码想象痛点——本轮若只看代码，会误判成"格式不统一"这个次要问题。

### A7. 「测试全绿」不等于测试有效——用变异检验确认它有牙齿（2026-10-31）

**背景**：给日志门面补 `scripts/verify_logging.ps1`，首轮 41 项全绿。但一个新写的测试全绿，既可能是"代码没问题"，也可能是"断言根本没测到东西"。

**做法**：把被测实现**故意改坏一处**，确认对应断言会红。本轮把 `summary()` 里的 `unwrap(t)` 改成 `t`（正是改造前的原始形态），重新编译运行，输出立刻退化为

```
[Mirage] ERROR ERR-CHAIN 注册失败: java.lang.reflect.InvocationTargetException
[Mirage] ERROR ERR-INIT 类初始化失败: java.lang.ExceptionInInitializerError
```

——与改造前线上日志一字不差，3 条断言必然失败。测试有牙齿，才算补完。

**结论**：新增验证脚本后，**至少做一次变异（一条即可，挑最核心的那条断言）**，把改动成本压到 1 分钟。
反过来也说明一件事：断言要盯**改造前的病态输出**（类名裸露、`null`、无 message），而不是盯"有没有打印"。

**边界**：变异只需证明"断言能感知差异"，不必覆盖全部断言；也不需要把变异引入 CI（凭空多一份维护成本）。


### B1. 原生崩溃的定位链（2026-10-31，可复用）

1. `hs_err` 读三件事：**崩溃线程名**、**崩溃 PC 落在哪个模块+偏移**、**寄存器指向的内存是否全零**；
2. 解析该 dll 的 **PE 导出表**，把 PC 偏移落到具体导出函数（本例 `glfw.dll+0x77a0` → `glfwDestroyWindow`）；
3. 反汇编第一条访存指令，判断是空指针解引用还是野指针（`mov rax,[rcx]` + `rcx=0` = 空链表头）；
4. **对比 hs_err 的模块列表**——同一路径族里同名 dll 出现两份，是"双实例"的强信号；
5. 最后才回 Java 栈找调用方，确认是哪一条路径调的。

顺序很重要：先拿决定性证据，再看代码。

### B2. "大部分功能正常，只有某个操作崩" → 优先怀疑同一原生库被加载两份（2026-10-31）

双实例的典型特征：只碰**传入结构体指针**的 API（`glfwSetWindowTitle`/`PollEvents`/`SwapBuffers`）全部正常，因为两份同版本库内存布局一致；只有访问**进程级全局状态**（窗口链表、单例、静态计数器）的 API 才炸。

**推论**：这类 bug 不会在启动、渲染、交互阶段暴露，只在销毁/关闭/枚举这类"要遍历全局表"的路径上出现。

### B3. 静态穷举调用点，比反复加日志收敛得快（2026-10-31）

本轮靠三条静态结论直接砍掉了大半可能性：全 MC jar 里只有 `Window.close()` 调 `glfwDestroyWindow`、只有 `Minecraft.close()` 调 `glfwTerminate`、`Minecraft.close()` 本次只执行一次。先把调用点穷举干净，再决定要不要插桩。

### B4. 修复原则：谁创建谁销毁；跨实例句柄按创建方分派（2026-10-31）

### B5. 判断「是不是我的改动引入的」→ 同命令跑旧 jar 做 A/B 对照（2026-10-31）

**现象**：改完 200+ 处日志后冒烟，游戏启动 9 秒就自己 `Stopping!` 退出。第一反应是"我把日志改坏了"——如果照这个假设去翻改动，会白查很久。

**判断**：把改动前的 jar 换回去，**用完全相同的命令**再跑一次。旧 jar 同样 9~12 秒自行退出 → 与本次改动无关，是验证方式本身的副作用（`cmd //c` + stdin 重定向到 `/dev/null`，非交互环境下 MC 会退出）。

**结论**：任何"改完就出现的新症状"，先做 A/B 对照再开始排查。成本是一次重启（几十秒），收益是直接排除或锁定整个改动面。**注意对照必须同命令同环境**，否则引入新的变量（比如这次若顺手去掉 stdin 重定向，就会得出"改了就好了"的错误结论）。

**边界**：只在能完整回退部署产物时适用（jar / 二进制）。纯源码改动要先 stash 再重建。


不要指望"让使用方直接调原生 API 也能对"。正确做法是加一层按句柄归属分派的入口（本例 `MirageEarlyWindow.destroyWindow(long)`：是早期窗口 → 用创建方 GLFW 销毁并置 `NULL` 保幂等；其他句柄原样透传），并在字节码层把 `Window.close()` 的 `glfwDestroyWindow` 改道过去。**同时覆盖所有间接路径**（本例还包括"GPU 后端重试 → 关窗"）。

## C · 工程踩坑

### C1. Mixin 静默失效：`defaultRequire: 0`（长期有效，详见 `AGENTS.md` 技术注意事项 §2）

注册了但 jar 里没有对应 `.class`，Mixin 不报错、只静默跳过。表现为"配置加载成功、游戏正常、功能就是不生效"。**任何 `mirage.mixins.json` 改动，都要 `jar tf` 核对类名是否真在 fat jar 里。**

### C2. `dumpbin` 在 Git Bash 下会被路径转换破坏（2026-10-31）

需要 `MSYS_NO_PATHCONV=1`。另外 **PE 镜像基址不一定是 `0x400000`**（本例 `0x180000000`），RVA → VA 的换算不能写死，否则反汇编地址全错、会误判崩溃点。

### C3. `glfwSwapInterval` 在没有 current GL 上下文时会报 `GL ERROR 65538`（2026-10-31，未处理）

`handoff()` 里对 MC 侧的 `GLFW_NO_API` 窗口调 `glfwSwapInterval(0)` 就会触发。**无害但污染日志**，后续清理时注意：这类窗口上不要调任何依赖 current context 的 GL 函数。

### C4. 文档漂移是慢性病，"改完就登记"要核文件不能凭记忆（2026-10-31）

更新日志写"已登记两个 Mixin"，实际 `mirage.mixins.json` 条目数与文件对不上。**登记动作要当场 `grep` 一次文件确认**，否则文档会稳定地撒谎，而且撒的谎会在几周后变成"计划地基"（见 A3）。

### C5. 工作区长期挂着 WIP 时，提交只 add 自己的文件（2026-10-31）

### C6. 批量改日志必须做「括号感知解析」，不能用字符串替换（2026-10-31）

**现象**：把 238 处 `System.out.println` 换成日志门面，看似是机械替换，实际有三个陷阱：

1. **多行拼接**：`System.out.println("[Mirage] xxx: " + a` 换行继续 `+ b + c);`，按行替换会截断语句。
2. **异常参数**：`"...失败: " + e` 里的 `e` 需要变成 `error(msg, e)` 的第二个实参，否则堆栈丢失（这是本轮改造的核心目的，丢掉就白干）。
3. **前缀重复**：门面自带 `[Mirage] `，原消息里的 `"[Mirage] "` 必须剥掉，否则出 `[Mirage] ERROR [Mirage] xxx`。

**判断**：判断"能不能机械替换"的信号——**同一模式是否跨行、参数里是否有非常量**。有就上结构化处理。

**做法**：写一个按字符扫描的小解析器：定位调用起点 → 括号计数（跳过字符串字面量与转义）→ 取出实参文本 → 用正则抽 `"[Tag] "` 前缀得到通道、抽尾部 `+ t` 得到异常变量 → 重新生成调用。比逐条手改可靠，也比 sed 安全。做完必须**抽样 grep 校验**，并跑一次编译。

**边界**：只适用于语法规整的旧代码。若原代码本来就有副作用（如 `println` 里嵌了赋值），要先人工确认再批量处理。

### C7. 日志门面不能缓存 `System.out` 引用（2026-10-31）

**现象**：`Launcher` 在 main 早期把 `System.out/err` 换成 tee 流（旁路喂 HUD 日志节选）。如果门面在类初始化时 `private static final PrintStream OUT = System.out;`，之后所有日志都绕过 tee —— 控制台照常有输出，但 **HUD 上看不到任何新日志**，且没有任何报错。

**结论**：日志门面每次写都要重新取 `System.out` / `System.err`。同理，任何"标准输出替身"必须晚于 `System.setOut` 之后再取引用。

**边界**：反过来，若某处**需要**拿到原始流（如 tee 自身），必须在替换前保存——这两件事逻辑相反，写的时候要明确是哪一种。

### C8. BOM 的两个反向陷阱：`.ps1` 必须有，`.java` 必须没有（2026-10-31）

**现象一**：新建的 `.ps1` 用工具写成无 BOM 的 UTF-8 → `powershell -File` 直接报一堆语法错
（`"("后面应为表达式`、`字符串缺少终止符`），且报错里中文全是乱码。原因是 **Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI(GBK) 解码**，中文被拆成非法字节把解析器带偏。

**现象二**：同一个脚本把自己生成的 `.java` 用 `Set-Content -Encoding UTF8` 写出（PS5.1 会**加** BOM）→ `javac` 报 `error: illegal character: '\ufeff'` + 后面全线 `需要 class、interface、enum 或 record`。原因是 **javac 不剥 UTF-8 BOM**。

**结论**：两件事方向相反，写脚本时一起记：
- `.ps1` 落盘用 **带 BOM** 的 UTF-8：`[System.IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($true)))`
- 脚本内生成的 `.java` 落盘用 **不带 BOM**：`... UTF8Encoding($false)`

**边界**：`pwsh` 7+ 默认按 UTF-8 读脚本，第一条不成立；但项目按 PS5.1 跑（`powershell -File`），照做。

### C9. `Start-Process` 在重复的大小写环境变量下会直接抛异常（2026-10-31）

**现象**：脚本里 `Start-Process -FilePath java ... -RedirectStandardOutput` 抛
`已添加项。字典中的关键字:"http_proxy"所添加的关键字:"HTTP_PROXY"`。

**根因**：本机环境里同时存在 `http_proxy` 与 `HTTP_PROXY`。Windows 的进程环境块大小写不敏感，
`Start-Process` 复制父环境时会往不区分大小写的字典里插第二个键 → `ArgumentException`。
与脚本逻辑无关，是环境特性。

**绕过**：用 .NET 直接起进程，不经过 `Start-Process` 的环境复制：

```powershell
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.UseShellExecute = $false; $psi.RedirectStandardOutput = $true; $psi.RedirectStandardError = $true
$psi.StandardOutputEncoding = [System.Text.Encoding]::UTF8
$proc = [System.Diagnostics.Process]::Start($psi)
$outTask = $proc.StandardOutput.ReadToEndAsync(); $errTask = $proc.StandardError.ReadToEndAsync()
$proc.WaitForExit()   # 先起异步读，避免缓冲区写满卡死
```

顺带解决另一个老问题：**不要用 `& cmd 2>&1`**——PS5.1 会把原生 stderr 变成 `NativeCommandError`，
配合 `$ErrorActionPreference="Stop"` 会直接终止脚本。分离取两个流反而更干净。

**边界**：这是本机环境的坑，换台机器可能不复现；但 `RedirectStandardOutput/Error` + 显式 `UTF8` 编码是跨机器都该这么写的（否则中文输出解码随控制台代码页漂移）。

### C10. 给日志写断言前，先确认它走哪条流、栈帧来自哪（2026-10-31）

**现象**：首轮验证 40/41，唯一红的是一条自己写错的断言——用 stdout 去匹配 `[Mirage] ERROR`，
而 ERROR 按设计走 stderr。

**两条容易踩的**：
1. **流**：`MirageLog` 里 WARN 及以上走 stderr、其余走 stdout。断言写错流 = 永远红；反过来，
   若断言"ERROR 不该出现在 stdout"没写，级别流向变了也测不出来。
2. **栈帧来源**：验证程序的异常若在 `main` 里 `new`，栈里只有验证程序自己的帧；这样
   **测不到**"项目帧（`io.mirage.` / `net.minecraft.` 等）在预算内被保留"这条 smart 策略。
   把验证类放进 `io.mirage.*` 包（本轮放 `io.mirage.api.log.check`）+ 造一条深递归栈，
   才能同时验到"项目帧保留"和"超预算折叠为 `... N more`"。

**结论**：写断言前先明确「这条输出应该出现在哪个流、它的栈帧会是什么形状」，再落正则。
匹配整段输出容易跨条误判，用"取从 marker 行到下一个行首非空白行"的块截取更准（本轮 `Get-Block`）。

**边界**：仅适用于自带流向/格式约定的日志门面；普通 `println` 调试不受此限。


本轮开工时工作区有 15 个改动 + 17 个未跟踪文件（上一轮的早期窗口/Fabric 特性 WIP）。这种情况下 `git add -A` 会把别人的半成品一起固化，`git checkout .` 会直接毁掉别人的活。**只暂存本轮自己的文件，并在提交信息和更新日志里注明"工作区另有 WIP 未一并提交"。**

### C11. `io.mirage.*` 强制 app 加载的白名单，会连坐它引用的 `net.fabricmc.*`（2026-10-31）

**现象**：Fabric 服务端 mixin 一注册，进世界就崩，`java.lang.LinkageError: loader constraint violation:
loader 'app' wants to load abstract class net.minecraft.server.MinecraftServer. A different abstract class
with the same name was previously loaded by 'MirageClassLoader'`。崩在 `ServerLifecycleEvents.<clinit>`
→ `FabricLifecycleBridge.fireServerStarting`。

**判断链**：`MirageClassLoader.loadClass` 对 `io.mirage.*` 直接 `ClassLoader.getSystemClassLoader().loadClass()`。
所以 `io.mirage.fabric.runtime.FabricLifecycleBridge` 是 **app 定义**的；JVM 解析符号引用用「引用方所在类的
定义 loader」，于是它引用的 `net.fabricmc.fabric.api.*` 也由 app 解析；而 stub 的静态初始化里有
`MinecraftServer` 的类引用 → app 从 `-cp` 上的 `26.2.jar` 自己 `defineClass` 一份 → 与 mcl 那份冲突。

**结论**：凡是被 mixin 织入代码调用、且自身引用 `net.minecraft.*` / `net.fabricmc.*` 的 MG 侧 helper，
必须排除在「强制 app」白名单之外。本轮按既有 `io.mirage.neoforge.` 先例加了 `io.mirage.fabric.`。
**边界**：只对"被 mcl 侧字节码调用"的类成立；纯 app 侧工具（Launcher、MirageDebug）仍应走 app，
否则早期窗口会拿到两个单例（见 `已知bug.md` 该条）。

### C12. `:launcher:mirage-launch:build` 会把 fat jar 覆盖成瘦 jar（2026-10-31）

**现象**：照 `build` 命令构建后 `build/libs/mirage-launch-0.1.0.jar` 从 2.6 MB 变 67 KB，部署后启动即
`NoClassDefFoundError`，但 `jar tf` 看着"有类"——只是没有依赖。

**原因**：`build` 会跑标准 `jar` 任务，与 `fatJar` 共用 `archiveClassifier=""` 的输出名，谁后跑谁覆盖。

**结论**：部署前一律用 `:launcher:mirage-launch:fatJar`，并核对产物大小（~2.6 MB 量级）与
`unzip -t` 通过。**边界**：只跑 `fatJar` 时它 `dependsOn(runtimeClasspath)`，子模块 jar 仍会重建，不会打包旧字节码。

### C13. 判定「注入成功」要看两个层次：`[MODIFIED]` 只证明改了字节码（2026-10-31）

**现象**：`transform … [MODIFIED]` 一出现很容易当作收工，但 `MirageMixinBootstrap.transform` 的 catch 会吞异常
返回原字节码；反之 `[MODIFIED]` 也可能只是别的 mixin 改了同一个类。

**做法**：在 bridge 的 `fire*` 里放**每种事件首次触发打一行**（高频事件用 `Set.add` 去重），
用日志证明"回调真被调到"。本轮靠这行才发现 `CLIENT_PLAY_DISCONNECT` 一直没触发（客户端自己退出不走
`onDisconnect`），而不是想当然认为"注册了就会 fire"。

**边界**：打点必须是"首次一行"，否则 tick 类事件会把日志刷爆、淹没其它线索。

### B6. 要改字节码，先读 `loadClass` 确认类到底在哪一层被定义（2026-10-31）

**现象**：想给沙盒里的 mod 类加改写，直觉是重写 `defineClass`，结果一行都不生效。

**判断**：`URLClassLoader` 的默认路径是 `loadClass`（parent-first）→ 父找不到才进本 loader 的
`findClass` → 由**继承的** `findClass` 读资源并 `defineClass`。自定义 `defineClass` 只有在自己的
代码里显式调用时才被经过。所以挂点必须是 `findClass`。

**做法**：先读 `loadClass` 的 override（本项目 fake 包走 `findFakeClass`，其余走 `super.loadClass`），
确认目标类实际落在哪条分支，再决定改哪里。**验证**：改写后必须看到"改写了几处"的日志/计数，
而不是"类能加载"就当作生效。

**边界**：接管 `findClass` 后 `defineClass` 的默认保护域没有 `CodeSource`，靠
`getProtectionDomain().getCodeSource().getLocation()` 定位自己 jar 的 mod 会变成 NPE——要显式构造
`ProtectionDomain`（见 C15）。

## C · 工程踩坑（续）

### C14. `jar:file:/x.jar!/…` 的 `getPath()` 不能直接喂 `new File(...)`（2026-10-31）

**现象**：P0 的 fake 包枚举写了 `new File(u.getPath())`，在 Windows 上路径是
`file:/D:/x.jar!/mirage/sandbox-fake/`，`File` 构造抛异常，而外层是 `catch (Exception ignore) {}` →
**静默失败**，一直靠写死的 `net.minecraft./net.neoforged.` 兜底，看起来"一切正常"。

**做法**：`u.getPath()` 只取 `!/` 之前的 `file:/D:/x.jar`，再 `URI.create(...).toURL()` →
`new File(url.toURI())`。更稳的定位方式是**用本类自己的 code source**
（`SandboxRecorder.class.getProtectionDomain().getCodeSource().getLocation()`）再判断 jar/目录。

**识别特征**：功能"靠兜底能跑"，但一旦需要**按内容判定**（本轮是算 fake 表面指纹）就立刻暴露为
`none`/空集。所以凡是"扫描类路径资源"的代码，都要有一个能被证伪的观测点（指纹、计数），
否则永远不知道它在不在工作。

### C15. 替换调用时保持栈形状，就不要碰 `COMPUTE_FRAMES`（2026-10-31）

**做法**：把 `System.exit(I)V` 换成静态 `exit(I)V`、把 `Runtime.halt(I)V` 换成静态
`halt(Ljava/lang/Runtime;I)V`（接收者当第 0 参），操作数栈净效应完全一致 ⇒
`new ClassWriter(reader, 0)` 原样保留 StackMapTable 即可，**不需要**重算帧。

**为什么值得强调**：本项目有过"ASM 改过的类再交给 Mixin 转换就失败"的历史（`AGENTS.md` 技术注意 §9），
重算帧会让 class 进入"被 ASM 深度重写"的状态，更容易与后续转换打架。**边界**：一旦改写要新增分支、
改变局部变量表或栈深度，就必须 `COMPUTE_FRAMES`（并自己传 `getCommonSuperClass` 的 loader，
否则会拿到错的公共父类）。

### C16. 验证脚本"按前缀取行"时，一个前缀只能对应一行（2026-10-31）

**现象**：P2 脚本里 7 条缓存断言共用一个 `CACHE` 前缀（`CACHE fresh …` / `CACHE incompleteStored …` …），
而取值函数是"返回第一行以该前缀开头的" ⇒ 7 条断言全拿到同一行，6 条立刻变红，看起来像实现全坏了。

**做法**：每个用例一个**唯一前缀**（`CACHE-FRESH` / `CACHE-TMP` / `CACHE-TMPONLY` …），
或者在 harness 里统一加序号（`CASE-1-a`）。判据：断言读到的文本里必须包含该用例的特征键，
不能只靠"前缀匹配成功"。

**顺带**：PowerShell 的 `-match` 默认**不区分大小写**，所以断言里写 `True` 而 Java 打 `true` 也能过——
别把这当成"格式被校验过了"。

### C17. 缓存"无变化不写"要用 mtime 验，"原子写"要验"只剩 .tmp 时读不到"（2026-10-31）

- **无变化不写盘**：不能比内容（内容本来就一样），要在两次写之间 `sleep 60ms` 再比
  `Files.getLastModifiedTime`；NTFS 时间戳精度足够，同毫秒也不会误判成"重写了"。
- **原子写**：真正的判据不是"有个 `.tmp`"，而是**只剩 `.tmp`（模拟 kill -9）时 `lookup` 必须返回 null**。
  实现侧靠"`isCacheFile` 只认 `.json` 后缀 + `ATOMIC_MOVE`"，测试侧就验这条。

### C18. 两条采集链路合并数据：并集，而不是"新的覆盖旧的"（2026-10-31）

沙盒（fake 表面全量）与被动捕获（自有入口）看到的**不是同一个集合**，谁都不是全集。
所以 `MidCache.merge` 取并集 + 计数取大值；相应地，**diff 的比较对象必须是合并后的结果**，
否则"上次沙盒录到一批、这次被动录到另一批"会被报成大面积删除，diff 报告直接变成噪音。

### C19. 「只把状态塞进队列」的 API，不能用"没报错"证明它生效（2026-10-31）

**现象**：加载界面把文字从「AWT 光栅化 + fill」改回 `gge.text(Minecraft.font, ...)` 后，
红底、内存条、两条进度条全对，**一条文字都没有**，`latest.log` 里连 WARN 都没有；
代码上"看起来没毛病"——反射解析到了方法、`font` 非 null、调用没抛异常。

**判断路径**：
1. 先排除"画错位置/被盖住"：同一帧里 `fill` 画出来的条是可见的 ⇒ 管线、坐标、alpha 都正常，
   问题只可能在文字这条支路。
2. 读 MC 字节码（`javap -p -c`）：`GuiGraphicsExtractor.text(...)` 全链路只有一句实质操作——
   `guiRenderState.addText(new GuiTextRenderState(...))`，参数非空才入队，**不画像素、不抛异常**。
   于是"调用成功"这件事**没有任何验证价值**。
3. 再看原版自己怎么用：`LoadingOverlay.extractRenderState` 只做 `fill` + logo `blit`，
   **一个 `text()` 都不调**。原版不用的东西，在同一个时点上大概率是不能用。
   结论指向字形图集——LoadingOverlay 显示期正是首次资源重载进行中，字形提供器还没装载，
   每个字符解析不出字形 ⇒ 静默画空。

**结论**：判断"某绘制 API 是否生效"只能看**目标像素**，不能看返回值/异常/日志。
凡是"只登记状态、延后出图"的 API（`text`、deferred render state 一类），
"没报错"和"没画出来"是兼容的。同理，**原版在同一处不用某个 API，本身就是最强的反面证据**。

**边界**：`gge.fill` / `blit` 在重载期可用（进度条、logo 都是证据），所以该阶段的文字只能走
「AWT 光栅化成像素块 + fill」。

### C20. 像素字"糊成马赛克"多半是光栅化尺寸没对齐，不是像素字本身不行（2026-10-31）

**现象**：上一版把文字画成马赛克后，结论被写成"像素字必然糊"，于是转去用 `text()`（撞上 C19）。

**真因**：固定按 12px 光栅化，再在 GUI 空间按 `sx = guiWidth/854` 缩放绘制。
`sx < 1` 时相邻两列字形像素被压进同一个 GUI 像素、另一列被跳过，边缘必然锯齿糊死。
**正确做法**：先按**目标 GUI 像素尺寸**光栅化（`px = round(设计字号 × sx)`），再 1:1 落 GUI 像素，
每个字形像素恰好占一个 GUI 单位——和 MC 自带位图字体在 `guiScale > 1` 时的放大方式一致。

**实测数值（Consolas 无抗锯齿）**：12px 墨迹 Cap 高约 6px、14px 约 7~8px（≈ MC 字体 9 GUI 单位的视觉大小）、
"Loading mods" 14px 宽 98px、"Memory: …/…MB (…%)  CPU: …%" 14px 宽约 310px（854 宽画布居中不越界）。
判据：`fill` 块数（854×480 下 445 个）与墨迹总面积（1212 px）都可离线断言，
不需要开游戏就知道字到底画没画出来——见 `scripts/verify_forgestyle_text.ps1`。

### C21. `latest.log` 里没有 S1–S3 —— log4j 接管之前的 stdout 根本没落盘（2026-10-31）

**现象**：MSR P2 实机冒烟，按清单去 `latest.log` 找 `[Sandbox] 录制` / `[MID] 被动捕获`，一行都没有，
差点被判定成"P2 没生效"。同一份日志的第一行就是 `[LS] stage S4 RegistryMerge done`。

**根因**：log4j 直到 Minecraft 启动后才接管日志并写 `latest.log`。在那之前的 banner、早期窗口、

3. 回归脚本 `scripts/verify_launch_log.ps1`：反射调 private `Launcher.installLogTee(Path)`，

### C24. Gradle 报 `Unable to delete file '…/build/classes/java/main'` 时，先试重命名（2026-10-31）

### C28. `MirageClassLoader` 的 parent 是 platform loader：第三方库会"被"双份加载（2026-10-31）

**现象**：进世界后视角转不动。WASD、左键挖、滚轮全正常，光标隐藏、`mouseGrabbed=true`，
但 `MouseHandler` 的 `ignoreFirstMove` 永远 `true`、`accumulatedDX/DY` 恒 0——
**`onMove` 一次都没被调用**；而回到主菜单光标立刻正常。关「原始输入」无效。

**定位法**：`FabricClientTickBridge` 里加一次性探针（反射读 `MouseHandler` 字段 +
`glfwGetInputMode`/`glfwGetCursorPos`），实机跑一轮看哪个判据先变。
`ignoreFirstMove` 只有 `onMove` 真被调用才会置 `false`，它是"回调有没有到"的最干净判据。
（探针源码会被并行分支覆盖，**要留证据就趁 jar 还在时 grep 日志**。）

**真因**：`TransformStage` 用 `new MirageClassLoader(urls, ClassLoader.getSystemClassLoader().getParent())`
创建 MCL——parent 是 **platform loader**（不含 lwjgl），`urls` 却是整条游戏 classpath。
于是 MCL 走 `super.loadClass` 时在**自己的 URL** 里找到 `org.lwjgl.glfw.GLFW` 并 define 出**第二份**。
铁证两条：①`lwjgl-unsafe-agent` 的 `Successfully transformed MemoryUtil` 打印 **2** 次
（AppClassLoader 一次、MCL 一次）；②探针 `Class.forName(GLFW)` 与
`ClassLoader.getSystemClassLoader().loadClass(GLFW)` **不相等**。

后果是经典的「两份 glfw.dll 模块」：早期窗口（AppClassLoader 的 GLFW-A）`CreateWindow`，
MC 的 `glfwSetInputMode(GLFW_CURSOR_DISABLED)` 打在 GLFW-B 上，只置 **B** 的
`_glfw.win32.disabledCursorWindow`；真正处理 `WM_MOUSEMOVE` 的是 **A** 的 WndProc，
它查 A 的该全局（仍 NULL）直接 `break`——所以**只有光标位移被吞**，
`WM_LBUTTONDOWN`/`WM_KEYDOWN` 不查这个标记，点击键盘照常。
（同因还造成过退出期 `glfwDestroyWindow` 崩溃，见改动登记表 10-31 那行。）

**修法**：与 `io.mirage.*` 完全同构——`org.lwjgl.*` 也强制 `ClassLoader.getSystemClassLoader().loadClass`，
两份 GLFW 合一、`_glfw` 全局共享。`MirageEarlyWindow.shareLwjglNatives()`（统一
`org.lwjgl.librarypath` 到同一个 native 目录）作为兜底仍保留，但它**解决不了 Java 类双份**，
单用它修不掉这个 bug。

**判据（修复后实测）**：`sameGlfwClass=true`；`MemoryUtil` 只重写 **1** 次；
`acc=(20,18)(-32,0)(-14,0)…` 真实累计、`ignoreFirst` 翻 `false`。

**通用教训**：MCL 的 parent 是 platform loader 这件事意味着**任何第三方库**（lwjgl/netty/asm/…）
只要被 MCL 和 app 同时引用，就是两份类、两份 native 静态状态。新增第三方依赖时先问一句
"这个库有没有进程级单例/原生全局状态"，有就必须进 `loadClass` 白名单。

### C29. 加载界面文字的「AWT 光栅化」必须放在渲染线程之外（2026-10-31）

**铁律**：渲染线程（`LoadingOverlay` 的 `ForgeStyleOverlay.draw()`）**严禁碰 AWT**。任何 `BufferedImage` / `Graphics2D` / `FontMetrics` / 系统字体枚举都只能放在启动早期主线程的 `prewarm()` 一次性做完，渲染线程只查缓存拼装 + `fill`。

**踩过的坑**：第一版在 `draw()` 里每帧光栅化整串文本（内存行每帧变 → 缓存 key 永不命中 → 每帧重跑 Java2D 字体管线）→ GLFW 消息泵被占住 >5s → Windows 判「未响应」。中间版整串**异步**光栅化（守护线程）首帧必然无字、MIN_PRIORITY 守护线程还可能被加载繁忙饿死。

**终版做法**：**字符级预渲染**——`prewarm()` 把 ASCII 32–126 字形一次性光栅化进 `GLYPH_CACHE`（等宽字体按字符步进拼装）；渲染线程只查表 + `fill`，零 AWT、首帧即有字、任意动态串（Memory/CPU）即时出图。字号在 GUI 空间取固定 `GUI_TEXT_PX=10`，**绝不**按 `guiWidth/854` 缩放（否则 GUI 427×240 下算出 7px，笔画细到断笔）。

**配套回归**：`scripts/verify_forgestyle_text.ps1`（须先 `prewarm()` 再 `draw`；现场 javac 编译 + 假 `GuiGraphicsExtractor`，断言字形块数/墨迹面积/不越界/内存文字居中/版本号右对齐/四文字带各有字 + 源码守卫禁 `drawTextSafe`/反射 `text`）。

### C30. 修「主窗口无文字」顺手根除 `[Probe]` 临时诊断刷屏（2026-10-31）

`FabricClientTickBridge` 里两处 `[Probe]` 临时诊断（`fireEndTick` 内 `probe` + `fireStartClientTick` 内 `noteMove`/`noteGlfwIdentity`，视角回归遗留）每 10~20 tick 打一行 INFO，是"日志刷屏"元凶之一。这类临时诊断定位完必须**整段删除**（含私有字段与 helper），否则既刷屏又留 dead code；删除按行号精确切除后 `grep [Probe]` 验证无残留。

**顺带踩的打包坑**：fatJar 配置已 `dependsOn(configurations.runtimeClasspath)`，但 `from(configurations.runtimeClasspath.get().filter{...}.map{...})` 在**配置阶段**就把 FileCollection 物化成普通 List——若中途 `rm -rf` 某子模块 build 再跑 `:launcher:mirage-launch:fatJar`，配置阶段解析时该 jar 已被删 → 被静默排除出 fat jar，产物悄无声息缺模块（曾让 fabric-compat 没打进去、jar 小 58KB）。**改完代码后不要 `rm` 子模块 build，直接增量 `:fatJar` 即可。**

### C31. Mixin 关键失败被 `catch` 降级 = 功能静默消失，比崩溃更难查（2026-11-01）

`MirageMixinBootstrap.transform` 原来对**所有**异常一律 `catch → 打一行 warn → 返回原字节码`。
这个降级看起来稳妥，实际制造了最阴的一类故障：**配置加载成功、字节码没报错、游戏照常能玩，
只是某个功能永远不触发**，且日志里只有一行"转换 X 失败"，事后很难还原现场。

关键失败必须**致命化**：识别 `InjectionError` / `InvalidInjectionException` /
`InvalidTargetException` / `TargetNotFoundException` / `CriticalInjectionError` /
`MixinApplyError` / `MixinTransformerError`，直接抛 `Error`（不是 `RuntimeException`——
上层大量 `catch(Exception)` 会把它吞掉），让启动崩。判定用**类名字符串**而非 `instanceof`，
避免对 mixin 包内多个子包的编译期依赖，也避免 mixin 升级换包名后编译失败。

打日志时必须拼**完整异常链**（`describeChain`）：「目标方法 + mixin 名」只写在 Mixin 内层
异常的 message 里（`Injection failed into the target method 'onDisconnect' in the mixin
'FabricClientDisconnectMixin'`），只打最外层异常就丢掉这段，等于没定位到具体注入点。

**更根本的一层**：光靠运行期致命化不够——等它炸说明已经漏过去了。必须配**构建期离线校验**
对着真实字节码查（`scripts/verify_mixin_registry.ps1`）。注入点失效有三种形态，全都能静态查：
① **漏注册**（源文件不在 `mirage.mixins.json` 里）——检查要**双向**，只查"json 里有源文件"
抓不到这一半；② **目标方法不在目标类里**（F1 的 `onDisconnect` 实际在父类）——查方法时要
**沿父类链**找；③ **目标类/字段/被调方法不存在**——用 `javap` 对着原版 jar 查。

### C32. 解析 `javap` 输出与 PowerShell 正则的两个坑（2026-11-01）

- **构造器在 `javap` 里没有返回类型**：形如 `public net.minecraft.commands.Commands(A, B);`，
  与普通方法 `public void tick(X);` 结构不同。而 `@Inject(method = "<init>(...)V")` 注入的正是它，
  必须单独识别成 `<init>`，否则构造器注入点会被误判成"方法不存在"。
- **正则里带尾随空格的可选分组，后面不能再要求 `\s+`**：写成
  `^(?:public |private )\s+(\w+)\(` 时，前缀组已经吃掉了那个空格，`\s+` 永远匹配不上，
  表现为"正则看起来对但一条都不中"。写 `(?:public|private)\s+` （空格移出分组）才对。
  这类"看起来没道理就是不中"的正则，先单独把样本行拿出来测，别在脚本整体里猜。
- **注入方法名有两种写法**：裸名 `"tick"` 与带描述符 `"tick(Ljava/util/function/BooleanSupplier;)V"`，
  提取时统一剥到标识符部分；`<init>` 要单独放行。

### C33. 测试「输出流向」要按消息内容判定，不要按前缀判定（2026-11-01）

验证 MEL 的分流时写了「stdout 里不应出现 `[MG-WARN]`」，结果误报：检查程序自己打印的 `MirageException.toString()` 本来就含 `[MG-WARN]` 前缀，它是合法输出。改成按**消息内容**判定（如「stdout 不含 warn-case」/「stderr 不含 ignore-case」）后通过。

教丝：**判定「这个流里有没有某类输出」要按内容特定字符串，不要按前缀（前缀很容易被其他合法输出带出）。** 另：测试自身的输出也是被测对象，断言前先看一眼测试程序自己打了什么，避免自岁a。

### C34. 性能测量先分阶段，一次就能看出靶子（2026-11-01）

原计划只有一个「启动时间」指标，实测出来端到端 23.6~70.3 秒、波动 3 倍，无法判断是哪里慢。拆成分阶段后一眼看出：**S4 RegistryMerge 占 6.8~25.9 秒，是唯一的大头**；而 S1+S2+S5+S6 合计仅 0.6~1.1 秒。且 S4 的波动远大于其他阶段，说明它大概率是**等待**（如等 tick 推进注册窗口）而不是计算。

推论：**测量粒度应当先拆到阶段，再看哪个阶段大；只看总数的话，无法引导行动。** 同理，面向用户的指标（「点开游戏到能玩」）与面向开发者的指标（「MG 自己开销多少」）要分开计量——S7 Loaded done 是「mod 管线结束」，不等于「TitleScreen 就绪」，后者目前没有锚点，得补。

**【已过时·2026-11-01 · 被 C35 修正】** 上面「S4 是唯一的大头」是**误判**：当时只抄了 S1~S6、只抄了 6 个会话里的 4 个，**整段漏掉了 S7 Loaded**（实测 23.6~68.1 秒，比 S4 还大），还漏掉了 S4 = 40 213 ms 的那个会话（把上界记小了 55%）。「S4 大概率是等待而不是计算」这个推论同样未经证实——S4 内部的大头是 `Bootstrap.bootStrap()`，那是 **MC 原版**的成本。同段末尾「后者目前没有锚点，得补」也已过时：锚点已于 2026-11-01 补上（`MiragePerf.mark("titlescreen")`）。

### C35. 手抄的性能基线会漏阶段——必须由脚本从日志生成（2026-11-01）

C34 结论里的「S4 是唯一的大头」被证伪。写 `scripts/measure_startup.ps1` 把 8 个会话全量解析一遍后发现两处漏：

1. **整段漏掉 S7 Loaded**（实测 23.6~68.1 s，比 S4 还大）。当时把 `S7 Loaded done` 当成「终点」而不是「一个阶段」，于是占大头的它根本没进表。
2. **漏掉 8 个会话里的 3 个**（含 S4 = 40 213 ms 的那个），S4 上界被记成 25 918 ms，比实测小 55%。

根因不是「抄错数字」，是**抄的时候只看了自己当时关心的阶段**——人抄的表会被当时的关注点污染，而且事后看不出漏了。

对策：把测量写成脚本，`docs/perf-baseline.md` 只留脚本生成的表 + 指向脚本的用法；脚本要**如实报告哪些维度测不了**（缺锚点就列出来），不要填 0 糊过去——「0 ms」会被读成「这段不花时间」，是假数据。

### C36. 变异检验的第二个作用：发现测试**没测到**的地方（2026-11-01）

给 `measure_startup.ps1` 做变异检验时，第一种变异（把段定义里的锚点名 `s4.version` 改成 `s4.versionX`）**退出码仍是 0**。原因：段定义共 10 条，自检只断言了其中 5 条的值，被改的那条**没有任何断言盯着**，于是它算出的 `null` 没人看——**测试全绿，但测试是残的**。

修法：加一条「段定义表自洽」断言（样本里每条定义的 from/to 锚点都必须存在，且每段算不出耗时就必须为 `null` 而不是 0），再补渲染层断言（缺锚点的段在报告里必须显示「缺锚点」，不能显示「0 ms」——报告给人看时，假数据比空值更有欺骗性）。

推论：**变异检验不只用来证明「测试有效」，也用来证明「测试覆盖完整」。** 一个变异打不红，往往不是变异无效，而是**那个位置根本没被测**。判据：故意破坏后退出码必须变红；变绿就说明该处缺断言。

### C37. PowerShell 的 `cd` 不改 .NET 的当前目录（2026-11-01）

在 PowerShell 里 `cd D:\xxx` 之后，`Copy-Item ".\a.ps1"`、`powershell -File .\a.ps1` 都能找到文件，但 `[System.IO.File]::ReadAllText(".\a.ps1")` 报「未能找到路径的一部分」——因为 .NET API 用的是 `[Environment]::CurrentDirectory`，它**不随 PowerShell 的 `cd` 变**。

后果：同一段脚本里两种路径语义不一致，且**报错信息是「文件不存在」**，极易误判成「文件真没了」或「替换逻辑写错了」——本轮就因此把三次变异检验全跑成了「替换未命中」。

对策：脚本里凡是用 .NET API 读写文件，一律传**绝对路径**；或者在脚本开头用 `$PWD.ProviderPath` 取绝对路径。

### C38. PowerShell 里 Markdown 反引号是转义符（2026-11-01）

脚本要生成 Markdown，习惯性写了 `` "> 数据来源：`" + $LogPath + "`" ``。PowerShell 的反引号是转义符，双引号字符串里的反引号会吃掉后面的字符，解析器报「方法调用中缺少 `)`」，而**报错位置指向那一行、看不出真正原因是反引号**。

对策：含 Markdown 反引号的字符串一律用**单引号**字符串（单引号里反引号是字面量）：`'> 数据来源：`' + $LogPath + '`'`。另：`.ps1` 必须带 UTF-8 BOM（否则 PS 5.1 按 GBK 读，中文乱码且直接语法错），但 `.ps1` 里**生成的 `.java` 不能带 BOM**（C8）。

### C39. multi-catch 不能捕获有继承关系的两种异常（2026-11-01）

写 `catch (JsonParseException | RuntimeException e)` —— **这是编译错误**，javac 报「multi-catch 中的异常类型之间有继承关系」。因为 `JsonParseException extends RuntimeException`，Java 不允许在 multi-catch 里同时列一个类及其父类。

坑在它长得太像「冗余但无害的写法」，而且**平时不写 multi-catch 的人不会想到**。本轮它是离线回归第一次运行时被抓出来的（javac 直接报错），比 gradle 构建早一步——说明「把纯逻辑拆出来单独编译」这件事本身就顺带抓到了构建期错误。

对策：只捕 `RuntimeException`（它已包含 `JsonParseException`）；若要区分处理，用两个 `catch` 分支或 `instanceof` 判别。

### C40. Gradle 9 移除了 `archivesBaseName`，而它在本项目里本来就是多余的（2026-11-01）

三个模块的 `build.gradle.kts` 里写了 `archivesBaseName.set("mirage-config")`，Gradle 9.1 构建直接失败：`Unresolved reference 'archivesBaseName'`（该 API 在 8.x 起废弃、9.x 移除）。

更值得记的是**它根本不需要**：gradle 默认就用项目名做 archiveBaseName，而 `settings.gradle.kts` 里 `include(":modules:mirage-config")` 的项目名就是 `mirage-config`，产物本来就是 `mirage-config-0.1.0.jar`。

推论：加构建脚本配置前先问一句「默认行为是不是已经是我要的」。凡是「把名字再声明一遍」式的配置，要么是历史迁移残留，要么是**用配置掩盖了真实的隐含依赖**——本例里 `ModuleRegistry.moduleJar` 按「文件名以模块 id 开头」匹配，**项目名必须等于模块 id**，这是条隐含依赖，值得写进注释而不是写一行冗余配置。

### C41. 在测试里重写一遍生产算法 = 测副本，不是测代码（2026-11-01）

给 G9 写离线回归时，我在**检查程序里**重写了一份依赖闭包算法（因为 `ModuleRegistry.collectClosure` 是包级可见、检查程序在子包下够不着）。跑出来 23 断言全绿，看着很稳。

但它测的是**检查程序里那份副本**，不是生产代码。生产代码若算错了，测试照样全绿——这正是「全绿的测试可能根本没测到东西」的典型形态（与 C36 同源，但更隐蔽：C36 是断言数量不够，这个是**断言打在被测对象之外的副本上**）。

修法两步：
1. **把纯逻辑抽成不依赖重物的类**：新建 `ModuleGraph`（只依赖 `ModuleDescriptor` 与纯 POJO `ModManifest`），`ModuleRegistry` 委派给它。这样闭包算法能离线编译。
2. **检查程序直接调生产代码的 public 静态方法**，不再重写副本。

推论：写测试时先问「**我这条断言打在谁身上**」。如果答案是「我刚写的一份等价实现」，那这条断言的价值是零。生产方法因为访问修饰符够不着而无法直接调用时，**该改的是生产代码的结构（抽类），不是测试的做法**。

### C42. PowerShell 取子进程输出：Write-Host 捕获不到、StandardOutput 只能读一次、必须先读流再 WaitForExit（2026-11-01）

写 `verify_module_loading.ps1` 时连踩三个坑，症状都是「脚本跑了但看不到任何输出」：

1. **`Write-Host` 走信息流**（PS 5.0+），不是标准输出。父进程里 `& powershell -File x.ps1 2>&1 | Out-String` **捕获不到**，而 `2>&1` 只合并错误流。→ 对策：脚本把明细**落盘成报告文件**，父进程读文件；这顺带对 CI 有用。
2. **`Process.StandardOutput` 只能读一次**：它返回的是 `StreamReader`，第二次读拿到的是**剩余空串**。本轮原本读了两遍（一次打印、一次拿去正则匹配计数），于是计数合并**静默失效**——不报错，只是永远匹配不上。→ 对策：`ReadToEnd()` 一次，存变量复用。
3. **必须先读流再 `WaitForExit()`**：反过来在子进程输出超过管道缓冲时会**死锁**（父进程等退出、子进程等写入）。

另：`[Diagnostics.Process]::Start` / `Start-Process` 在部分执行通道里被安全策略拦截（但**写在 `.ps1` 文件里**再执行则放行），遇到「命令被拦」时先考虑换个落盘/委托方式，别在同一条路上反复试。


### C43. 一项能力被文档归到多个实现类时，逐个 grep 调用方——死代码会让完成度虚高（2026-11-01）

**现象**：缺口清单把「fabric.mod.json 解析」写成 `FabricModManifest` + `ModsJsonParser` 两个类并列；盘点时 grep 发现 `ModsJsonParser`/`OutputModel`（fabric-compat 包下那对）**全仓无任何调用方**——是硬解码器早期遗留。更隐蔽的是：`ModsJsonParser` 里解析了 `accessWideners`/`mixinConfigs`，让"accessWideners 是否已解析"的存疑项看起来接近完成——**死代码里的已实现 ≠ 运行时已实现**。

**判断路径**：`Grep ModsJsonParser|OutputModel` 全仓 → 命中只有文档与自身 → 定案死代码；再对照 `ModDiscoverer` 确认运行时唯一解析路径是 `FabricModManifest`。

**结论/边界**：盘点完成度时，"文档说有"和"代码里有"都不算数，要找**从入口可达的调用链**。删除死代码前先 grep 一次并留档（本轮只标注未删除，与 WIP 收口策略一致）。

### C44. 模块搬迁后，旧文档的引用不会自己搬家（2026-11-01）

**现象**：LS 拆分把 entrypoints/DIST 逻辑从 `Launcher` 迁到 `lifecycle-starter` 后，缺口清单和 AG 总计划仍写 `Launcher.callOnInitialize` / `Launcher.DIST`——按图索骥去 `Launcher.java` 里 grep 什么都找不到。

**结论/边界**：盘点"实现细节在哪个文件"这类问题时，一律以 grep 当前符号为准，不信任文档里的类名/方法名；发现漂移按规则 9「标注原文 + 追加正确内容」。搬迁类改动的验收清单里应含"旧引用是否需要同步"一项。

### C45. "极简 mod 能跑" ≠ "真实 mod 能跑"：结构性缺口按链接期依赖分类（2026-11-01）

**现象**：Fabric 兼容层的实机验证都是"注册 lifecycle/tick 回调"的极简 mod，全绿；但真实 Fabric mod 几乎必然踩三类**链接期**硬伤——① 调 fabric-api 未实现的事件类 → `NoClassDefFoundError`；② mod 自带 mixin config 不被加载（`FabricModManifest` 不解析 `mixins` 字段、mixin 引擎只认自家单一配置）→ mixin 派生类型 `NoClassDefFoundError`/`NoSuchMethodError`；③ accessWidener 未放宽 → `IllegalAccessError`。

**结论/边界**：评估兼容层覆盖面时，把缺口按「链接期炸」（类/方法/访问缺失，mod 完全起不来）与「行为缺口」（跑了但语义偏差）分两档——链接期档优先级天然更高，且**验不出来**（现有极简 mod 冒烟永远不会碰它），只能靠代码盘点暴露。本轮据此把「mod 自带 mixin config 不加载」新列为缺口（清单 P1-13），并定案 accessWideners（P2-9）。
