# 性能与体积基线（Phase 1 验收标准 4）

> 采集时间：2026-10-31 ~ 2026-11-01
> 数据来源：本机实机日志 `mc-shili/versions/26.2-mirage/logs/mirage-launch.log`（6 次启动）
> 环境：Windows 11 / Intel UHD Graphics / JDK 25.0.4 / MC 26.2 / 4 个测试 mod（examplemod / testtab / addonmod / expore）
> **本文只记实测数字，不记目标值。** 目标由 Q9 裁决后另立（见 §5）。

---

## 1. 测量口径（先说清楚，免得数字被误读）

| 指标 | 起点 | 终点 |
|---|---|---|
| 端到端启动 | `Launcher` 打印启动横幅（`===== Mirage Launch 0.4.0 @ ...`） | `[LS] stage S7 Loaded done` |
| MG 自身阶段 | `S1 Discovery start` | `S6 ModInit done` |
| 单阶段 | 该阶段 `start` 行 | 该阶段 `done (N ms)` 行 |

**注意**：`S7 Loaded done` 是「mod 加载管线结束」，此时 MC 主类刚启动、**资源重载与 TitleScreen 尚未完成**。
所以「端到端启动」这一列**不是**用户感知的"点开游戏到能玩"，真实感知还要加上 MC 自身的资源加载
（该会话实测：早期窗口交接 17:59:24 → 17:59:30，Sound engine 17:59:33，recipes 加载完 17:59:41）。
**要拿到"到 TitleScreen"的真值，必须补一个 TitleScreen 锚点**——目前日志里没有，见 §4。

---

## 2. 分阶段实测（毫秒）

| 阶段 | 会话 1 | 会话 2 | 会话 3 | 会话 4 | 性质 |
|---|---:|---:|---:|---:|---|
| S1 Discovery（mod 发现） | 111 | 103 | 110 | 97 | 毫秒级，稳 |
| S2 Parse（描述符解析） | 4 | 2 | 5 | 3 | 毫秒级，稳 |
| S3 BytecodeTransform（字节码转译） | 741 | 910 | 574 | 569 | **亚秒级**，随 mod 数与类数增长 |
| S4 RegistryMerge（注册表合并） | 6764 | 11732 | **25918** | 7433 | **⚠ 唯一的大头，且波动 4 倍** |
| S5 EventBusInit | 0 | 0 | 0 | 0 | 空操作 |
| S6 ModInit（mod 初始化） | 416 | 108 | 257 | 517 | 亚秒级 |

**读法**：MG 自己的计算量微不足道——S1+S2+S5+S6 合计通常在 **0.6 ~ 1.1 秒**，
S3 转译也在 1 秒内。**S4 一项就吃掉其余所有阶段的总和的 7 ~ 25 倍。**

## 3. 端到端实测

| 会话 | 横幅 → S7 done | 其中 S4 占比 |
|---|---:|---:|
| 1 | 34 972 ms | 19% |
| 2 | 70 301 ms | 17% |
| 3 | 23 594 ms | — |
| 4 | 34 278 ms | — |
| 5 | 51 799 ms | — |
| 6 | 34 972 ms | 21% |

区间 **23.6 ~ 70.3 秒**，波动 3 倍。同样的机器、同样的 mod 集合，差异来自
资源缓存冷热、显卡驱动、后台负载，以及 S4 自身的等待量。

## 4. 体积

| 项 | 实测 |
|---|---|
| `mirage-launch-0.1.0.jar`（fat jar，含 Mixin / ASM / Gson / fabric-compat stub） | **2.72 MB**（2 850 293 字节） |
| 其中 `net.fabricmc.*` 运行时 stub（11 个类） | 数十 KB 量级 |
| 空壳模块 `mirage-config` / `mirage-kotlin` / `mirage-network` | 各产一个 0.1.0 的**空 jar**（Phase 1 模块懒加载落地后可改为按需加载） |

**峰值内存：未测。** 本轮没有取得可信数字——需要在一局游戏运行中采样进程
`PeakWorkingSet64`（或用 `jcmd <pid> GC.heap_info` 多次取样），而按项目规则
（GUI 类改动不自行启动游戏、交互式验收交用户手测）本轮没有自行拉起游戏，
因此**这里不填估计值**。

复现方法（用户侧，一次约 1 分钟）：

```powershell
# 启动游戏后另开一个 PowerShell 窗口，跑到进世界后执行：
$p = Get-Process java | Sort-Object StartTime -Descending | Select-Object -First 1
$p.PeakWorkingSet64 / 1MB      # 峰值工作集（MB）
# 或直接看 GC 堆：
& "C:\Program Files\Java\jdk-25.0.4\bin\jcmd.exe" $p.Id GC.heap_info
```

启动参数里 `-Xmx1740m -Xmn261m` 是**上限配置**，不是实测占用，两者不要混。

## 5. 结论与建议（建议，待 Q9 裁决）

1. **Q9 原来的「< 2s 启动」不成立**——它从提出起就没被测量过。实测端到端是 **23.6 ~ 70.3 秒**，
   与目标差一个多数量级。**Q9 必须重定**，否则 Phase 1 的验收标准 4 无法客观判定"达标"。
2. **建议把目标拆成三项可分别判定**，而不是一个笼统的"启动时间"：
   - **MG 自身计算开销**（S1+S2+S3+S5+S6，不含 S4）：**当前 1.6 ~ 2.6 s** → 目标可定 **< 2 s**（已接近达成）。
   - **S4 注册表合并**：**当前 6.8 ~ 25.9 s** → 这是唯一值得动刀的地方，且**大概率不是计算耗时，
     而是"等游戏 tick 推进注册窗口"的固定等待**（否则不会随外部负载波动 4 倍）。
     建议把 S4 改成「按需触发 + 显式等待条件可观测」，先量出"等了多久、在等什么"，再谈优化。
   - **端到端到 TitleScreen**：需先补锚点（见下），再定目标。
3. **补一个 TitleScreen 锚点**：在 `S7 Loaded done` 之后再打一行"TitleScreen 就绪"，
   才能回答"用户点开游戏到能玩要多久"这个真正的用户感知指标。现在缺这一环。
4. **体积**：2.72 MB，与 `< 3 MB` 的既有目标相安有余（余量约 9%）。若后续引入 KubeJS 这类
   重依赖，按 AG 总计划 Q3 的口径应做成**独立可选模块**，不要进核心 fat jar。
