# MG（虚幻加载引擎）项目总纲

> Minecraft Java 版 26.1+ 自研模组加载器
> 最后更新：2026-10-11

---

## 一、项目定位

MG 是自研的第五个 Minecraft Java 版模组加载器，中文全称**虚幻加载引擎**。目标是从底层摆脱 Forbrick 式"多加载器嵌套、强行合并、排错困难"的路线，做一个独立运行时。

**核心定位：**

- **不基于任何现有加载器**：Forge、Fabric、NeoForge 只作为参考或沙箱记录源，不作为 MG 的宿主。
- **只做 MC 26.1+**：26.x 是 MC 官方自 2026 年开始的新命名规则，且不带混淆，可直接读类名、方法名、字段名。
- **MG 是唯一运行时**：模组最终通过 MG 描述被重放，避免加载器嵌套。
- **直接沿用 Mixin**：Mixin 成熟且底层，重写不现实；MG 集成 Mixin，不重造注入框架。
- **Fabric mod 的 Mixin 部分理论上可直接转换**；但 Fabric API 必须在 MG 上重建高频子集。
- **已有基础**：MG 此前已能做到加入方块和代码注入，但不够全面；需要补事件、网络、资源、GUI、配置、依赖、生命周期、访问宽化、多版本适配等。

**参考与许可证原则：**

| 项目 | 许可证 | 用法 |
|---|---|---|
| Fabric Loader / Fabric API | Apache 2.0 | 可参考架构，注意 NOTICE |
| Mixin | MIT | 可直接集成 |
| ASM | BSD | 可参考 |
| Forge / NeoForge | LGPL 2.1 | **禁止直接抄代码**，只能行为观察、接口枚举，或 clean-room 实现 |

---

## 二、核心架构

```
Minecraft 26.x
    ↓
MG 加载器（模组发现、依赖解析、生命周期）
    ↓
Mixin 引擎（直接集成，不重写）
    ↓
MG 运行时（类变换、事件、注册表、资源、网络）
    ↓
Fabric API 兼容层（高频子集 → 逐步扩展）
    ↓
Fabric mod
```

**与 Forbrick 的本质区别：**

- **Forbrick**：同进程硬缝 Forge、NeoForge、Fabric，互相嵌套，问题层层传递；
- **MG**：MG 是唯一运行时，其他加载器只作为记录源，模块边界清晰，排错容易。

## 三、四层实现思路

### 1. 硬解码

- 直接解析字节码，转译为 MG 码；
- 用 ASM 提取类结构、方法调用、字段、注解、Mixin 目标、事件监听器候选；
- 构建依赖图、注册表引用、访问宽化需求；
- 输出 MG 静态描述；
- 只做静态分析，不做运行时执行；
- invokedynamic、Lambda、反射、MethodHandle、Unsafe 等标注"静态不可解析"，交给软解码。

### 2. 软解码

- 多 JVM 进程，分别使用虚拟沙箱；
- 让原模组加载器认为自己在正常环境下运行；
- 用 Java Agent + Instrumentation 拦截类加载；
- 实时捕捉钩子、Mixin 内容、事件订阅、注册表、资源加载；
- 创建 MG 文件，输出 MG 动态描述；
- 服务端优先，客户端后置。

### 3. 加载后对比提取

- 在软解码基础上，不实时捕捉；
- 加载完成后与原游戏对比，提取差异，生成 MG 文件；
- 作为校验和补漏手段，不作为主要手段；
- 因为类加载后很多中间态会丢失，事件订阅是运行时对象图，事后 diff 难以完整还原。

### 4. 自研 MG 加载器

- 重放 MG 描述，不依赖任何现有加载器；
- 实现类加载器、生命周期、注册表、事件总线、网络、资源包/数据包；
- 把 MG 描述编译成 JVM 字节码，不做解释执行；
- 生命周期严格设计，不靠试错调顺序；
- 错误分级：可忽略 / 警告 / 致命，禁止静默失败。

## 四、9 个 Agent 分工

通用规则写进每个 Agent 提示词开头：

```
【项目】MG（虚幻加载引擎），Minecraft Java 版 26.1+ 自研模组加载器。
【原则】
1. 不基于 Forge/Fabric/NeoForge，MG 是唯一运行时。
2. 只做 26.1+，官方不混淆，直接用类名/方法名。
3. 直接沿用 Mixin（MIT），不重写注入框架。
4. 接口先冻结，模块间只通过 A1 定义的接口通信。
5. 参考 Fabric/Mixin 系（Apache 2.0 / MIT），禁止抄 Forge/NeoForge（LGPL）。
6. 禁止静默失败，所有错误必须记录并分级。
7. 禁止跨模块修改代码，只在自己模块内工作。
8. AI 上下文只装本模块，接口以 A1 文档为准，不以代码为准。
9. 虚拟桌面技能仅 A7 独占，其他 Agent 禁止使用。
```

| Agent | 模块 | 核心职责 | 虚拟桌面 |
|---|---|---|---|
| A1 | MG-Spec | 定义 MG 格式规范、模块接口、生命周期、错误分级；冻结接口；不写业务实现 | 否 |
| A2 | MG-HardDecode | ASM 静态解析，输出 MG 静态描述；不做运行时执行 | 否 |
| A3 | MG-Sandbox | 多 JVM 沙箱，Java Agent 实时拦截 Mixin/事件/注册表，输出 MG 动态描述 | 否 |
| A4 | MG-Runtime | 重放 MG 描述，实现类加载、生命周期、注册表、事件总线、网络、资源；编译为 JVM 字节码 | 否 |
| A5 | MG-Mixin | 直接集成 Mixin，实现 MixinService；解析 Mixin 配置；注入失败必须记录 | 否 |
| A6 | MG-FabricCompat | 实现 Fabric API 高频子集：事件、注册表、网络、资源；解析 fabric.mod.json；提供 FabricLoader 等价 API | 否 |
| A7 | MG-GUI | 客户端/GUI/渲染/输入/窗口；在虚拟桌面测试；先做单进程兼容，多 JVM 客户端后置 | **是，独占** |
| A8 | MG-QA | 测试矩阵、CI、冒烟测试、启动顺序回归、许可证合规、兼容率统计、检查隐式耦合 | 否 |
| A9 | MG-Report | 总结报告与用户沟通；维护状态看板；向用户汇报；传达用户决策；不写代码、不改模块 | 否 |

### A7 虚拟桌面特殊规则

虚拟桌面技能让 AI 使用另外的账号，与用户环境隔离，适合 GUI 相关开发。该技能只能由 A7 独立使用，其他 Agent 禁止使用。

A7 启动任何 GUI 程序时：

- 按 **Win+R** 打开运行对话框；
- 手动输入命令；
- **不要使用任何工具直接运行命令**，否则会在用户环境启动，而不是虚拟桌面。

## 五、并行运行策略

A1 是总闸。A1 不冻结接口，其他并行就是各写各的，最后拼不起来。

### 阶段 0：立即并行（3 个）

- A1：写规范与接口
- A8：建测试与合规框架
- A9：建状态表与沟通机制

A2–A7 此时只准备环境、读资料，不写业务代码。

### 阶段 1：A1 接口初版冻结后（7 个）

- A2、A3、A4、A5 四路并行
- A8、A9 继续在线
- A1 维护接口

### 阶段 2：A5 初版可用后（8 个）

- A6 加入并行

### 阶段 3：A4 初版可用后（9 个）

- A7 加入并行，独占虚拟桌面

**依赖关系：** A5 是 A6 的前置；A4 是 A7 的前置；A8、A9 全程并行，不阻塞任何开发。

**实际建议控制在 6–8 个同时**，因为 A1 要协调接口，A9 要汇总，太多会上下文爆炸。

## 六、关键约束与规则

1. **接口先冻结**：A1 先定义 MG-Spec、MG-Interfaces、MG-Lifecycle、MG-Errors 初版，之后只做增量修订。
2. **禁止跨模块修改**：每个 Agent 只在自己模块目录工作，AI 上下文只装本模块。
3. **接口以文档为准**：代码可以变，A1 的接口文档是唯一真相。
4. **错误不静默**：所有运行时错误必须记录并分级；致命错误直接崩溃。
5. **许可证分层**：Fabric/Mixin 系可参考，Forge/NeoForge LGPL 禁止抄。
6. **26.x 无混淆**：省掉 remap 层，硬解码、Mixin 重放、API 适配、调试、跨版本 diff 都大幅简化。
7. **虚拟桌面隔离**：仅 A7 可用，按 Win+R 手动输入，不用工具直接运行。
8. **A9 只沟通不开发**：A9 是用户与开发团队唯一沟通桥梁，不写代码、不改模块。

---

## 七、风险与难点

1. **Mixin 集成**：Mixin 成熟，直接沿用正确；但 MG 要实现 MixinService，提供类字节、混淆环境、注入器。
2. **Fabric API 兼容层是无底洞**：Fabric API 包含事件、注册表、网络、资源、配置、命令、界面、渲染、传输、权限、标签、配方等；只能先做高频子集，逐步扩展。
3. **客户端多 JVM 沙箱几乎不可能**：客户端依赖 OpenGL、LWJGL、原生库、窗口、输入；多 JVM 共享渲染上下文极难。建议服务端优先，客户端后置或单进程兼容。
4. **性能**：MG 解释执行会慢，必须编译成 JVM 字节码。
5. **版本内碎片**：即使只做 26.1+，26.1、26.2、26.3 之间也会有 API 变化，需要版本适配层。
6. **AI 上下文膨胀**：模块化并行是解法，但必须接口冻结、禁止跨模块修改。
7. **许可证风险**：Forge/NeoForge 的 LGPL 代码不能直接抄，必须 clean-room 或只做行为观察。

---

## 八、推进顺序建议

1. **先做 MG 格式规范**：定义清楚类变换、事件、注册、资源、依赖怎么描述。
2. **再做沙箱记录器**：服务端 + Fabric + 26.1，跑通 10 个模组，输出 MG。
3. **然后做 MG 运行时**：能重放这 10 个模组的 MG，验证行为一致。
4. **扩展 API 适配层**：逐步加 Forge/NeoForge 高频 API。
5. **测试矩阵**：100 个模组、1000 个模组，统计兼容率。
6. **客户端**：最后考虑，先单进程兼容，多 JVM 沙箱后置。

---

## 九、最终判断

MG 方案比 Forbrick 干净，也比"基于 NeoForge 做 MG"彻底。它不是写兼容层，而是重造整个模组生态的基础设施。

- **方向对**：独立运行时 + 26.x 无混淆 + 沿用 Mixin + 模块并行；
- **范围要控**：先服务端 Fabric 26.1 子集，跑通 MG 闭环，再扩展；
- **最大风险**：Fabric API 兼容层无底洞，客户端多 JVM 沙箱几乎不可能；
- **成功关键**：A1 接口冻结、A8 合规测试、A9 汇总沟通、A7 虚拟桌面隔离。

---

**一句话**：9 个 Agent，A1 冻接口，A2–A5 四路并行，A5 好后加 A6，A4 好后加 A7，A8/A9 全程在线，A7 独占虚拟桌面按 Win+R 手动启动。先做服务端 Fabric 26.1 子集，跑通 MG 闭环，再谈扩展。
