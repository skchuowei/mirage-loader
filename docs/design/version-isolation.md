# 版本隔离设计冻结（Version Isolation — Design Freeze）

> 状态：**设计冻结（Design Freeze）**，开发为**事件触发**，非进度触发。
> 冻结日期：2026-11-01
> 来源：`MG-设计脉络与命名体系.md` §二（主体与补充包）、§三（沙盒报版本）、§七（AG/MG 分离）；2026-11-01 对话澄清（用户三点修正）。
> 关联计划：`docs/plans/2026-10-31_AG-总计划重梳理.md` §58 G18 / §418 T7.2 / §560 T7.2 / §197 G18 前提 / §594 Q7（均已同步修正）。

## 0. 要解决的问题

1. 规划文档原把"适配新版本"和"补充包"揉在"版本区间补充包（MVA/MCP）"一个名目下，触发条件写"出现 26.3 → 做补充包"，混淆了两个本质不同的机制。
2. 用户 2026-11-01 澄清：
   - **26.3 已发布**，但因 AG（转译层，F2）未完成，**暂不移植 26.3**；
   - **适配 26.3 = 单独出 26.3 加载器主版本**，不是"发布补充包"；
   - **补充包 = 补 mod 加载器（NeoForge/Fabric）的版本**（同主版本内的小修订）。
3. 核心担忧：若 neo 2.0 写法在 3.0 中不适配，转译"保留哪一套"会让 MG 若追求全兼容，开发累赘极高。

## 1. 两个独立机制（本次冻结的核心拆分）

| 机制 | 名称 | 解决什么 | 触发 | 是否向后兼容旧主版本写法 |
|---|---|---|---|---|
| **A. 主线加载器版本** | Mainline Loader Version（如 26.2 / 26.3 加载器） | 支撑一条新的 MC/Neo 主线 | 新 MC/Neo 主线出现 **且** AG(F2) 转译就绪 | 否（继承 D10 不向下兼容） |
| **B. 补充包** | MCP（Mirage Compat Pack，原 MVA/MCP 中的"包"部分） | 同主线内 mod 加载器（NeoForge/Fabric）的小修订 API 差异 | 同主线内出现 mod-loader 小修订缺口 | 只补同主版本，不跨主版本 |

> 旧文档把 A 的触发（"出现 26.3"）和 B 的实现（"第一个补充包"）绑在同一行，本次明确拆开：**26.3 适配走机制 A（新主线），与机制 B（MCP）无关。**

## 2. 机制 A：主线加载器版本

- 每个要支持的 MC/Neo 主线由**独立加载器版本**承载（26.2 是当前主线，26.3 将是下一条）。
- 只实现**它绑定的那一代 Neo API 面**，不内嵌旧主版本写法。
- 不向后兼容旧主版本写法（继承决策 **D10**）。
- **门禁（开发前置）**：① 该主线有可用 ModLoader 发行版；② **AG(F2) 转译能力就绪**（当前 F2 = IR 只解析不重放，未做，故主线 26.3 适配被门禁挡住）。
- 当前状态（2026-11-01）：26.3 **触发已发生（26.3 已出）**，但门禁②未过 → **暂不开启 26.3 主线适配**。

## 3. 机制 B：补充包 MCP

- 只处理**同一主线加载器版本内**、mod 加载器（NeoForge/Fabric）的**小修订 API 差异**（如 NeoForge 同主版本内的点版本新增/微调方法）。
- 不跨主版本、不跨 MC 主线。
- 一个 mod-loader 小修订区间一个包，可独立开发、测试、发布，**不装不加载**；运行时自动匹配当前加载器版本对应的补充包，其余待命（对齐 `MG-设计脉络` §二）。
- 当前状态：仅 26.2 一个主线、无 mod-loader 小修订缺口 → **MCP 不触发**。

## 4. "写法不适配"如何消解累赘（回应核心担忧）

- **每个主线只背自己那一代 API 面** → 累赘是**常数级**（每代维护自己那一代），不是叠加级。
- **跨主版本的写法差异**（如 neo 2.x 写法在 3.x 不适配）→ 由**出新的主线加载器版本（机制 A）**解决，而非在单版本里同时塞两套写法。旧 mod 跑对应旧主线版本，新版不背旧写法。
- **同主版本小修订差异** → 由 **MCP（机制 B）**补。
- **结论**：用版本边界隔离代替"单版本通吃跨主版本写法"，直接消解"全兼容累赘会很高"的担忧；与 D10、D2（MC 升级 mod 需重编译）一脉相承。

## 5. 与既有决策/代码的关系

- **D10（只支持 MC 26.2，不向下兼容）**：保留，本条设计冻结是其延伸。
- **`MG-设计脉络` §二**：原"主体只做最新稳定加载器版本，补充包一个旧版本区间一个包" → 本次对齐为：主体=机制 A 主线，补充包=机制 B MCP；措辞统一为"主版本/小修订"而非模糊"版本区间"。
- **§三 版本伪装**：`LoaderVersionMasquerade` + `VersionMasks` 是当前主线适配的**临时措施**（对 mod 报它声明期望的版本）；待机制 A+B 体系成熟后由主线 + MCP 取代，应在代码注释中标注其生命周期（见待办）。
- **§七 AG 按加载器版本区间拆分转译规则**：对齐机制 A——AG 的转译规则按主线版本拆分，独立开发测试发布。
- **转译现状（事实）**：AG 的转译（F2）目前 `IR 只解析不重放`（代码事实），MG 跑 Neo mod 是"直接加载 mod 字节码 + 提供 `net.neoforged.*` stub"，故"保留哪套写法"的压力当前不在转译层，而在 **stub 面（MG 提供哪一代 Neo API）**；该压力由机制 A 的"每主线只含一代 API 面"封顶。
