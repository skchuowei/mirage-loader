## 3. 决定：织入优先级（社区最大化）

用户裁定：**mod 织入与 MG 冲突时，放弃 MG 的织入**。这是明确的优先级决定，写进计划作为后续实现轮次的验收目标。

- **顺序**：`原版字节 → mod Mixin 织入 → MG 自研织入 → defineClass`（当前是反的，MG 先）。
- **冲突检测**：MG 自研 transformer 硬编码 7 个目标类（SharedConstants / LoadingOverlay / TitleScreen / Window /
  CreativeModeInventoryScreen / VanillaPackResourcesBuilder / CreativeModeTab）；mod Mixin 目标来自 `@Mixin` 注解。
  两者求交集，命中即跳过 MG 对该类的织入。
- **让路必须可观测**：跳过时打 WARN 说明"因 mod X 注入了类 Y，MG 的某功能已让路"，禁止无声放弃。
- **粒度**：先做类级交集（保守，不易误放行），验证后再细化到方法级。
- **例外清单**：早期窗口交接（`Window.createGlfwWindow`）让路会丢加载界面但**不影响 mod 兼容**，
  按社区最大化原则仍可让路；但若实机确认让路导致启动失败，加入不可让路黑名单并说明原因。

> 落地动作：单独的九节立项计划（下一轮写），含顺序颠倒 + 冲突检测纯函数 + 变异门禁 + 实机验证。

## 4. GitHub 源码调研：Sinytra/Connector（公开正面参照）

**仓库**：`Sinytra/Connector`（767 stars，默认分支 `26.2.x`，与本项目目标版本一致）。
纪要称它是"国标插座上加一个美标转换头"——相对 Forbrick 的"万能插座+铁丝"是**正面参照**。
我通过 GitHub 读取了 `transformer/src/main/java/org/sinytra/connector/transformer/**` 与 `src/**`，结论：

### 4.1 值得借鉴的三个机制（有源码证据）

1. **显式排序而非硬编码顺序**
   `api/TransformerRegistrar.java` 提供 `registerBefore/registerAfter` + `OrderingHint{EARLY,DEFAULT,LATE}`；
   `plugin/TransformerRegistrarImpl.java` 的 `getSortedTransformers()` 用 `MutableGraph` + `TopologicalSort.topologicalSort`，
   比较器 `ordering → name`。`PatchRegistrar` 另有 `HIGHEST=1000 … LOWEST=-1000` 优先级。
   → **对应我们的禁 4**：启动/织入顺序应是设计出来的拓扑序，不是试错时间表。

2. **目标精确匹配**
   `api/PatchRegistrar` 用 `targetClass`/`targetMethod`/`targetInjectionPoint` 限定作用范围；
   `transform/MixinPatchTransformer.isMixinClass()` 用 `invisibleAnnotations` 里的 `MixinAnnotations.MIXIN` 识别真正的 Mixin 类。
   → **对应我们的冲突检测**：先扫注解收集目标集，再求交集，不要笼统"全局优先级数字"。

3. **失败集中仲裁**
   `AuditTrail.getFailingMixins()` 收集失败；`locator/MixinTransformSafeguard.trigger()` 在 prelaunch 集中抛 `ModLoadingException`。
   → 我们可以借鉴"集中仲裁点"，但结论要反过来：**我们选择让路而不是崩溃**（因为是自研织入让路，不是 mod 让路）。

### 4.2 必须避开的坑（Connector 自己也踩）

- `jar/JarTransformInstance.transformJar()` 有 `silenceClasses(ignore)`——不在配置里的 Mixin 失败被**静默吞掉**；
- `MixinTransformSafeguard.prepare()` 里 `enableMixinSafeguard=false` 时只 `LOGGER.warn` 后忽略。

这两处正是我们的**禁 3**所禁止的。借鉴机制，不借鉴这两个开关。

### 4.3 没找到的源码

- 反面教材 **Forbrick / Forge Kernel**：GitHub 搜索无结果（很可能未公开，纪要说第一版从未正式发布）；
- **Kilt**、**ModLauncher** 本体：本次搜索工具未返回（refs 里只有集成侧代码，本体是外部依赖，版本固定在 settings.gradle）。
- 结论：**公开可读、且与本项目最相关的是 Connector**，已读；其余不必强求，refs 里的集成侧代码 + 纪要的实测结论已足够支撑决策。

## 6. 决定：Q1 判据是"全部兼容"的前置

用户要求"不允许能力边界"，但"兼容"必须可验收，否则无法判断目标是否达成。
沿用 AG 总计划 Q1 建议并钉死三级判据：

- **L1**：能启动、无 FATAL；
- **L2**：进世界、无 ERROR 日志；
- **L3**：mod 核心功能可观察（对应到我们的场景＝每个 mod 的关键日志标记出现）。

"全部兼容"的口径定义为 **L3**。这是后续所有门禁与实机矩阵的判据来源。
