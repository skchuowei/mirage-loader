# 织入优先级实现（原版字节 → mod Mixin → MG 自研织入 → defineClass）

> 关联：`docs/plans/2026-11-22_C决策复盘与计划补丁.md`（本计划的裁定来源）、`AGENTS.md` 技术注意事项 §16（禁 1 + 织入优先级）、
> 经验 `C109`（MixinExtras 时序）、`C93`/`C107`（启动判据：门禁可自跑，GUI 等用户命令）

## 目标

把 `MirageClassLoader.findClass` 的字节码管线从「MG 自研 ASM → mod Mixin」倒成
「**原版字节 → mod Mixin → MG 自研织入 → defineClass**」，并落实 AGENTS.md §16 的裁定：
MG 自研 transformer 的 7 个硬编码目标类与 mod `@Mixin` 目标类**按类求交集，命中即放弃 MG 对该类的织入**，
且必须以 WARN 说清「放弃了哪一项 MG 功能」——禁止无声放弃。

**可验证标准（done 怎么判）**：
1. `MirageClassLoader.findClass` 里 Mixin 调用行在 MG ASM 调用行**之前**（源码行序，门禁行首锚定断言）；
2. 纯函数 `WeavePriority.decide(className, modTargets)` 的判定表可离线单测：非 MG 目标 / MG 目标无冲突 / MG 目标有冲突 三态正确；
3. 冲突命中时：MG 该项织入不生效（可反射观测，`CreativeModeTab.builder()` 无参版本不出现）+ WARN 含类名与放弃的功能说明；
4. 无冲突时：MG 织入照旧生效（`CreativeModeTab.builder()` 无参版本存在）——零回归；
5. 新门禁 `scripts/verify_mixin_order.py` 守卫 + 行为 + 变异三层全绿，且落盘变异必须判红、字节级还原、编译路径自检、基线回绿；
6. 四个既有门禁（`verify_mixin_registry.ps1` / `verify_mod_mixin_config.ps1` / `verify_fakepack_w3_c.ps1` / `verify_w3c_c1_events.py`）仍全绿。

## 现状分析

**as-is（本轮改动前）**：`MirageClassLoader.findClass`（第 115~122 行）

```java
// 1) MG 自研 ASM transformer（调试 UI、资源命名空间、创造模式分页等硬编码织入）
byte[] transformed = transformer.transform(name, original);
// 2) SpongePowered Mixin 管线（mod 通过 @Inject/@Redirect 织入目标 MC 类）
transformed = io.mirage.mixin.MirageMixinBootstrap.transform(name, transformed);
```

**为什么必须改**：mod 的 `@Mixin` 是基于**原版字节码**写的（注入点由 `@At(INVOKE/FIELD)` 之类精确定位）。
MG 先改过字节码后再交给 Mixin，等于让 mod 面对一份被改造过的字节码：注入点可能失配、可能拿到错位的
局部变量表/栈映射帧，甚至抛 `MixinTransformerError`。`AGENTS.md` §9 早就记着
「`SharedConstants` 在 ASM 注入后交给 Mixin 时转换失败」，正是这个顺序的直接后果；§3 也写了
「两条路径不要同时改同一个 MC 目标类」。§16 的禁 1（禁止合并/改造游戏本体字节码）把这条升级为硬禁令。

**MG 自研 transformer 的 7 个硬编码目标类**（`MirageTransformer.transform` 的 if 链，逐条核对）：

| 目标类 | MG 织入做什么 | 备注 |
|---|---|---|
| `net.minecraft.SharedConstants` | `tryDetectVersion()` 头插版本日志 | M3 验证遗留 |
| `net.minecraft.client.gui.screens.LoadingOverlay` | `extractRenderState` RETURN 前画 Forge 式遮罩 | 只能用 fill/像素字 |
| `net.minecraft.client.gui.screens.TitleScreen` | `init` / `extractRenderState` / `mouseClicked` 三处 | 含 ExitDissolve 收尾 |
| `com.mojang.blaze3d.platform.Window` | `createGlfwWindow` 交接 + `close` 销毁改道 | 谁创建谁销毁 |
| `net.minecraft.client.gui.screens.inventory.CreativeModeInventoryScreen` | 创造栏标签分页 | **当前空实现**（直接 `return original`） |
| `net.minecraft.server.packs.VanillaPackResourcesBuilder` | `build()` 头插 mod 命名空间挂载 | 资源层 |
| `net.minecraft.world.item.CreativeModeTab` | 追加无参 `builder()` 兼容方法 | NeoForge 语义补齐 |

**mod 侧目标类怎么得到（本轮的技术难点）**：Mixin 的「目标」写在 mixin 类上的
`@org.spongepowered.asm.mixin.Mixin`（`value` = `Class[]`，`targets` = `String[]`，Retention = CLASS），
mixin config 的 `mixins`/`client`/`server` 数组给的是 **mixin 类**（相对 `package`）。
所以链路是：config 资源 → gson 解析出 mixin 类名 → 用 MCL 读该 mixin 类的字节码 →
ASM 读 `@Mixin` 注解 → 目标类名集合。这些都在 `MirageMixinBootstrap.init` 已具备的条件下可得
（`mcl` + `configs` 都在入参里），**不需要改 `TransformStage`**。

**边界与坑（写死在实现里）**：
- `mirage.mixins.json` 是 **MG 自己的** mixin 配置，必须排除在「mod 目标集合」之外——否则 MG 自己的
  `CreativeModeInventoryScreenMixin` 会把 `CreativeModeInventoryScreen` 判成冲突，MG 的 MiXin 与 ASM
  互相让路，逻辑自噬。
- 只做**类级**交集（用户明示「先做类级交集，不过度设计」）；方法级留待后续验证后再细化。
- 收集失败一律降级（WARN + 空集 ⇒ 不做让路、保持老行为），绝不让收集阶段把启动搞崩——这与
  §16 禁 3「禁止静默跳过失败的 Mixin」不冲突：让路是**显式裁定 + WARN**，收集失败是**观测能力降级**。

## 每处改动要点

### 1. `WeavePriority`（新，纯逻辑）

- `MG_TARGETS`：`LinkedHashMap<String,String>`，键=类名（点分），值=该织入做什么（WARN 用白话），
  `Collections.unmodifiableMap` 包一层；顺序即 WARN/日志顺序。
- 静态快照：`private static volatile Set<String> modMixinTargets = Set.of();`，
  `setModMixinTargets(Collection)` 拷贝成不可变 `LinkedHashSet`（防御调用方后续改集合）。
- `decide(String className)` = `decide(className, modMixinTargets)`；
  `decide(String className, Set<String> modTargets)` 为纯函数（**可离线单测，不碰静态态**）：
  - 非 MG 目标 → `applyMgWeaving = true`，`reason = "not-mg-target"`；
  - MG 目标且 mod 无交集 → `true`，`reason = "mg-target"`；
  - MG 目标且 mod 命中 → `false`，`reason = "mod-mixin-conflict"`，`purpose` 取 `MG_TARGETS` 的值。
  - 入参 `modTargets` 为 `null` 视作空集（收集失败降级路径）。
- `conflicts()`：按 `MG_TARGETS` 顺序返回交集列表（给 `init` 的阶段日志用）。
- `Decision.describe()`：`[织入优先级] 让路：<类名> 已被 mod @Mixin 命中（社区最大化裁定），放弃 MG 自研织入「<功能>」——该项 MG 功能本次启动不生效`
  —— WARN 文案在类里生成，`MirageClassLoader` 只负责 `MirageLog.warn(d.describe())`，便于门禁直接断言文案要素。

### 2. `ModMixinTargets`（新，纯逻辑 + 资源接缝）

- `public static Set<String> collect(ClassLoader mcl, Iterable<String> configs)` → 委派到
  `collect(Function<String,byte[]> resources, Iterable<String> configs)`（**接缝**：门禁用内存资源喂它，不必造 jar）。
- 跳过 `MG_OWN_CONFIG = "mirage.mixins.json"`（含注释说明「MG 自己的 mixin 不算 mod，否则逻辑自噬」）。
- `mixinClassNames(String json)`：gson `JsonParser` 解析；取 `package`（可缺）+ `mixins`/`client`/`server`
  三个数组的字符串项；`package` 非空且名字未带包前缀时补前缀；`/`→`.`。JSON 坏掉 → 抛给上层 WARN 降级。
- `targetsOf(byte[] mixinClassBytes)`：ASM `ClassReader` + `ClassVisitor.visitAnnotation`，
  desc 命中 `Lorg/spongepowered/asm/mixin/Mixin;` 时读 `value`（`Type[]` → internal name → 点分）
  与 `targets`（`String[]` 原样，`/`→`.`）；注解为 `RetentionPolicy.CLASS`（RuntimeInvisible），
  `visitAnnotation` 对不可见注解同样回调，故用 `visible` 无关的方式读取。
- 每个 mixin 类读不到字节 / 解析抛错 → 单条 WARN 后继续（不中断整轮收集）。

### 3. `MirageMixinBootstrap.init`

- 现有 config 注册循环加一句 `cfgList.add(c)`（保留 `Iterable` 单次语义，后面还要用这份清单）。
- 循环之后、`initialized = true` 之前插入收集块：
  ```java
  try {
      Set<String> targets = ModMixinTargets.collect(mcl, cfgList);
      WeavePriority.setModMixinTargets(targets);
      // INFO: mod 目标 N 个 / 与 MG 硬编码目标冲突 M 处 -> [类名...]
  } catch (Throwable t) {
      MirageLog.MIXIN.warn("收集 mod @Mixin 目标类失败（MG 自研织入不做让路判定，保持老行为）", t);
  }
  ```
- 时序：必须在 config 注册之后（config 资源此时才保证可达）、在类加载开始之前（`init` 整体就在 S3，早于 S4/S7 的类加载）。

### 4. `MirageClassLoader.findClass`

```java
// 1) mod Mixin 先跑：mod 必须面对原版字节码（AGENTS §16 织入优先级 / 禁 1）
byte[] transformed = io.mirage.mixin.MirageMixinBootstrap.transform(name, original);
// 2) MG 自研 ASM 后跑；与 mod @Mixin 目标类冲突时让路（社区最大化）
io.mirage.mixin.WeavePriority.Decision weave = io.mirage.mixin.WeavePriority.decide(name);
if (weave.applyMgWeaving) {
    transformed = transformer.transform(name, transformed);
} else {
    MirageLog.MIRAGE.warn(weave.describe());
}
```
- `readClassBytes == null` 两条降级分支（`MissingNeoTracker` / `RuntimeFakePack`）与 `LoadProgress.increment` 原位不动。
- 新增 `import io.mirage.api.log.MirageLog;`（mirage-loader 已 `api` 依赖 mirage-api，无构建改动）。

## 回归测试影响面

**可能被打破的旧行为**：
1. **`SharedConstants`** — 之前是「ASM 先、Mixin 后」且已知会转换失败（§9）。改成 Mixin 先之后，
   MG 自己的 `MirageTestMixin` 面对原版字节，理论上从「转译失败退原字节」变成「正常织入」。
   ⇒ 这是修复方向，但属于**行为变化**：实机应能看到 `[Mirage] mixin applied`（ASM 那行）。
   风险：`mirage.mixins.json` 的 `defaultRequire: 1` 与新增顺序组合若出现注入失败，会按 FATAL 铁律崩——
   这比静默更可接受，且由实机验收暴露。
2. **`CreativeModeInventoryScreen`** — MG 的 `Mixin`（`CreativeModeInventoryScreenMixin`）先跑，ASM 后跑
   （ASM 对该类本来就是空实现），顺序变化无副作用。注意 `mirage.mixins.json` 必须被排除，否则该类会被
   误判冲突、MG MiXin 还在织入 —— 逻辑不一致。
3. **`TitleScreen` / `LoadingOverlay`** — MG 只有 ASM，不受顺序影响（Mixin 管线处理它们时无 mod mixin 参与）。
   但**一旦有 mod 织入这两个类，MG 的 HUD/遮罩会整体让路**（用户已裁定，WARN 可见）。这是本轮最大的
   「功能可见性」变化，必须靠 WARN 与真机验收确认可接受。
4. **`Window`** — 同上：mod 织入 Window 会导致早期窗口交接/销毁改道放弃 ⇒ 早期界面可能不交接
   （退回原版窗口）。WARN 必须点名，实机需要看一次（留用户拍板）。
5. **性能** — 每个类多一次 map 查找 + set 查问，可忽略。

**新门禁**：`scripts/verify_mixin_order.py`（守卫 + 行为 + 变异）。**不改**任何一个既有门禁脚本。
`verify_mod_mixin_config.ps1` 对 `ModMixinConfigs.java` / `TransformStage.java` 有源码守卫，本轮不动这两个文件；
`verify_mixin_registry.ps1` 的「每个 `*Mixin.java` 都必须注册」glob 不匹配 `WeavePriority.java` / `ModMixinTargets.java`（名字不以 `Mixin` 结尾），无假红风险。

**零侵入**：`modules/**`（兼容层）、`api/**`、`launcher/**`、`mdk/**`、`mc-shili/**`。mdk-example 冒烟步骤不变。
