## 0. 需求复核：三处必须修正的口径（规则 1）

用户需求原文：把 MSR 从进程内沙箱升级为进程级沙箱——每个 mod 一个独立 JVM，`kill -9` 硬超时，
overlay 文件系统隔离，网络隔离，IPC 回传录制数据；目标「全部 mod 兼容、不允许能力边界」。

按规则 1，动手前先把三处不一致摆出来，本计划按「修正后口径」写，不按字面写。

### 0.1 决策冲突：roadmap 明确否决过 MSJ

`docs/plans/2026-10-25_msr-roadmap.md` 末行原文：

> 6. MSJ（每 mod 一 JVM）维持否决：冷启动线性成本；P3 是批量实例，不是每 mod 一 JVM。

**处置（只标不删）**：在该行追加 `【已过时·2026-11-22】`，理由写清——当时的否决前提是
「MSR 只是轻量预检器，能省一次冷启动就省」；现在前提变了三处：

1. 用户已钉死「不允许能力边界」，而进程内的四条限制（exit 绕过 / `catch(Throwable)` 吞信号 /
   自旋残留 / 副作用无隔离）**在进程内没有解**，不是成本问题而是可行性问题；
2. 成本不再线性失控：`RecordingPolicy`（P2 已落地）让绝大多数 mod **一次都不录**，实际只有
   「缺版本区间 / `force` / 首次遇到」的少量 mod 进 worker；
3. 隔离是**硬需求**，不能用「省一次冷启动」去换——进程内残留一个自旋线程，代价是整个
   launcher 挂死，比冷启动贵得多。

同时要钉清 **MSJ 与 P3 不是替代关系**：P3 是「批量把整库录成行为级 MID-B」的构建期工具
（一次性实例、带真 NeoForge 客户端）；MSJ 是「用户机器上按需隔离单个 mod 的需求发现」。
两者共享进程管理经验，产物格式也需要对齐（见 §5.3），但**互不取代**。

### 0.2 字面需求里有两项兑现不了，必须先改正

用户列的五项能力，四项可兑现，一项要拆开说：

| 需求原文 | 可兑现性 | 修正后口径 |
|---|---|---|
| 每 mod 一个独立 JVM | 可兑现 | 保留。worker 只跑 mod 构造，**不启动 MC**（不是 P3） |
| `kill -9` 硬超时 | 可兑现 | 保留。Windows 侧等价物是 `TerminateProcess`（`Process.destroyForcibly()`） |
| overlay 文件系统隔离 | **部分可兑现** | 真 union mount 在 Windows 需管理员或三方驱动 ⇒ 明确不做。改为「一次性沙盒根 + `cwd` + `-Duser.home` + `-Djava.io.tmpdir` 启动期注入 + 绝对路径写入**检测**」 |
| 网络隔离 | **部分可兑现** | JDK 24 起 `SecurityManager` 永久禁用（JEP 486，`System.setSecurityManager` 抛 UOE）⇒ 无法用官方沙箱机制。改为「`java.net.*` / DNS 改道拒绝 + JNI 直连标 `unknown` 不假装拦住」 |
| IPC 回传录制数据 | 可兑现 | 保留，但**不用 socket**：用「原子写结果文件（权威源）+ stdout 行协议（诊断源）」。理由见 §5.3 |

这两项的残余风险不藏起来：**本方案承诺的是「宿主不被污染」（isolation），不是「mod 行为被物理阻止」
（containment）**。无管理员权限的 Windows 上，绝对路径写入与 native 网络调用只能检测、不能禁止。
这条边界必须写进 `docs/已知bug.md`（实现轮做，本轮不改台账）。

### 0.3 目标归因：MSJ 不会提高兼容率

用户总目标是「全部兼容」，兼容上限 = 需求发现(MSR) × API 语义实现 × Mixin 注入兼容。
**MSJ 只作用于第一项**，它提高的是「发现数据的可信度与覆盖面」，不提高「真实加载时这个 mod 能不能跑」。
换句话说：MSJ 让 `touched_apis` / `failed` 不再被「沙盒自己被 mod 搞死」污染，从而让
「该补哪个 fake / 该实现哪个语义」的判断更可靠；**但补 fake 与实现语义仍是别的计划的事**。

而且进程级**不解决语义保真度**：worker 里仍然是 fake 表面 + clean-room stub，沙盒里跑通
≠ 真实加载跑通（C108 的教训：`FMLLoader.getDist()` 缺失导致 JEI 早期中断，那是语义缺口不是隔离问题）。
把这条写明，是为了防止后续把「MSJ 上线」误当「兼容性提升」汇报。

## 3. 现状分析

### 3.1 现在的 MSR 是怎么跑的

`ModDiscoverer` 在逐 jar 的发现循环里内联调 `SandboxRecorder.record(jar, detected)`：
进程内起一次性 `SandboxClassLoader` → `Class.forName(mainClass, true, cl)` + 构造 →
`join(2000)` → 超时 `interrupt` → 结果写 `MidCache`。整条链路**没有进程边界**。

### 3.2 四条已知限制的机理（为什么进程内注定解不了）

不是「实现得不够好」，是四条各自撞在不同的 Java 语言/平台硬墙上：

**（a）`System.exit` 经方法引用 / 反射绕过。**
进程内的防线是 `SandboxBytecodeGuard` 在 `findClass` 里枚举并改写调用点。但可调用的面是开放集合：
`invokedynamic`（`Runtime.getRuntime()::halt`）、`MethodHandle`、`Method.invoke`、JNI 里 `call_static`、
以及未来新增的 API。**枚举式防线在原理上不可能闭合**，只能提高命中率。
进程边界的完备性则由 OS 提供，**与 mod 用什么方式调用 exit 无关**——把「完备性」这个不可能任务
从我们的代码转移到操作系统，这是本方案最根本的收益。

**（b）`catch(Throwable)` 吞掉杀进程信号。**
`SandboxKillException` 继承 `Error` 只是为了躲过 `catch(Exception)`；`Throwable` 是 catch 的
最外层，**Java 语义保证它能拦下一切**。进程内凡是用「Java 异常」当杀信号，就必然要经过 mod 的
catch 层级。OS 的 `TerminateProcess` / `SIGKILL` 根本不进入 Java 异常表 ⇒ mod 无从 catch。
载体换了，问题才消失。

**（c）超时只 `interrupt`，纯 CPU 自旋残留。**
Java 语言层已无强制终止原语：`Thread.stop()` 在 JDK 20 起抛 `UnsupportedOperationException`，
`interrupt` 是**协作式**的（mod 不检查中断标志就无效），daemon 线程只能等进程结束。
⇒ 想要硬上界，只能借 OS 的强制终止。这条没有任何进程内替代品。

**（d）文件 / 网络副作用无法隔离。**
进程内**没有任何合法的进程级隔离原语**，四条全是坏消息：
`cwd` 没有 Java API 可改（`user.dir` 改了只影响部分路径解析，库多处已缓存）；
`java.io.tmpdir` 在 JVM 启动时被 `File` 静态缓存，之后改属性无效；
`user.home` 是全局属性，改了会污染宿主自己；
`SecurityManager` 自 JDK 24 起永久禁用（JEP 486）。
关键洞察：**隔离原语的生效时机是「被隔离者启动之前」**（cwd、`-D` 系统属性都只在启动时读一次）。
进程内方案永远错过了那个时机，只剩「启动之后再挽救」，而挽救手段已被 JDK 清理干净。

## 5. 每处改动要点

### 5.1 四条缺陷的逐条攻克（与 §3.2 一一对应）

| 缺陷 | 进程级怎么解 | 为什么进程内解不了（一句话） | 残余风险与处置 |
|---|---|---|---|
| exit 绕过 | 不改写也要不了命：exit 只杀 worker，宿主只看退出码 | 枚举式防线不闭合（`invokedynamic`/反射/JNI） | 无。`SandboxBytecodeGuard` 保留只为把 `failed=exit(code)` 记清楚（**数据质量**收益，非安全收益） |
| `catch(Throwable)` 吞信号 | 杀信号是 OS 原语，不进 Java 异常表 | 「Java 异常」必然经过 mod 的 catch 层级 | 超时硬杀会丢数据 ⇒ 靠 200 ms 周期快照 + 宿主盖章（§5.1.1） |
| 自旋超时残留 | `destroyForcibly()`（Windows=`TerminateProcess`） | JDK 20 起无 `Thread.stop`，`interrupt` 是协作式 | 孙进程：worker 内 `exec` 改道 + 宿主 `taskkill /T /F` 兜底（§5.2.3） |
| 文件/网络副作用 | `cwd` + `-Duser.home`/`-Djava.io.tmpdir` **启动期**注入 | 隔离原语只在启动前生效，进程内已错过时机 | 绝对路径写入 / JNI 网络：只检测不改写，标 `unknown` |

#### 5.1.1 硬超时与「数据不丢」的竞态（本条是进程级方案最容易做砸的地方）

硬杀会**同时杀死「正在写结果的代码」**。若只做「超时 → kill → 读文件」，超时 mod 会连
`touched_apis` 一起丢光，数据质量反而比进程内更差。因此定三条规矩：

1. **子进程侧周期快照**：`ProcessSink` 每次 sink 变更后 200 ms 节流原子写 `snapshot.json`
   （`.json.tmp` → `ATOMIC_MOVE`，与 `MidCache.writeAtomic` 同形态）。P3 的 `RecorderAgent`
   已有同款 ticker，经验直接搬。
2. **宿主侧盖章**：`failed=true` / `incomplete=true` / `error="timeout"` 由**宿主**写入，
   不依赖子进程「死前写一句话」。宿主读到的是最后一次成功解析的快照，能读到多少算多少。
3. **「半成品不入库」不变**：`incomplete=true` ⇒ `touched_apis` 清空 + `cache.store(jar, neo, null)`
   （`ModDiscoverer` 现有分支原样保留），下次启动重录。宁可没数据，也不要把半截数据固化进缓存
   （P1 定的规矩，进程级更该守）。

#### 5.1.2 网络隔离的诚实边界

`java.net.Socket` / `ServerSocket` / `SocketChannel` / `DatagramSocket` 的连接入口 + `InetAddress.getByName`
（防 DNS 泄露）在 worker 内改道：记录一条 `netEvents{target, phase, result:"blocked"}` 然后抛。
**不承诺**：`JNI` 直连、`libcurl`、mod 自带 native 库——这些记 `result:"unknown"`，
门禁 V4 明确断言「JNI 路径必须记 unknown，不许记 blocked」，防止用假数据充数。

关键认知：**改道不完美在进程级是可接受的**。进程内的不完美拦截 = 宿主中毒；进程级的不完美拦截
= 这一次录制数据不可信、丢掉重录即可。拦截完备性从「正确性问题」降级为「数据质量问题」，
这是本方案能落地的真正原因。

### 5.2 独立 JVM 的启动协议

#### 5.2.1 命令行（宿主 → 子）

```
<java> -XX:TieredStopAtLevel=1 [-XX:AOTCache=<path> | -Xshare:auto]
       -Duser.home=<sbx>/home
       -Djava.io.tmpdir=<sbx>/tmp
       -Dmirage.msr.worker.id=<modId>
       -Dmirage.msr.worker.result=<sbx>/result.json
       -Dmirage.msr.net=block|record|allow
       [-Dmirage.msr.fakepack=<dir>]              # 透传 P4 外部 pack（可选）
       -Dfile.encoding=UTF-8
       -cp <fat-jar>
       io.mirage.loader.sandbox.worker.WorkerMain
       --jar <mod.jar> --main <fqcn> --mod-id <id> --spec 0.4 --timeout-ms <n>
```

三条硬约束（写错就白做）：

1. **mod jar 绝不进 `-cp`**。只通过 `SandboxClassLoader` 的 URL 挂载。进了 `-cp`，父优先会先定义
   mod 类，绕过 fake 表面与字节码改道——「直接 `java -cp mod.jar Main`」恰恰是要避免的形态。
2. **worker 代码进 fat jar**（与 P3 agent 相反）。P3 是构建期工具（`javaagent`，明确不进 fat jar）；
   worker 是**运行时按需组件**，用户机器上只有 fat jar 可用。它不进 MC 的类加载路径，只被
   `java -cp` 拉起的子进程使用，因此不会污染主线。
3. **`-D` 必须在启动时给全**。`java.io.tmpdir` 被 `File` 静态缓存、`user.dir` 改不动，
   任何「先启动再改属性」的做法都无效（§3.2(d)）。

#### 5.2.2 退出码表（唯一来源 `WorkerProtocol`）

| 退出码 | 含义 | 宿主处置 |
|---|---|---|
| 0 | 构造走完（无论 `failed` 与否，`failed` 看 `recorded`） | 正常入库 |
| 3 | 构造抛异常（`ctor_failed` / `missing_fake` / `stub_incomplete`） | 正常入库（分类看 `error` 前缀） |
| 4 | worker 内部错误（基建：fake 读不到、沙盒根建不出） | 记 `engine_error`，**不入库**，下次重试 |
| 5 | 参数 / 协议错误 | 记 `[MG-FATAL]` 级日志（我们自己写错了，不许静默） |
| 其他 / `killed=true` | 被外部杀（含超时硬杀、用户 Ctrl-C、OOM killer） | `incomplete=true` 盖章 → 不入库 |

#### 5.2.3 进程树与残留

`destroyForcibly()` 只杀直接子进程，**不杀孙进程**。三层处置：
① worker 内把 `Runtime.exec` / `ProcessBuilder.start` 改道为「记录 + 抛」（绝大多数 mod 不会用到）；
② 宿主超时后追加 `taskkill /T /F /PID <pid>`（Windows）/ `kill -9 -<pgid>`（POSIX）兜底；
③ 两者都失败时，把 pid 写进 `worker.orphanPids` 并 WARN，下一轮启动前清理检查。
如实标注：native `fork` 拦不住，属 §0.2 的 containment 边界。

### 5.3 通信协议与格式兼容（本节是「能不能不返工」的关键）

#### 5.3.1 两条通道，一条权威

| 通道 | 载体 | 权威性 | 用途 |
|---|---|---|---|
| 结果文件 | `<sbx>/result.json`（原子写；超时场景读 `snapshot.json`） | **唯一权威** | 入库数据 |
| 行协议 | 子进程 stdout，`@@MSR@@ {"t":"ready"\|"touch"\|"event"\|"error"\|"done",...}` 单行 JSON | 仅诊断 | 进度、超时定位、日志 |

**为什么不用 socket / 不用 IPC 框架**：① 硬杀场景下 socket 里的在途数据一起没，文件才是唯一
可靠载体；② Windows 上开监听端口会触发防火墙弹窗——**那是抢用户桌面的行为**，违反 C93 的
「不打扰用户」判据；③ 行协议足够做进度，不需要引入依赖。若将来真要实时流，走父子 stdin/stdout
双向管道，**不开 TCP**。

#### 5.3.2 `result.json` schema

```json
{
  "schema": "mirage.msr.worker.result/1",
  "worker": {
    "pid": 12345, "engine": "process", "javaVersion": "25.0.4",
    "startedAt": 0, "wallMs": 0, "exitCode": 0, "killed": false,
    "modId": "example", "jarSha256": "...", "mainClass": "a.b.C",
    "fsEvents": [{"path":"config/x.toml","op":"write","abs":false}],
    "netEvents": [{"target":"127.0.0.1:25565","result":"blocked"}],
    "execAttempts": ["cmdline"], "orphanPids": []
  },
  "recorded": {
    "recorded_loader_version": "[26.1.0.1-beta,)",
    "recorded_mc_version": "[26.1,27)",
    "touched_apis": [], "registered_events": [],
    "deferred_register_count": 0, "record_duration_ms": 0,
    "failed": false, "error": null, "incomplete": false,
    "source": "sandbox", "complete": true
  }
}
```

**兼容性设计（三条，缺一条就会返工）**：

1. `recorded` 是 `MidCache.Recorded` 的**逐字段镜像**（字段名、语义、可空性全部一致）⇒ 宿主用
   现成 Gson 直接反序列化成 `MidCache.Recorded`，`MidCache.store(jar, detected, recorded)` 原样可用，
   **零转换代码 = 零漂移**。
2. 新增信息全部放在 `worker` 子对象里。Gson 忽略未知字段 ⇒ 老读取方（含任何只看 `recorded` 的脚本）
   不会因为新字段而炸。
3. `error` 字符串必须沿用进程内形态：`<kind>: <SimpleName>: <message> <- <cause>`，其中
   `<kind> ∈ {missing_fake, stub_incomplete, ctor_failed}`。**这是被下游正则消费的格式契约**——
   `FakeGenCli.extractMissingFromMid` 的正则是
   `missing_fake:\s*(?:NoClassDefFoundError|ClassNotFoundException):\s*(\S+)`。
   保证方式不是「照着写一遍」，而是 §4 里的 `SandboxFailure` 纯函数**两路共用同一份实现**，
   让漂移在结构上不可能发生。

#### 5.3.3 关于 `--only-file` / `--from-mid` 的结论

**零改动**。`--only-file` 读的是「每行一个类名」的白名单文本，与录制方无关；
`--from-mid` 只依赖 `recorded.error` 的字符串形态（上一条已守住）。因此：
`worker 录制 → .mid-cache → FakeGenCli --from-mid → 生成 fake pack → 再录制` 这条闭环
不需要改一行生成器代码。V5 判据就是钉这一条。

#### 5.3.4 为什么不升 `SPEC_VERSION`

`SPEC_VERSION` 是「字段语义变了就整体作废」的开关，升 0.5 会让**整库 `recorded` 一次性重录**
（已知成本：N × 一次录制）。本计划的 `Recorded` 字段语义**一个都没变**，新增的只是
`Entry.recorderEngine`（条目级，不是载荷级）⇒ 不升版是正确的。

但必须补一条校对：`recorderEngine` 与当前 engine 不一致时**视为未命中**。理由：进程内录制出来的
`failed/incomplete` 结论与进程级不可互认（一个是「沙盒被 mod 搞死」，一个是「宿主动不了」），
混用会让 V6 对账变成假绿。老条目缺该字段 ⇒ 按 `inproc` 处理。

代价要说清：从 inproc 切到 process 那一次启动会**全库重录一次**。灰度期用
`-Dmirage.mid.cache=<独立目录>` 隔离对账，不污染用户既有缓存。

### 5.4 隔离实现（可兑现的口径）

沙盒根布局（每次录制一个，跑完按 `-Dmirage.msr.keepOverlay` 决定删除/保留）：

```
<TEMP>/mirage-msr/<modId>-<pid>-<nanos>/
├── work/      ← ProcessBuilder.directory(work/)，相对路径全落这里
├── home/      ← -Duser.home
├── tmp/       ← -Djava.io.tmpdir
├── result.json / snapshot.json
└── fs-baseline.txt / fs-after.txt   ← 跑前跑后树快照（sha+size），diff 出 fsEvents
```

| 面 | 手段 | 强度 | 残余风险 |
|---|---|---|---|
| 相对路径写入 | `cwd` = `work/` | 强 | 少数库缓存了启动时 cwd |
| `user.home` / 临时文件 | 启动期 `-D` | 强 | 启动后再改无效（已知，不需要） |
| 绝对路径写入 | 前后快照 diff **检测** | 中 | 拦不住；`fsEvents` 标 `abs:true` 如实记录 |
| 子进程 | `exec` 改道 + 进程树 kill | 中强 | native fork 拦不住 |
| 网络 | `java.net.*` 改道 | 中 | JNI 直连记 `unknown` |

`fsEvents` 不只是隔离证据，它还是**需求发现数据**：mod 想写哪些配置文件、写到哪，
本来就是兼容层需要知道的信息（P2 的 `PassiveRecorder` 看不到这些）。

### 5.5 与现有 MSR P0–P4 资产的关系（只标不删）

**复用（不动或极小改动）**：

| 资产 | 复用方式 |
|---|---|
| P0 `SandboxClassLoader` + fake 表面 + `mirage/sandbox-fake/` | 整体搬进 worker，parent 换成 worker 的 app loader（fat jar） |

| 资产 | 处置 | 理由 |
|---|---|---|

| `SandboxRecorder.StateSnapshot`（Locale/TimeZone/属性恢复） | 【已过时】进程级无必要（进程要死）；inproc 路径保留 | 隔离边界取代了状态复原 |

| roadmap「MSJ 维持否决」 | 【已过时·2026-11-22】见 §0.1 | 前提变了 |
| `SandboxRecorder` 的类注释「必须由 P3 一次性实例消化」 | 【已过时】改为指向本文件 | 当时的结论已被本方案取代 |

### 5.6 触发、并发与两阶段化

`ModDiscoverer` 现在是「发现一个 jar → 就地录一个」，进程级会更慢且不可并行。改为三阶段：

1. **收集**：走完 `NeoForgeModDetector`（静态 ASM，仍在宿主进程内，不进 worker），
   用 `RecordingPolicy.decide` 收集待录清单（含 `Detected`）。
2. **并发执行**：`ProcessRecorder` 池，默认并发 `min(2, cores)`，上限 4（可 `-D` 调）。
   墙壁时间上界从「N × 无上界」变成 `ceil(N/并行度) × (worker 冷启动 + timeout)`。
3. **汇总落盘**：按 jar 写回 `MidCache`，日志保持现有 `[Sandbox]` 前缀与措辞（避免旧门禁失配）。

**熔断**：连续 3 个 worker 以 `engine_error` / 超时结束 ⇒ 本批次降级回 inproc 并发 WARN 记账
（不静默、不无限重试）。

## 9. 回滚方案

三层，任一层单独可用：

1. **运行期开关（最快，秒级）**：`-Dmirage.msr.engine=inproc` 立即回到今日行为。
   默认值在 M1–M4 全程保持 `inproc`，M5 才考虑切换——**「默认不变」本身就是回滚方案**。
2. **提交级**：M1–M5 每期独立 commit，`git revert <M_n>` 只摘掉当期。
   `MidCache` 新增字段向后兼容（缺失按 `inproc`）⇒ 回滚**不需要清缓存**，
   这是刻意不做 `SPEC_VERSION` 升版换来的好处（§5.3.4）。
3. **文件级**：实现轮动工前给 `SandboxRecorder.java` / `ModDiscoverer.java` / `MidCache.java`
   各留 `.bak-<date>-msj` 副本（项目既有惯例），回滚后按规则 6 写
   `docs/回退报告_<日期>_MSR进程级沙箱.md`，说明回退范围与保留部分。

**回滚后要保留的**：`SandboxFailure` 纯函数抽取（行为等价、无风险）、门禁脚本与夹具
（下次重启时直接可用）、`fsEvents` 采集（独立价值）。

## 10. 性能代价与缓解

### 10.1 代价的定性结构

进程内：`N_needing × (≤2000 ms 熔断 + 自旋残留的**无上界**风险)`。
进程级：`ceil(N_needing / 并行度) × (T_cold + T_run ≤ timeout)`，**上界确定**。

最关键的差别不是「谁更快」，而是「**最坏情况有没有上界**」。进程内一个自旋 mod 能把整个
launcher 拖到用户强杀；进程级最坏就是多花一个 timeout。

### 10.2 可查的事实与待测的空白（不编数字）

| 项 | 状态 |
|---|---|
| P3 一次性客户端冷启动 10–30 s | 已有实测（roadmap 原文），但**含 MC 客户端**，不能直接套到 worker |
| 进程内 fake pass 上限 2000 ms/个 | 事实（`SandboxRecorder.TIMEOUT_MS`） |
| fat jar 3 835 633 B / 2 897 entries | 事实（C109 对账值） |
| **worker 冷启动 `T_cold`** | **未知，M0 必须实测**（空 worker ready 的时间） |
| **worker 跑一个夹具 `T_full`** | **未知，M0 必须实测**（含 fake 表面扫描 + 构造） |
| 并发 1/2/4 的墙壁时间 | 未知，M0 实测 |

**设计预算（判据，不是实测值）**：`T_cold ≤ 800 ms`。若 M0 实测超出，则必须先启用 AOT/CDS 档，
否则本方案在「首启遇到 20 个新 mod」场景下不划算，需重新评估默认并行度与 timeout。
按 C104 的规矩，**预算值写进计划，实测值回填，绝不拿绝对值当门禁阈值**。

### 10.3 缓解手段（按收益排序）

1. **按需触发（已有，收益最大）**：`RecordingPolicy` 让区间完整的 mod 一次都不录 ⇒ 日常启动
   **0 个 worker**。这是本方案能成立的前提，不是补充。
2. **静态识别留在宿主**：`NeoForgeModDetector` 的 ASM 扫描不进 worker，只有「行为录制」才付进程费。
3. **并发池**：默认 `min(2, cores)`，上限 4。并发放大的收益随 `N_needing` 增长，`N=1` 时无用。
4. **AOT/CDS 归档**：JDK 25 的 AOT 类加载/链接可预烘 `-cp fat-jar` 的类索引成本。
   具体开关与收益以 M0 实测选定，**失败自动回落无归档档**（不许让归档缺失变成启动失败）。
5. **熔断降级**：连续 3 次 `engine_error`/超时 ⇒ 本批切回 inproc（宁可数据差一点，不要卡死启动）。
6. **结果永久复用**：录一次进 `.mid-cache`，之后 N 次启动都是 0 成本（已有机制）。
7. **不进日常路径**：与 P3 同一原则——录制是**代价换可信度**的按需动作，不是每次启动的固定税。
