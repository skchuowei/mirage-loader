## 目标

把加载界面从「一根假百分比条 + 7 行静态阶段表 + 只有 Mirage 自己日志的面板」，改成**一台能回答"现在在干什么、干到哪、卡了多久"的仪表盘**：

1. **多根互相独立的进度条**（每根 = 一个正在跑的任务），能确定分母的画真实比例，**拿不到分母的画"不定进度游标"而不是编一个百分比**；
2. **详情计数区**（mods / mixin / 注册表 / DeferredRegister / 失败数 / 耗时），数字全部来自真实计数器；
3. **事件流**（不是"日志尾巴"）：阶段进出、每 N 个 mod、每条失败都成事件，长等待期间屏幕不会静止。

**可验证标准（done 的判据）**
- D1：任一次启动的截图里，**不存在"百分比长时间不变"的静态假进度**——只要数字不动，那根条必须是在走游标的不定条；
- D2：每根条的 label 都能读出"在干什么 + 分子/分母（或已用秒数）"，例如 `初始化 mod 7/12 · jei`；
- D3：`grep "\[LS\] perf" logs/mirage-launch.log` 能得到与本轮 UI 上显示的耗时一致的数据（UI 不是另一套独立估算）；
- D4：`scripts/verify_loadprogress.ps1` 全绿 + 变异检验全红；`verify_forgestyle_text.ps1` 扩展后仍全绿（新增 5 个像素带不重叠）；
- D5：S4（`Bootstrap.bootStrap()` 黑盒区间）在屏幕上表现为**游标 + 秒表在动**，而不是冻在 42%。

## 用户诉求拆解（三条，分别对应什么改动）

用户原话：「我要进度条，不是单纯的色块，然后要详细的内部调试信息 + 独立进度条，不是单纯的 s1 s7，这样没有参考价值」。

| 诉求 | 真实指向 | 对应改动 |
|---|---|---|
| **不是色块** | 现在的条虽然有三层描边（外框/内衬/填充），但**语义只有一根**、填充是**一整块纯色**、百分比是**手写常量**——视觉上就是"会变色的色块" | 条内加**分段刻度**（总进度 7 段）、加**游标**（不定进度）、填充色只表达状态不表达进度、每根条独立 label + 计数 |
| **独立进度条** | 一根条被硬塞了 7 个阶段的信息（`progress` 是全流程单一整数），无法同时表达"总进度"和"当前任务进度" | `LoadProgress` 栈式 meter：主条（分段总进度，最底层）+ 最多 2 根并发子条（Neo 也是 ≤2，见 §参考） |
| **详细内部调试信息** | 现状只有「S4 合并注册表 · 解冻注册表 (42%)」一行字，`MiragePerf` 已经量出 S4/S7 各占十几秒却**一个数字都没上屏** | 计数行（真实计数器）+ 事件流（阶段进出带 ms）+ 每条 meter 带 elapsed |
| **不是单纯的 S1..S7** | S1–S7 是加载器内部概念，7 行占掉 170px 只表达"第几步"，且在 S4 里整整 40 秒都不变 | 步骤条**压成一行面包屑**（`S1✓ S2✓ S3✓ S4▶ …`）保留方位感，把纵向空间让给 meter 与计数 |

> **注意**：`refs/forge/fmlearlydisplay/` 那份是**旧版结构**（`RenderElement` + `PerformanceInfo` + `ElementShader`），NeoForge 26.2 早已换成 `theme/*.json` + `elements/*`。看 Neo 行为**必须**看 `earlydisplay-11.0.16.jar`，拿旧 Forge 源码对照会得出错误结论。

### 1. 屏幕元素清单（坐标取自 jar 内 `theme/theme-default.json`）

画布 **854×480**（`LoadingScreenRenderer.LAYOUT_WIDTH/HEIGHT`，与 Mirage 的 `DESIGN_WIDTH/HEIGHT` 同值）。默认主题：

| 元素 | 位置（主题 json） | 内容 |
|---|---|---|
| `performance` | `left:220 top:10` | 内存条 + `Memory: 1024/4096 MB (25%)  CPU: 37%` |
| `progressBars` | `left:220 right:220 top:250`，`labelGap:4 barGap:5` | **最多 2 根条**，每根上方一行 label |
| `startupLog` | `left:10 bottom:10` | **最多 2 条**最新消息，按年龄淡出 |
| `mojangLogo` | `top:96` 居中 | 品牌 |
| `decoration.version` | `right:10 bottom:10` | `${version}` 版本号 |
| `decoration.fox` | `right:10 bottom:1rem` | 28 帧狐狸动画 |

对照 Mirage 现状：`MEMORY_BAR_TOP=10`、`BAR_LABEL_TOP=250`、`BAR_HEIGHT=20`、版本号右上，**几何本来就是从这套坐标抄来的**（一轮前已经对齐）；差别全在"内容密度"——Neo 把 250~480 这 230px 全给了 2 根条 + 事件流，我们把同样的空间给了 7 行静态步骤条 + 16 行日志尾巴。

### 2. 进度条模型：`ProgressMeter` 栈（**这是核心，也是"独立进度条"的出处**）

```java
// net.neoforged.fml.loading.progress.ProgressMeter
ProgressMeter(String name, int steps, int current, Message label)
  int  steps();          // == 0  → 不定进度
  void increment();      // 每完成一个单位 +1
  void setAbsolute(int);
  float progress();      // current / steps
  void label(String);    // 换行标签（MessageType.ML）
  void complete();       // 出栈
```

`StartupNotificationManager` 维护一个 `Deque<ProgressMeter>`：`prependProgressBar` → `addFirst`，`addProgressBar` → `addLast`，`popBar` → `removeLastOccurrence`。

**渲染侧**（`ProgressBarsElement.render`）的关键两条：

```java
for (ProgressMeter meter : StartupNotificationManager.getCurrentProgress()) {
    if (++count > 2) break;                      // ← 只画 2 根，其余排队不显示
    String text = meter.label().getText();
    if (!text.isEmpty()) { 画 label; 行高 += lineSpacing + labelGap; }
    Bounds bar = ...;                            // 条区宽 400、高 = 贴图高
    if (meter.steps() == 0) renderIndeterminateProgressBar(bar);   // 游标
    else                    renderProgressBar(bar, meter.progress());
}
```

- **不定条的画法**（`RenderContext.renderIndeterminateProgressBar`）：前景按 `animationFrame/100` 取 `0.2×宽` 的滑块在轨道上来回/循环滑动，不是"填一块固定色";
- 条贴图是 **9-slice 40×20，背景边框 2px、前景内缩 4px** —— 这正是 Mirage `OUTER_EXPAND=8 / INNER_INSET=2 / FILL_INSET=4 / BAR_HEIGHT=20` 的来源，**这层不用改**。

**真实在用的条**（反汇编 `loader` 侧调用点）：

| 创建点 | 文案 | steps | 类型 |
|---|---|---|---|
| `FMLLoader.runDiscovery()` | `Discovering mods...` | `0` | 不定（prepend 到最前） |
| `ModLoader.dispatchParallelTask(name, …)` | 任务名，如 `Mod Construction` | `modList.size()` | 确定，**每个 mod 完成 +1** |
| 同上 | `Mod Construction: Deferred Queue` | mod 数 | 确定 |
| `DisplayWindow.<init>` | `""`（空标签，**恒不定**） | `0` | 不定，label 由 `updateProgress()` 随时替换 |
| `ModLoader.waitForTask(name, …)` | 任务名 | `0` | 不定 |

而那根"主条"的 label 全流程只被这几个字符串改写过（`EarlyLoadingScreenController.updateProgress` 的实现就是 `mainProgress.label(s)`）：

```
"Loading bootstrap resources"   BackgroundWaiter
"Discovering mod files"         ModDiscoverer
"Loading language providers"    LanguageProviderLoader
"Loading mods"                  ClientModLoader
```

**这条最重要**：Neo 的主进度条**从来不给百分比**——因为它自己也不知道总步数。它给的是"现在在干什么"。真正带分母的条，只在"每 mod 一步"这种天然可数的任务上出现。

### 3. 事件流：`StartupLogElement`（不是日志面板）

```java
List<AgeMessage> msgs = StartupNotificationManager.getMessages();
// getMessages(): 四类 MessageType(MC/ML/LOC/MOD) 的消息合并 → 按时间倒序 → limit(2)
for (AgeMessage m : msgs) {
    alpha = clamp(...);                       // 依 age 淡出（常量 1000 / 5000，<0.01 直接不画）
    画一行 m.message().getText();
}
```

- 每类消息自带颜色（`MessageType.colour`：MC / ML / LOC / MOD 四色），一眼分辨"这条是 MC 原版、加载器、定位器还是某个 mod 说的"；
- **容量**：`addModMessage` 走 `CharMatcher.ascii().retainFrom(s)` + `Ascii.truncate(80, "~")` + 每类保留 20 条；`modLoader/mcLoader/locator` 三类不截断、不限量；
- 屏幕上**同时只有 2 条**、且会自己淡掉——它表达的是"刚刚发生了什么"，不是"完整日志"。

### 4. 性能条

`PerformanceElement.PerformanceInfo`：`"Memory: %d/%d MB (%d%%)  %s"`，`%s` 是 `"CPU: %d%%"`（`getProcessCpuLoad()<0` 时退化成 `"*CPU: %d%%"` 取系统负载）；条色 = 主题 `memoryLowColor #007f00` → `memoryHighColor #ff7f00` 按占用率插值。
> Mirage 现有 `memoryText/cpuText` 的格式（含 `*CPU` 降级分支）**与这里逐字一致**，保持不动即可。

### 5. 可以直接借 / 绝对不能照抄

**借**：
1. `ProgressMeter` 的「steps==0 = 不定条」语义 —— 这是解决"假百分比"的正解；
2. 栈式并发条（渲染 2 根）+ 每根独立 label 与计数；
3. 四类消息着色 + 按年龄淡出（我们改成 5 行滚动 + 保留通道色）；
4. 主条只报"正在干什么"，不报百分比。

**不照抄**：
1. **`CharMatcher.ascii()`**：Neo 这条把非 ASCII 全删了——Mirage 的日志几乎全是中文，照抄等于日志全空（我们已为此打包了 594 字字表，见 `LOADING_CJK_LOG_SOURCE`）；
2. **只显示 2 条消息**：中文 24px 字一行只能放约 29 个汉字，2 条不够看出趋势，我们保留 5 行；
3. **狐狸动画 / logo**：占体积、零诊断价值（用户本轮诉求是"参考价值"，不是好看）。

## 现状分析（as-is：为什么"没有参考价值"）

### 1. `progress` 是手写常量，与真实工作量无关

全仓 `setProgress(...)` 的字面量（`lifecycle-starter/.../stage/*.java`）：

| 位置 | 值 | 语义 |
|---|---|---|
| `DiscoveryStage` | 3 / 8 | 扫描目录 / 解析清单 |
| `TransformStage` | 14 | 创建类加载器 |
| `RegistryWindow` | 22 / 32 / 42 / 72 / 85 | 版本 / Bootstrap / 解冻 / 修补 / 冻结 |
| `ModInitStage` | `45 + 20*i/n` | 每个 mod |
| `LoadedStage` | 92 / 95 / 100 | 启动 MC / 启动客户端 / 完成 |

这些数字是**写死的阶梯**，不对应任何计数：S4 里 `Bootstrap.bootStrap()` 实测 **6.8~40.2 秒**，屏幕上就一直停在 `42%`；S7（MC 建窗口 + 资源重载）**23.6~68.1 秒**，屏幕上一直是 `92%`/`95%`。**用户说"没有参考价值"说的就是这个**：不是配色问题，是这根条上的数字不再变化，变成了装饰。

### 2. 一根条承担两个语义

`progress` 同时被当成"总进度"和"当前阶段进度"用（`stageSummary()` 也是拿它拼 `(42%)`），所以既不能表达"7 个阶段走到第几个"，也不能表达"这一步内部完成了多少"。

### 3. 步骤条是静态表

`phaseStates()` 只返回 已完成/进行中/待处理 三态，7 行 × 24px = 168px 的纵向空间，换来的信息量是"到第几个阶段了"——这一句话用一行面包屑就能表达。

### 4. 日志面板收不到真正重要的行

`MirageDebug.isImportantLog()` 只认前缀 `[Mirage` `[LS]` `[Loader]` `[MidCache]` `[Mirage-Mixin]` + `ERROR/WARN`：

- **mod 自己的日志**（`ModLoggerImpl` 输出）不进来；
- **MC 原版**在 S4/S7 的行（注册表预填充、资源重载）不进来；
- `MiragePerf` 的 `[LS] perf ...` 行虽然匹配 `[LS]`，但**没有被渲染成任何数字**（面板里只是一行文本）。
  结果就是：S4 那 6.8~40 秒里，面板通常**完全静止**。

### 5. 已经拿到手、但没上屏的数据

| 数据 | 现在在哪 | 上屏了吗 |
|---|---|---|
| 阶段耗时（S4 四段 / S7 两段 / 交接三段） | `MiragePerf.mark` → `logs/mirage-launch.log` | ✗ |
| mod 总数 / 已完成数 | `MirageDebug.modTotal/modCount` | 只在 TitleScreen 面板 |
| 当前 mod id | `MirageDebug.currentMod` | 只进了 `stage` 字符串尾巴 |
| 已解冻注册表数 | `RegistryWindow` 日志 `已解冻 N 个 MappedRegistry` | ✗ |
| 已修补 BlockState 数 | 同上 `已修补 N 个` | ✗ |
| DeferredRegister flush 数 | `ModInitStage` 日志 `flush N 个` | ✗ |
| 失败 mod 数 | `ModInitStage` 失败汇总 | ✗ |

## 每处改动要点

### A. `LoadProgress`：meter 栈 + 计数器 + 事件环（纯逻辑）

```java
public final class LoadProgress {
    public static final class Meter {                 // 不可变快照之外全部原子
        private final int id;
        private volatile String label;
        private final int steps;                      // 0 = 不定
        private final AtomicInteger current;
        private final long startNanos;
    }

    Meter begin(String label);                        // 不定条（steps=0）
    Meter begin(String label, int steps);             // 确定条
    void  label(Meter m, String label);
    void  step(Meter m);                              // current++
    void  set(Meter m, int absolute);
    void  end(Meter m);                               // 出栈
    List<Snapshot> snapshot(int max);                 // 渲染侧：最多 2 根 + 主条

    void counter(String key, long value);             // 计数行数据源
    void event(String channel, String text);          // 事件流（环形 32）
}
record Snapshot(String label, int steps, int current, float fraction,
                boolean indeterminate, long elapsedMs) {}
```

- 用 `ArrayDeque` + `synchronized`（与 Neo 一致：起点低、无锁竞争压力；不要为它引入并发库）；
- `elapsedMs` 在 `snapshot()` 里现算（`System.nanoTime()` 差值），渲染侧不做算术以外的判断；
- **为什么独立成类**：踩过 C41 的坑——把逻辑写在渲染类里就只能"在测试里复制一遍算法"，等于没测。

### B. 埋点表：每个阶段能拿到什么真实数字（**这是本轮的核心判断**）

原则：**分母已知 → 确定条；分母未知 → 不定条 + 计数 + 秒表。绝不编百分比。**

| 阶段 | 真实数据源（代码位置） | 分母可得 | 条形态 | label 示例 |
|---|---|---|---|---|
| S1 发现 | 扫描候选 jar 数 / 已解析 manifest 数（需 `ModDiscoverer` 加回调） | ✓ | 确定 | `扫描 mod 3/12` |
| S2 解析 | `ParseStage` 循环 i / mods.size() | ✓ | 确定 | `解析清单 7/12` |
| S3 建类加载器 + 挂 jar | `TransformStage` 循环 i / mods.size() | ✓ | 确定 | `挂载 jar 9/12` |
| S3 mixin config 收集 | `perMod` 已处理数 / mods.size() | ✓ | 确定 | `收集 mixin 配置 12/12` |
| S3 **实际织入** | 计数：`MirageMixinBootstrap.transform` 被调次数（每个目标类一次） | ✗ 目标类总数要等 MC 跑起来才知道 | **不定 + 计数** | `织入字节码 · 已处理 37 个类` |
| S4 版本检测 | 单步 | — | 不定（<1s） | `检测 MC 版本` |
| S4 **Bootstrap.bootStrap()** | **黑盒，MC 无回调** | ✗ | **不定 + 秒表** | `初始化注册表（MC 原版）· 8.4s` |

### D. 渲染（两窗口同步改，两处都要过断言）

- **分段总条**：先画 7 段边框（1px 竖线分隔），再逐段填；
- **游标条**：`cursor = (frame % 100) / 100f`，画 `0.2×宽` 滑块，位置在 0..(1-0.2) 之间来回（`bounce`）或循环；早期窗口用 `EarlyGl.quad`（**ABGR**，见记忆铁律），主窗口用 `fillRect`；
- **meter label 右端计数**：右对齐到 `barOuterRight()`，避免中文 label 与数字挤在一起；
- **颜色语义**：填充色只表达状态（进行中=白/淡青、完成=绿、失败=红），**不再用颜色表达百分比**（旧的"红→绿渐变"就是"色块感"的来源之一）；
- **无 AWT**：主窗口仍只查 `GLYPH_CACHE` 拼装；新文案里的汉字必须来自 `LOADING_CJK_SOURCE`（UI 用字）或走 `ensureRasterized`（主窗口按需）/ `LOADING_CJK_LOG_SOURCE`（早期窗口字表）。**新加的中文 label 词（如"挂载""织入""秒"）必须补进 `LOADING_CJK_SOURCE`**，否则早期窗口静默留白（STB 缺字不报错）。

## 实施记录 · 2026-11-07（用户「开始」确认方向后落地）

**完成范围**：P0 + P1 一并落地（用户诉求「进度条 + 详细内部调试信息 + 独立进度条」需要两者同时到位才成立）；**P2 未做**，仍未动 `mirage.mixins.json`。
