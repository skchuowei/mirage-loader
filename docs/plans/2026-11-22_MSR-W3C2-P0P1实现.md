## 现状分析

**为什么这三个能上一个 C1 没做的**：C0 自动分档把 A 档 34 类扩成 108 待实现时，这三个在内置 pack 的 114 类里**没有沙盒骨架**（pack 来自 P3 沙盒 + 6 mod 常量池，这三个是 18:20 真机才暴露的），所以 C1 生成器（从 pack 骨架取形状）用不上——本轮改为直接从形状源 jar `javap` 取签名，同样 clean-room。

**已知坑与对策**：
- C104 暗门②（第三方链）：`OnDatapackSyncEvent` 的 `recipeTypesToSend` 是 fastutil `ReferenceSet`，getter 若返回该类型会拉第三方链 ⇒ `getRecipeTypesToSend()` 抛 UOE，字段仍保存引用但不暴露；
- C104 暗门①（依赖闭包）：三个类的 super/接口已逐个核过，无悬空 neo 引用；
- N1 原则：`createScreen` 返回 `Screen`——MG 没有真实配置屏，**抛 UOE 不返回假 Screen**；`getForMod` 是 static 查询，返回 `Optional.empty()` 语义为"没有注册任何配置屏工厂"（这是真值，不是编造）；
- C84 假覆盖：三个类都只解决链接期形状，本轮**不宣称 Cloth Config/JEI 兼容通过**——真机要用户双击验证。

## 每处改动要点

1. **IExtensionPoint**：空接口一行，`package net.neoforged.fml;`，Javadoc 注明 clean-room 来源边界。
2. **IConfigScreenFactory**：`extends IExtensionPoint`；`createScreen(ModContainer, Screen)` 声明（实现由 mod 提供，接口只声明）；`static Optional<IConfigScreenFactory> getForMod(IModInfo)` 返回 `Optional.empty()`——语义真值"MG 侧无注册工厂"，Javadoc 写清。
3. **OnDatapackSyncEvent**：`extends Event`；三个 `private final` 字段（其中 `ReferenceSet` 用完全限定名避免 import fastutil）；`getPlayerList()`/`getPlayer()` 返真值；`getRelevantPlayers()`/`sendRecipes(...)`×2/`getRecipeTypesToSend()` 抛 UOE 带 `OnDatapackSyncEvent#方法名`。
4. **门禁 `verify_w3c2_p0p1.py`**：
   - 守卫层：三文件存在+UTF-8、行首锚定签名（接口/继承/getter/UOE）、禁止 `return null` 假值、禁止 import fastutil；
   - 行为层：`javac` 编译三文件 + 探针，断言 `getForMod` 返 empty、`getPlayerList/getPlayer` 同一实例、三个 UOE 消息格式、类由自定义 classloader 加载；
   - 变异层：3 个落盘变异（去 UOE / 改 getter 返 null / 把 getForMod 改成编造实例），`try/finally` 字节级还原 + 编译路径自检 + 基线回绿；
   - 遵循 C89（-D 整体引号）、C76（ReadAllBytes/WriteAllBytes）、GBK 优先解码。
