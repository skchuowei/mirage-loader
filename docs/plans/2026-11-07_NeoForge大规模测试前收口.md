# NeoForge 大规模测试前收口（N0–N4）

> 关联：`docs/plans/2026-10-31_AG-总计划重梳理.md` Phase 3（T3.1–T3.6）；
> `docs/NeoForge兼容层缺口清单.md`（其"P0+P1 全绿、可小规模试跑"结论已被本轮实测推翻）；
> 本轮取证：从 Modrinth 下载 3 个 26.2 真实 NeoForge mod，用 jar 常量池对账（JEI 30.48.0.244 / Cloth Config 26.2.155 / FerriteCore 9.0.0）。

## 目标

把 NeoForge 兼容层从「代码齐」推进到「真实 mod 可跑、可批量统计」：先 3 个真实 mod 全链路通过，再 20 个矩阵可量化。

**可验证标准（三道门禁，按顺序过）**

- **门禁 A（N1+N2 出口）**：FerriteCore + Cloth Config + 一个注册/配置型真实 mod，三者日志都有 `[NeoCompat] mod=<id> ctor=ok events=N regs=M`（N、M 非 0），且与本次改动相关的 `NoClassDefFoundError` / `IllegalAccessError` / `MixinApplyFatalException` 为 0。
- **门禁 B（N3 出口）**：门禁 A 的 3 个 + 5 个含客户端事件/配置界面的 mod 通过；JEI 能完成 mod 构造与 `@SubscribeEvent` 注册（客户端事件缺失数降到 0，或明确列出并接受剩余缺口）。
- **门禁 C（N4 出口）**：20 个真实 mod 矩阵跑完，`docs/compat-matrix.md` 里"构造成功 / 事件触发 / 注册成功 / 全链路通过"四列有数据，兼容率可作为对外口径。

## 前置条件与阻塞项

- 工作区当前有多条 WIP（加载界面、性能基线等）。本计划**只动 NeoForge 兼容层与它直接依赖的加载链路文件**，不碰 UI / 早期窗口 / 性能脚本。
- 真实 mod 样本按 AGENTS「测试 Mod 获取规则」下载到 `mods-library/neoforge/`；测试时**复制**到 `mc-shili/versions/26.2-mirage/mods/`，测完移走。不修改 `mc-shili/` 其他文件（规则 8）。
- 所有"启动游戏"动作必须由用户双击 `启动 26.2-mirage.bat`（虚拟桌面规则）；AI 只做离线校验与读日志。
- 26.2 真实 NeoForge mod 供应已核实：Modrinth `versions=26.2 & loaders=neoforge` 共 7769 个，样本不缺。
- 无前置代码阻塞，N0/N1/N2 的离线部分可立即开干；门禁实机部分等用户配合。

## 现状分析

### 1. 链接期 API 面（真实 mod 实测）

| mod | 引用 `net/neoforged/*` | 当前缺失 | 直接后果 |
|---|---|---|---|
| JEI 30.48.0.244 | 92 | **81** | 类链接期大面积失败 |
| Cloth Config 26.2.155 | 7 | 5 | `Dist` / `FMLPaths` / `ModContainer` / `FMLEnvironment` / `IConfigScreenFactory` 缺失 |
| FerriteCore 9.0.0 | 5 | 3 | `FMLPaths` / `LoadingModList` / `ModInfo` 缺失 |

缺口集中在整片包：`net.neoforged.api.distmarker.*`、`fml.{ModContainer,ModList}`、`fml.loading.{FMLPaths,FMLEnvironment}`、`fml.event.IModBusEvent`、`neoforge.common.{NeoForge,NeoForgeMod,Tags}`、**整个 `net.neoforged.neoforge.client.*`**（真实 NeoForge 有 90 个 client event 类，本项目 0 个）。

主类构造签名同样是链接期门槛：`NeoLifecycle.constructModInstance` 只支持无参与 `(IEventBus)`（[NeoLifecycle.java](file:///d:/bing/MC/mcmoderr-my/mirage-loader/lifecycle-starter/src/main/java/io/mirage/ls/stage/NeoLifecycle.java#L34-L48)），而真实样本里 JEI 是 `(IEventBus, Dist)`。

### 2. 加载语义缺口（不崩，但 mod 等于没装）

- **mod 自带 Mixin 不加载**：只收集 `fabric.mod.json` 的 `mixins` 声明 + 根目录 `*.mixin.json` 盲扫（[TransformStage.java](file:///d:/bing/MC/mcmoderr-my/mirage-loader/lifecycle-starter/src/main/java/io/mirage/ls/stage/TransformStage.java#L87-L106)）；不解析 `neoforge.mods.toml` 的 `[[mixins]]`，且 Neo 惯例文件名是 `*.mixins.json`，盲扫也匹配不到。FerriteCore 声明 5 个 config，实际生效 0。
- **Access Transformer 未应用**：JEI / Cloth Config 都带 `META-INF/accesstransformer.cfg`；当前只被 `NeoModScanner` 解析进 `OutputModel.accessWideners` 后无消费方，运行时不做访问放宽。
- **依赖解析口径不对**：真实 toml 用 `type = "required"`，[NeoForgeModDetector.java](file:///d:/bing/MC/mcmoderr-my/mirage-loader/core/mirage-loader/src/main/java/io/mirage/loader/NeoForgeModDetector.java#L105-L133) 只认旧式 `mandatory = ...` ⇒ 拓扑排序与缺失依赖检查对真实 mod 失效。
- **`@EventBusSubscriber` 无扫描器**：只有注解类（[EventBusSubscriber.java](file:///d:/bing/MC/mcmoderr-my/mirage-loader/modules/mirage-neoforge-compat/src/main/java/net/neoforged/fml/common/EventBusSubscriber.java)），静态订阅类不会被注册。

### 3. 测试基建

- 至今 **0 个真实 NeoForge mod 通过验收**；`mods-library/neoforge/` 只有自建 `neop0test`，`mc-shili/.../mods/` 的样本全是自建夹具（ExpOre / testtab / mdk-example）。
- 无 `docs/compat-matrix.md`、无每个 mod 的期望日志行、无批量统计脚本；单 mod 失败只记 ERROR 并继续（[ModInitStage.java](file:///d:/bing/MC/mcmoderr-my/mirage-loader/lifecycle-starter/src/main/java/io/mirage/ls/stage/ModInitStage.java#L191-L196)），"看起来加载成功、实际全死"很难发现。
- 事件覆盖：主侧约 25 / 161，客户端 0 / 90；高频事件（`LivingDropsEvent`、`ItemTooltipEvent`、`PlayerDestroyItemEvent`、`AdvancementEvent`…）缺失。

结论：`docs/NeoForge兼容层缺口清单.md` 的 P0/P1 只覆盖了"自有测试 mod"能跑，没覆盖真实 mod 的链接期与加载语义；本计划以实测为准重新排序。

## 每处改动要点

### N0
- `verify_neo_api_surface.ps1`：输入 mod jar + 参考类列表（从 `modules/mirage-neoforge-compat/build/classes` 或 fat jar 提取），用与人工取证相同的方法（读 `.class` 常量池 ASCII 串 `net/neoforged/...`）求差集；输出「引用数 / 缺失数 / 缺失类清单 / 覆盖率」。用于：① 选样本（优先缺失最少的）；② 每次改动后防回归。
- 缺口清单只追加一节「2026-11-07 真实 mod 实测」，旧结论行标已过时，原文保留。

### N1
- `Dist` 必须与真实签名一致（枚举常量、`isClient()/isDedicatedServer()` 视真实 API 补齐）；`@Mod` stub 同步加 `Dist[] dist()` 元素（默认双端），避免反射读注解时漏元素。
- 构造器选择：按真实 NeoForge 的优先顺序尝试；找不到时降级为「无参 → WARN」，并记录最终命中的签名。
- `FMLPaths`/`FMLEnvironment` 的静态值只能由加载器注入（不能在 stub 里写死相对路径），否则和 bug #4 的 CWD 依赖同源。
- 所有未知方法一律 `UnsupportedOperationException` 带类名+方法名，不返回编造值（沿用 `FMLLoader` 的既有原则）。

### N2
- `[[mixins]]`：`config` 值可能是子目录或带 `.json`，复用 `ModMixinConfigs.normalize`；合并顺序 = fabric 声明 → neo 声明 → 根目录盲扫兜底，保序去重。
- AT：只做访问标志改写（`ACC_PUBLIC/PROTECTED/PRIVATE`、`-f/-m`），不改描述符、不删成员；解析失败整文件跳过并 WARN；应用点必须在 Mixin 之前（Mixin 需要看到放宽后的访问级别）。
- **mod 自带 Mixin 失败的隔离策略（需拍板）**：
  - 方案 A（默认）：保持现有 FATAL，先靠矩阵逐个定位；
  - 方案 B：mod 提供的 config 织入失败 → 记录 mod + config 名，降级返回原始字节并标记该 mod 失败，游戏继续。
  - 建议先 A（门禁 A 阶段），验证 3 个样本后再评估 B；B 需要 config→mixin 类名映射，复杂度另计。
- 依赖：解析 `type`（required/optional），保留 `mandatory` 兼容分支；缺失 required 依赖的处置沿用现有 `DependencySorter` 策略，不新增 FATAL 语义。
- `SubscriberScanner`：只扫 annotation 描述符，不加载全 jar；`value` 为 Dist 数组时按当前 dist 过滤；与已注册的 mod 主类实例按「类+方法」去重。

### N3
- 每个事件类必须**同时**有类定义、post 调用点、构建期注入校验三件套；只建类不 post = 假覆盖（AGENTS 技术注意事项第 7 节）。
- `MenuScreens` / `IConfigScreenFactory` 只做注册与查询，打开配置界面不在本轮。
- `ModConfigSpec` 只支持 `Builder.push/pop/define*/comment` 与基础取值；不支持的 API 明确抛异常。

### N4
- 矩阵脚本只读日志，不启动游戏；`-OutFile` 写文档时口径段（样本数、缺失锚点、单次样本不可当阈值）由脚本生成。
- 20 个样本按类别取：性能/核心 4、配置 3、物品/方块内容 4、UI/HUD 4、配方/API 3、其他 2；每个都要在 `compat-matrix.md` 里写期望锚点。

## 回归测试影响面

**可能被打破的旧行为**
- AT 应用错误 → MC 类加载异常或仍 `IllegalAccessError`；用「只对索引命中的类生效 + 失败跳过」限制爆炸半径，并加 kill switch。
- 开启 mod 自带 mixin 后，任何一个 mod 的坏 mixin 都可能让启动 FATAL（现有 `MirageMixinBootstrap` 会升级致命）；门禁 A 阶段按方案 A 接受，但要先确认 loader 自身 mixin 不受影响。
- `@EventBusSubscriber` 扫描可能重复注册（mod 主类既被实例注册又带注解）；去重键 = 类名+方法名+事件类型。
- 依赖改 `type` 后，现有自建 mod 的 `mandatory` 写法必须继续生效；新增断言覆盖两种写法。
- `Dist`/`NeoForge` 等新类与 mod 自带的 jarJar 副本理论上可能重名；按现有 classloader 规则（`net.neoforged.*` 由 mcl 加载）处理，不做额外隔离。

**零侵入**
- Fabric 兼容层、事件总线、注册表桥接、UI/早期窗口、性能脚本、mdk-example 冒烟步骤均不改。

**新增回归**
- `verify_neo_api_surface.ps1`、`verify_neo_ctor.ps1`、`verify_neo_at.ps1`、`verify_neo_depends.ps1`、`verify_neo_client_events.ps1`、`verify_compat_matrix.ps1`；全部必须带 `-SelfTest` 与至少 3 个变异点（变异真红、还原回绿）。
- `verify_mixin_registry.ps1` 扩到新客户端 mixin；`verify_mod_mixin_config.ps1` 扩到 `[[mixins]]`。

## 验证步骤

1. 基线：`gradle build`（JDK 25，全局 Gradle 9.1）。
2. 离线：依次跑上述 `verify_*.ps1`，全部绿 + 变异全红；`verify_neo_api_surface.ps1` 对 3 个样本的缺失数记录进 `compat-matrix.md`。
3. 出包：只认 `:launcher:mirage-launch:fatJar`；`unzip -l` 核对新增类（`Dist.class`、`ModContainer.class`、`AccessTransformer*.class`、`SubscriberScanner.class`、客户端事件类）都在包内，体积 ~2.9MB。
4. 部署：备份旧 jar（`.bak-YYYYMMDD-<标签>`）后替换；**不自行启动游戏**。
5. 实机（用户双击 `启动 26.2-mirage.bat`）：读 `mc-shili/versions/26.2-mirage/logs/mirage-launch.log` 与 `logs/latest.log`，按门禁核对：
   - `[NeoCompat] mod=<id> ctor=ok`（每个样本一行）
   - `[NeoCompat] mixins=<config 数> applied=<n>`（FerriteCore ≥1）
   - `[MODIFIED]` 出现对应 MC 目标类（mod mixin 生效）
   - 无 `NoClassDefFoundError` / `IllegalAccessError` / `MixinApplyFatalException`
   - 注册型 mod 的 item/tab 进创造栏
6. 每轮实机后运行 `scripts/measure_neo_compat.ps1` 更新矩阵；完成后清理本轮放进 `mods/` 的样本。

## 合规边界（条件必填）

涉及 `modules/mirage-neoforge-compat/` 与 `refs/neoforge/`。NeoForge 为 LGPL 2.1：本计划只做**行为观察 / 接口签名枚举 / clean-room 实现**，不抄其实现代码。`refs/neoforge/` 仅用于核对类名、包名、方法签名与事件命名；AT / Mixin 配置格式按公开规范实现。新增 stub 的 Javadoc 注明 clean-room 来源边界。`THIRD_PARTY_NOTICES.md` 已有声明，本轮不改变授权口径。

## 回滚方案

- 每个阶段独立提交（N0/N1/N2/N3/N4），回滚按阶段 `git revert <commit>`；不一次性合并。
- 三个新子系统各留运行时 kill switch（默认开）：`-Dmirage.neo.at=false`（AT）、`-Dmirage.neo.modmixins=false`（mod 自带 mixin）、`-Dmirage.neo.subscribers=false`（静态订阅扫描）。出问题先关开关复验，再决定 revert。
- 每次部署前备份 fat jar（`.bak-YYYYMMDD-<阶段>`）；回滚后按规则 6 写回退报告，说明连带撤掉的内容。
- N3 客户端事件面独立提交，未通过门禁 B 时可整体不部署，不影响 N1/N2 已通过部分。
