# MID 磁盘缓存层（第一步）：NeoForge 识别结果落盘 `.mid-cache/`

> 日期：2026-10-17
> 范围：`core/mirage-loader` 运行时发现管线
> 前置：本计划只做"识别结果缓存"这一层基础设施，不做字节码转译。AG 的真正转译能力（@Mod 桥接、事件总线桥接、DeferredRegister 桥接）是后续步骤，不在本计划内。

## 目标

让 `ModDiscoverer` 遇到 NeoForge mod 时：
- **第一次**：跑 `NeoForgeModDetector.detect(jf)`（含 ASM 扫 class 找 `@Mod`），结果写到 `<gameDir>/.mid-cache/<mod-id>+<jar-sha256>.json`；
- **第二次起**：校对缓存头（jar 哈希 / AG 版本 / MC 版本）全过，直接读缓存，跳过 ASM 扫 class；
- 任一项对不上，自动重走 `detect()` 并重写缓存；
- 提供 `--mid-cache-force-regen` 启动参数作为逃生开关（配置文件层在第二步做）。

**可验证标准**：同一个 `ferritecore-9.0.0-neoforge.jar` 放进 `mc-shili/versions/26.2-mirage/mods/` 连启两次，第二次启动日志里出现"使用 MID 缓存，跳过 ASM 扫描"，且从 ASM 扫 class 开始到 mod 列表打印完成的耗时显著下降。

## 现状分析

读 `core/mirage-loader/src/main/java/io/mirage/loader/ModDiscoverer.java` 与 `NeoForgeModDetector.java` 后确认：

1. `ModDiscoverer.discover(Path modsDir)` 已按四级优先级扫描：
   - jar 根 / `META-INF/mod.mirage.json`（IR v0.1，Mirage 原生）
   - `META-INF/mirage.mod.json`（legacy）
   - `fabric.mod.json`（Fabric）
   - `META-INF/neoforge.mods.toml`（**当前落点**：每次都现场调 `NeoForgeModDetector.detect(jf)`）
2. `NeoForgeModDetector.detect(JarFile)` 做了三件事：
   - 解析 `neoforge.mods.toml` 的 `[[mods]]` 段，提取 `modId` / `version` / `displayName`；
   - **ASM 遍历 jar 里所有 `.class`**，找带 `@Lnet/neoforged/fml/common/Mod;` 的主类（这是耗时大头）；
   - 返回 `Detected(id, version, displayName, mainClass)`。
3. 没有任何磁盘缓存：每次启动、每个 NeoForge mod 都重扫一遍 class。
4. `Launcher.main` 通过 `--gameDir` 参数已经把 gameDir 传进来，`Loader.discoverMods(gameDir)` 直接可用。
5. Gson 已是 `core/mirage-loader` 的依赖（`ModDiscoverer` 已 import `com.google.gson.Gson`），JSON 序列化零新增依赖。

**为什么现在做**：ferritecore 这种 70KB 的小 jar 扫 class 都要几十 ms，未来 mod 多了/大了，启动时间线性累积。缓存是基础设施，先上；AG 的真正转译能力长出来后，MID 文件内容会从薄（4 字段）变厚（加 Mixin 规则、桥接指令），但缓存目录结构不变。

**当前工作区阻塞**：写计划时 `git status` 显示 `ModDiscoverer.java`、`NeoForgeModDetector.java`、`MirageClassLoader.java`、`Launcher.java` 等还有另一会话未提交改动（接 NeoForge 运行时检测的后续打磨）。**实施前必须先等那批改动落地提交**，否则改在别人的 WIP 上会冲突。

## 每处改动要点

### 1. `MidCache.java`（新建，~150 行）

数据结构（内部静态类，Gson 序列化友好）：

```java
public final class MidCache {
    /** 缓存文件头。每次写缓存都填这些字段。 */
    public static final class Entry {
        public String specVersion;     // 固定 "0.1"
        public String agVersion;       // = NeoForgeModDetector.AG_VERSION
        public String mcVersion;       // 从 net.minecraft.SharedConstants 读（启动早期还读不到，
                                       //  先写 "26.2" 占位；第二步改成读真实值）
        public String jarSha256;       // mod jar 全文件 SHA-256
        public long   cachedAt;        // epoch millis
        public NeoForgeModDetector.Detected detected;  // 真正的识别结果
    }

    private final Path cacheRoot;     // <gameDir>/.mid-cache/<mcVersion>/
    private final Gson gson = new Gson();

    public MidCache(Path gameDir) {
        this.cacheRoot = gameDir.resolve(".mid-cache").resolve("26.2");
        Files.createDirectories(cacheRoot);
    }

    /** 尝试读缓存。返回 null 表示未命中/校对失败。 */
    public Entry lookup(Path jar, boolean forceRegen) throws IOException { ... }

    /** 写缓存。文件名 = <modId>+<jarSha256前16位>.json */
    public void store(Path jar, NeoForgeModDetector.Detected d) throws IOException { ... }

    /** 算 jar 全文件 SHA-256。 */
    private static String sha256(Path jar) throws IOException { ... }
}
```

**校对规则**（`lookup()` 内）：
- `forceRegen=true` → 直接返回 null（强制重转）；
- 文件名按 `<modId>+<hash16>.json` 索引，遍历 `cacheRoot` 找前缀匹配 `<modId>` 的文件；
- 打开 JSON，反序列化 Entry；
- 比对：`entry.agVersion == AG_VERSION`、`entry.jarSha256 == 当前jar哈希`；
- 任何一项不等 → 删除该 json，返回 null；
- 全过 → 返回 entry。

### 2. `NeoForgeModDetector.java`（小改，~30 行）

- `Detected` 类字段保持 `public final`，Gson 反序列化需要无参构造——改成 `public Detected() {}` + `public` 非 final 字段，或者加一个 `fromJson` 用的静态工厂。**选最小改动**：把 `final` 去掉，留 public 字段。
- 新增 `public static final String AG_VERSION = "0.1.0";`
- 不改 `detect()` 逻辑。

### 3. `ModDiscoverer.java`（核心改动，~60 行）

在第 4 步 `NeoForgeModDetector.detect(jf)` 前后包一层：

```java
// ---- 4. neoforge.mods.toml（带 MID 缓存） ----
Path modJarPath = jar;
NeoForgeModDetector.Detected neo = null;
if (midCache != null) {
    MidCache.Entry cached = midCache.lookup(modJarPath, forceRegen);
    if (cached != null) {
        neo = cached.detected;
        if (verbose) System.out.println("[Mirage]   · MID 缓存命中: " + cached.detected.id);
    }
}
if (neo == null) {
    neo = NeoForgeModDetector.detect(jf);   // 原逻辑
    if (neo != null && midCache != null) {
        try { midCache.store(modJarPath, neo); }
        catch (IOException e) { System.err.println("[Mirage] MID 缓存写入失败: " + e); }
    }
}
if (neo != null) { ...原有的 ModContainer 构造逻辑... continue; }
```

`ModDiscoverer.discover(Path modsDir)` 签名不动；新增一个重载 `discover(Path modsDir, MidCache cache, boolean forceRegen, boolean verbose)`，老方法委托新方法传 `null/false/false`，避免影响现有调用方（`Loader.discoverMods`）。

`Loader.discoverMods(gameDir)` 里 new 一个 `MidCache(gameDir)` 传下去（从 `Launcher` 读 `--gameDir` 时已经拿到 gameDir 了）。

### 4. `Launcher.java`（小改，~20 行）

`parseGameDir` 旁边加：
```java
boolean forceRegen = hasFlag(args, "--mid-cache-force-regen");
boolean verbose    = hasFlag(args, "--mid-cache-verbose");
System.setProperty("mirage.midcache.forceRegen", Boolean.toString(forceRegen));
System.setProperty("mirage.midcache.verbose",    Boolean.toString(verbose));
```

`Loader` / `ModDiscoverer` 读这两个系统属性。

### 5. `scripts/verify_mid_cache.ps1`（新建，~80 行）

自动化冒烟，不真拉 MC：
1. 检查 `mc-shili/versions/26.2-mirage/mods/ferritecore-9.0.0-neoforge.jar` 存在（不存在就从 `mods-library/neoforge/` 拷一份；库存也没有就报错退出码 2）；
2. 删除 `<gameDir>/.mid-cache/26.2/` 整目录，模拟"冷启动"；
3. 用 `java -cp <启动classpath> io.mirage.launch.Launcher --gameDir <gameDir> --mid-cache-verbose` 启动，**但 5 秒后强制 kill**——只要日志里出现"MID 缓存写入"或 ferritecore 被识别为 neoforge mod，就算首启通过；
4. 检查 `.mid-cache/26.2/*.json` 文件确实生成；
5. 再启一次，5 秒后 kill，日志里必须出现"MID 缓存命中"；
6. 断言：`.mid-cache/` 文件数 = 1（只有 ferritecore 一个 NeoForge mod），用户原有的 addonmod/examplemod/testtab 是 Mirage 原生或 fabric，不进 NeoForge 缓存。

退出码 0 = 全绿，非 0 = 失败。

- **现有行为不变**：
