## 3. 可实现性分析

### 3.1 判定口径

- **可直接实现**：施工图清晰、有同构先例、无外部未知量，按现有模式增量即可。
- **需补充前置工作**：技术上可行，但缺 schema / 发布渠道 / 抽象层 / 验证手段，先补前置才能开工。
- **存在不确定性**：结果取决于外部条件（上游版本、上游维护状态）或需要先做实验才能判断可行性，不能排进承诺路径。

| G18 版本区间补充包 | 需要至少两个版本区间才能验证；当前只有 26.2 且 D10 明确不向下兼容 → 先做抽象（`CapabilityProbe` + `VersionAdapter` SPI），等 26.3 出现再落具体包 | 前提不存在 |
| G23 MSR P2（版本伪装回放） | 需要"拦截 mod 对 loader 版本的查询并报录制版本"的机制；且 P2 依赖 P1 先把进程内加固做完 | 顺序前置 |
| G24 MID-S / MSCP | 需要先冻结 MSF schema 与"语义 → 字节码"映射规则；还需先回答"MID-B 与现有 IR v0.1 是不是同一物"（见 Q4） | 设计前置 |
| G27 MDK 10 分钟验收 | 需要 api 先能发布（`maven-publish` + 版本号），否则 MDK 只能靠 `includeBuild` 指向本地 | 发布前置 |
| G29 0.1.0 发布 | 需要 tag 策略 + release note + 三份缺失文档；且必须先关闭 G11（否则发布的是"回调不触发"的版本） | 质量前置 |

#### 存在不确定性（5 项）

| 目标 | 不确定性来源 | 判断 |
|---|---|---|
| G25 KubeJS 原生承载 | ① KubeJS 上游是否支持 26.2（未知，需查）；② "原生承载"等价于在 MG 上重建 NeoForge API 子集 + Rhino + KubeJS 自身 API + 附属 API；③ 与 <3MB 目标冲突 | 工作量与外部依赖双重不确定，**不能进承诺路径**，只排 spike |
| G17 Forge 兼容 | ① Forge 在 26.x 的维护状态未知；② LGPL clean-room 的边界成本高（需重写整套 FML 语义）；③ 与 NeoForge 兼容层大量重叠 | 建议**明确不做**，或降级为"能加载最简 Forge mod"的 PoC |
| G19 客户端渲染兼容 / 客户端沙盒 | 26.2 渲染管线（Blaze3D/GpuBackend）变化大；多 JVM 客户端沙盒已被总纲判死 | 降级为"只做渲染层注册子集"，沙盒明确放弃 |
| 兼容率目标（10 选 5 / 20+ mod） | "跑通"未定义：能启动？能进世界？功能正确？无 ERROR？ | 必须先定义判据（Q1），否则验收不可执行 |
| 性能目标（启动 <2s） | 26 mixin + 早期窗口 + N 个 mod 的 ASM 扫描；从未测量 | 需先测基线（T1.6），再决定是否修订 |

### 3.3 结构性矛盾（必须由决策者裁决，不能靠排期消化）

1. **体积 vs 生态**：`<3MB` 与 KubeJS 承载不可兼得（F4）。当前 2.68MB 已用掉 89% 预算。建议把"核心 jar <3MB"改为"核心 jar <3MB，KubeJS 作为独立可选模块按需加载"，从而保留两个目标。
2. **"零依赖" vs 版本伪装**：D11 要求不引用其他加载器任何类；但"按 mod 报录制版本"需要拦截 mod 对其他加载器版本 API 的调用——这只能在 MG 自己的 stub 里做，不能加载真 NeoForge。技术上成立，但要求 stub 面足够广，等于把兼容层做成"API 面模拟器"，工作量随 mod 复杂度非线性增长。
3. **"不静默失败" vs <2s 启动**：每个 Mixin/注入点都做目标签名校验会加启动开销；建议把校验做成"一次构建期校验 + 启动期轻量校验（只查类存在）"，避免每次启动全量反射。
4. **单人产能 vs 目标总量**：现有 16.2k 行覆盖了 MG 内核 + 双兼容层雏形；剩余目标（KubeJS、Forge、MID-S、客户端）体量是现有代码的数倍。**本计划的 Phase 0–4 是"能对外交付一个可用加载器"的最短路径；Phase 5–7 是愿景，必须按条件触发，不能当承诺。**

## 4. 分期路线图

### 4.0 排序原则

1. **先收口再前进**：工作区有 3 条并行 WIP，不先提交就无法二分定位任何回归。
2. **先基线再改代码**：没有"构建绿 + 冒烟关键字"基线，后面每一次改动都是盲改。
3. **先修断链再扩广度**：F1 让 Fabric 整层失效，此时继续加 20 个事件类等于往断路里铺轨。
4. **先前置再目标**：Gradle 插件依赖 api 发布；MID-S 依赖 IR 稳定；KubeJS 依赖 NeoForge API 面子集。倒序执行必然返工。
5. **每期出口 = 下期入口**：任何一期验收不过，不进入下一期；不设"并行追赶"。

### 4.1 Phase 0 · 收口与基线（P0，最高优先，1 周量级）

**目标**：把工作区从"3 条 WIP 混在一起"变成"干净基线 + 可重复验证"。

**入口条件**：无（立即开工）。

**关键动作**
- 拆 3 批提交（早期窗口 / LS+Launcher / Fabric P1），按 `AGENTS.md` 规则 5 只用 `git add <指定文件>`。
- 补注册 8 个 Fabric Mixin（F1）。

- 写 `scripts/smoke_check.ps1` + `docs/smoke-baseline.txt`（关键字断言集合）。
- 台账收口：登记表清空"进行中"、`PROJECT-STATUS.md` 标废弃、`AG-总计划.md` 标历史。

**里程碑 M-P0**：`git status` 干净；`./gradlew build` 绿；冒烟脚本对一次成功启动返回 0；三份台账与代码一致。

**验收标准**
1. `git status --short` 输出为空。
2. `./gradlew build` BUILD SUCCESSFUL，任务数 ≥ 48。

**出口 → 进入 Phase 1 的前提**：M-P0 四条全过。

### 4.2 Phase 1 · 内核加固：把"能跑"变成"可依赖"（P0，1–2 周量级）

**目标**：让 MG 内核具备"改动后能判断有没有坏"的属性，为后续所有兼容层工作提供稳定地基。

**入口条件**：Phase 0 出口达成（干净基线 + 冒烟脚本）。

**关键动作**
- 注入点自检（构建期 + 启动期两级），消灭"配置加载成功但注入没生效"的幽灵 bug。
- MEL 错误分级落地（`ErrorLevel` + `MirageException` + 统一前缀），替换裸 `printStackTrace`。
- 模块懒加载（G9）：`META-INF/mirage-module.json` + `requires` 解析 + 动态 `addURL`。
- LS phase 3 `ModuleHandle`（AG 模块接入契约）。
- 已知 bug 清理：`GL ERROR 65538`、`handoff()` 顺序。
- 性能与体积基线测量（启动耗时、jar 体积、内存）。

**里程碑 M-P1**：MG 0.5 "可依赖内核"——任何注入点失效都会响亮报错而不是静默退化；体积/耗时数字落文档。

**验收标准**
1. 故意把一个 Mixin 的 `@Inject(method=...)` 方法名改错 → 启动 FATAL，日志指明"类 + 方法 + mixin 名"。
2. 三类错误各有一例可 grep：`[MG-FATAL]` / `[MG-WARN]` / `[MG-IGNORE]`。
3. 一个声明 `requires: ["mirage-config"]` 的测试 mod 触发模块加载日志；不声明则不加载。
4. `docs/perf-baseline.md` 含：冷启动到 TitleScreen 耗时、fat jar 体积、峰值内存。

**出口 → Phase 2 前提**：验收 1–4 全过；且 `build` 仍绿。

### 4.7 Phase 6 · 语义层：MID-S 与整合包魔改（P2/P3，4–6 周量级）

**目标**：实现"第五生态"的差异化能力——整合包作者用声明式 JSON 改游戏，不写 Java。

**入口条件**：Phase 5 出口达成（IR 能重放是 MID-S 编译的前置）。

**关键动作**
- 冻结 MSF（MID-S）schema，先四类最小语义：改数值 / 加方块 / 删配方 / 改战利品。
- MSCP 语义编译器（MSF → IR `transforms` + `registries`）。
- MCR 冲突解决（同目标多语义：报错 / 显式优先级，禁止静默覆盖）。
- MPK 极简 pack 格式（`pack.mirage.json` + MID 列表 + 加载顺序）。
- 端到端：手写一个 MSF 文件，游戏内出现新方块 / 配方被删。

**里程碑 M-P6**：整合包作者可通过 JSON 完成一次真实魔改，无需 Java 与重新编译。

**验收标准**
1. 手写 MSF（加一个方块 + 删一个原版配方）→ 启动后创造栏出现该方块、配方书里该配方消失。
2. 语义冲突样例（两个 MSF 改同一数值）→ 启动 FATAL 且信息列出两个来源文件。
3. 编译器单测覆盖四类语义各 ≥2 例（正例 + 边界）。
4. `docs/modder-guide.md` 增加"整合包魔改"章节，含完整可复制样例。

**出口 → Phase 7 前提**：验收 1–4 全过。

### 4.9 依赖图（串行，无断链）

```
Phase 0 收口+基线
   │  (git 干净 / build 绿 / 冒烟脚本可用)
   ▼
Phase 1 内核加固 (自检 / MEL / 懒加载 / LS phase3 / 性能基线)
   │  (注入点失效必报错)
   ▼
Phase 2 Fabric 闭合 (修 F1 → events → registry → AT → 矩阵)
   │  (3 真实 mod 通过)
   ▼
Phase 3 NeoForge 收口 (stub / 扫描 / data 复核 / 矩阵)
   │  (3 真实 mod 通过)
   ▼
Phase 4 工具链 + v0.1.0 (api 发布 → 插件 → MDK → 文档 → tag)
   │  (外部开发者可用)
   ▼
Phase 5 转译闭环 (schema → IR 消费 → MSR P1/P2 → 端到端)
   │  (1 mod 全链路重放)
   ▼
Phase 6 MID-S (schema → MSCP → MCR → MPK → 魔改验收)
   │
   ▼
Phase 7 生态扩展 (条件触发，先出报告)
```

**为什么必须串行**：Phase 2/3 的验收依赖 Phase 1 的注入点自检（否则新注入点失败无法区分是"写错"还是"没注册"）；Phase 4 的发布依赖 Phase 2/3 的真实 mod 通过（否则发布的是"回调不触发"的版本，重演 F1）；Phase 5 的 IR 消费依赖 Phase 4 已发布的 api 形状；Phase 6 依赖 IR 稳定；Phase 7 依赖 NeoForge API 面子集稳定。

2. 每期验收后：在本文件对应 Phase 块追加"实际完成日期 + 偏差说明"，不删原文。
3. 出现新阻塞：先改 §3 分类，再改 §4 顺序，**不要**只在聊天里说。
4. 本文件不承载 bug 与逐轮改动（那是 `docs/已知bug.md` / `docs/更新日志.md` 的职责）。
