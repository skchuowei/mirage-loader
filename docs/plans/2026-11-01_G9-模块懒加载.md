# G9 模块懒加载（`requires` → 动态 addURL，"不调用不加载"）

> 关联：AG 总计划 `docs/plans/2026-10-31_AG-总计划重梳理.md` 的 **G9** 与 **T1.3**；
> 前置：F1 接线（`ee5d403`）、Mixin 注入点自检（`c17c70b`）、性能埋点（`1fed9e4`）。

## 目标

让「可选模块」（配置系统 / Kotlin 支持 / 网络层 /将来的 KubeJS 等重依赖）
**默认不进 fat jar、不参与启动期扫描**，只有当某个 mod 在描述符里显式声明
`"requires": ["<模块 id>"]` 时，该模块的 jar 才被动态加入类加载器并执行其初始化入口。

**可验证标准**（完成时怎么判断 done）：

1. 模块 jar 内含 `META-INF/mirage-module.json`，声明 `id` / `version` / `provides` / `requires` / `entrypoint`。
2. mod 的 `META-INF/mirage.mod.json` 新增 `requires` 字段（**模块 id 数组**，与既有的
   `depends`（mod 依赖，modId→版本范围）语义区分）。
3. 声明了 `requires:["mirage-config"]` 的 mod → 日志出现
   `[LS] 模块已加载: mirage-config v0.1.0 (jar=..., 需求来源: modA)`；
   **未**声明 → 日志出现 `[LS] 模块跳过: mirage-kotlin v0.1.0 (无 mod 声明 requires)`，
   且该模块 jar **不在** 类加载器 URL 列表里。
4. 模块间依赖可传递闭包（A 依赖 B，B 依赖 C → 加载 A 时 B、C 一并加载）。
5. 声明了但仓库里不存在的模块 → **WARN 并继续启动**（模块是可选增强，不是硬依赖）。
6. `scripts/verify_module_loading.ps1` 纯 JVM 回归全绿 + 变异检验全红。
7. `docs/architecture.md` 补上模块加载时序。

## 前置条件与阻塞项

* 上游：F1 接线已完成（Fabric 桥接不再是死代码）；注入点自检已落地。
* 工作区状态：干净（`1fed9e4` 已推送），无他人 WIP 冲突。
* **可立即开干**，但有一项**外部依赖**留给用户（见「验证步骤」§实机部分）：
  实机验证需要把模块 jar 放进 `<gameDir>/modules/`，而 `mc-shili/` 是用户的游戏目录
  （规则 8：未经同意不得修改）——因此**本轮只交付构建产物与命令，不自动写入 `mc-shili/`**。

## 现状分析

### 已有能力

* `MirageClassLoader.addJar(File)` 已存在（`core/mirage-loader/.../MirageClassLoader.java:29`），
  走 `URLClassLoader.addURL`，可把任意 jar 加进搜索路径。
* S3（`TransformStage`）是 classloader 的创建点，也是**唯一的** URL 组装点：
  `java.class.path` 全量 URL + 每个 mod jar（`mcl.addJar`）。
* `ModManifest`（`core/mirage-loader/.../ModManifest.java`）是 `mirage.mod.json` 的 POJO，
  Gson 直接映射，`depends` 字段是 mod 级依赖（modId → 版本范围）。

### 缺口（AG 总计划 G9 原文：「`MirageClassLoader.addJar` 在；无 `META-INF/mirage-module.json`
### 约定、无 `requires` 解析、无按需加载日志」）

1. **无模块描述符格式**：没有任何地方定义「什么是模块」「模块 id 是什么」。
2. **无模块仓库概念**：三个空壳模块 `mirage-config` / `mirage-kotlin` / `mirage-network`
   只有 `build.gradle.kts`，各产一个 0.1.0 的**空 jar**，既不进 fat jar
   （`launcher/mirage-launch/build.gradle.kts` 的 `implementation` 里没有它们），
   也没有任何地方去加载它们——它们是「建了目录但没接线」。
3. **无 `requires` 解析**：`ModManifest` 里没有「这个 mod 需要哪个模块」的概念。
4. **无按需加载日志**：即使把模块 jar 塞进 classpath，也无从观测「加载了哪些、为什么加载」。

### 本设计要踩的最深的坑（必须写进实现）

**`io.mirage.` 前缀在 `MirageClassLoader.loadClass` 里被无条件委派给 `SystemClassLoader`**
（`MirageClassLoader.java:54`，例外只有 `io.mirage.neoforge.` / `io.mirage.fabric.` /
`io.mirage.mgscript.`）。这条规则的动机是「保证 Launcher 和 MC 渲染线程看到同一份类」
（否则 `net.minecraft.*` 会被 app loader 与 mcl 各定义一份 → `LinkageError: loader constraint
violation`，见 `docs/经验与踩坑.md` C11 / C25）。

推论：**模块提供的公共 API 类不能放在 `io.mirage.` 包下**。否则 mcl 会把它委派给
app loader，而模块 jar 只在 mcl 上、不在 app loader 的 classpath → `NoClassDefFoundError`。
因此本设计规定：

> 模块的公共 API 包名**不得**以 `io.mirage.` 开头（约定用 `dev.mirage.<模块>` 等），
> 并在描述符的 `provides` 里声明自己提供的 API 包前缀。

模块**实现**类若需要用 Mirage 自有能力（`DeferredRegister` 等），那些在
`io.mirage.api.*` 下、随 fat jar 走 app loader——模块由 mcl 加载后引用它们时，
委派给 app loader 拿到的是同一份，**安全**。

## 每处改动要点

### 1. 模块描述符（`ModuleDescriptor`）

```json
{
  "id": "mirage-config",
  "version": "0.1.0",
  "provides": ["dev.mirage.config"],
  "requires": [],
  "entrypoint": "dev.mirage.config.ConfigModule"
}
```

* `id`：模块唯一 id，正则 `[a-z][a-z0-9-]{1,63}`（与 mod id 同风格）。
* `version`：语义化版本。
* `provides`：本模块提供的**公共 API 包前缀**（供文档与校验用；不得是 `io.mirage.` 前缀）。
* `requires`：本模块依赖的其他模块 id（参与闭包）。
* `entrypoint`：可选，模块初始化入口类全限定名（由 mcl 加载后反射调 `init()` 或静态 `setup()`）。

### 2. 模块注册表（`ModuleRegistry`）

* **仓库目录**：默认 `<gameDir>/modules/`；可用系统属性 `mirage.modules.dir` 覆盖。
  目录不存在 → 视为「没有可选模块」，静默跳过（**不是**错误）。
* **扫描**：目录下 `*.jar` → 读 `META-INF/mirage-module.json` → 有则登记为模块；
  无则忽略（普通 jar 不该被当模块）。
* **需求集合**：所有 mod 的 `manifest.requires` 并集。
* **闭包**：`需要 = 需求集合 ∪ {每个需要模块自身的 requires}`，递归展开；
  **循环依赖**要能终止（用 visited 集合）。
* **加载**：对闭包内每个模块 → `mcl.addJar(jar)` → 打加载日志（含需求来源 mod id）→
  若有 `entrypoint` → `Class.forName(entrypoint, true, mcl)` + 反射调 `init()`（无则调静态 `setup()`）；
  入口抛异常 → **WARN 并继续**（模块初始化失败不该让整个游戏起不来）。
* **跳过**：仓库里有、但不在闭包内的模块 → 打「跳过」日志（debug 级，避免刷屏）。
* **缺失**：mod 声明了但仓库里没有 → **WARN**（列出 mod id 与缺失模块 id），继续启动。

### 3. mod 侧 `requires`

`ModManifest.requires`（`List<String>`）。Gson 自动映射 `mirage.mod.json` 的 `"requires"`。
语义与既有 `depends` 区分：`depends` = mod 依赖（modId → 版本范围）；
`requires` = **模块**依赖（模块 id 列表）。

### 4. S3 接线（`TransformStage`）

在 mcl 创建 + mod jar 全部 `addJar` 之后调用：

```java
ModuleRegistry.Result r = ModuleRegistry.load(ctx.gameDir(), mcl, mods);
ctx.properties().put("S3.modules", r);
```

`Result` 持有已加载模块 id 集合、跳过集合、缺失集合，供后续阶段/文档/调试查询。

### 5. 包名约定守卫

`verify_module_loading.ps1` 里加一条**源码守卫**：三个模块的 `provides` 前缀都不得以
`io.mirage.` 开头（否则必然 `NoClassDefFoundError`——见「现状分析」的坑）。
这条守卫比「读文档记住约定」可靠。

## 回归测试影响面

* **风险 1**：`ModuleRegistry` 在 S3 里 `addURL` 会不会破坏既有类加载？
  模块 jar 是**新**的 URL，不覆盖既有类（URL 顺序：新加的在末尾，先命中先加载的仍是原 URL）。
  → 用 `verify_module_loading.ps1` 的「模块 jar 不在 classpath 时 mod 引用模块类 → 明确失败」
  与「加载后 → 能找到」两条对照断言。
* **风险 2**：模块 jar 名字与既有 classpath 上的 jar 重名 → 先命中的赢，可能加载到旧版。
  → 守卫：模块 id 与仓库内 jar 文件名不同时只按描述符 id 登记；日志打出 jar 绝对路径。
* **风险 3**：`requires` 字段名与将来 IR 描述符的 `dependencies` 混淆。
  → 本轮**只**支持 legacy `mirage.mod.json` 的 `requires`；IR 描述符路径不动（IR 仍是「只解析不重放」）。
* **风险 4**：新增字段让 Gson 反序列化报错？`requires` 缺失时 Gson 给 `null`，
  代码里必须按 null 处理（`ModuleRegistry` 收集需求时对 null 跳过）。
* **零侵入**：`mirage-fabric-compat` / `mirage-neoforge-compat` / `mirage-mgscript` /
  `mirage-mixin` / `mirage-eventbus` / `api` 全部不改。
* **mdk-example 冒烟步骤**：不变（不声明 `requires` 就没有模块被加载，行为与现在完全一致）。

## 实施结果与偏差（2026-11-01 收尾时补记）

上文是**实施前**的计划。实际落地时出现了 5 处偏差，逐条记录（原文保留不删）：

### 偏差 1：多抽了一个 `ModuleGraph`（计划里没有）

**原因**：原计划让 `ModuleRegistry` 同时负责「扫描仓库 / 收集需求 / 求闭包 / 加 URL / 调入口」。
但 `ModuleRegistry` 依赖 `MirageClassLoader` / `ModContainer` / `NeoForgeModDetector`，
**没法脱离游戏编译**，于是离线回归只能测到 `ModuleDescriptor.parse` 一小段。

更糟的是：最初版本的检查程序在**测试里重写了一遍闭包算法**——
那样测的是副本，生产代码改了测试照样全绿（这正是「全绿的测试可能根本没测到东西」）。

**改法**：把「需求收集 + 依赖闭包」抽成 `io.mirage.loader.module.ModuleGraph`
（只依赖 `ModuleDescriptor` 与纯 POJO `ModManifest`），`ModuleRegistry` 委派给它。
检查程序直接调 `ModuleGraph` 的 public 静态方法 —— **测的是生产代码本身**。
另加一条源码守卫：`ModuleRegistry` 必须委派，否则两份算法迟早漂移。

### 偏差 2：`mirage-kotlin` / `mirage-network` 补了桩入口类（计划只写了 config）

**原因**：两个模块的描述符声明了 `provides: ["dev.mirage.kotlin"]` 却**没有对应源码包**——
mod 真去 `import dev.mirage.kotlin.*` 必然 `NoClassDefFoundError`。这是描述符与代码不一致。
回归脚本的守卫直接把它抓了出来（2 个 FAIL）。

**改法**：两个模块各补一个 `static init()` 桩类（`KotlinModule` / `NetworkModule`），
描述符的 `entrypoint` 填上。**它们仍然是桩**（Kotlin 模块没带 kotlin-stdlib，
网络模块没实现网络能力），但至少「声明的 API 前缀下真的有类」这条成立了。
守卫同步加强：`provides` 前缀下**至少一个类**、且 `entrypoint` **必须有对应源码**。

### 偏差 3：`archivesBaseName` 与 Gradle 9 不兼容

原计划在三个模块的 `build.gradle.kts` 里写了 `archivesBaseName.set("mirage-config")`。
Gradle 9.1 已移除该 API（8.x 起废弃），构建直接失败：
`Unresolved reference 'archivesBaseName'`。

**改法**：删掉这三行。gradle 默认用项目名做 archiveBaseName，而项目名本来就是
`mirage-config`，产物仍是 `mirage-config-0.1.0.jar`，**与 `ModuleRegistry.moduleJar`
「文件名以模块 id 开头」的匹配约定一致**。注释里写明这个隐含依赖。

### 偏差 4：`ModuleDescriptor` 的 multi-catch 是编译错误

初版写的是 `catch (JsonParseException | RuntimeException e)`——
`JsonParseException` 本身就是 `RuntimeException` 的子类，**Java 不允许 multi-catch 捕获有继承关系的两个类型**。
这是离线回归第一次运行时抓出来的（javac 报错），比 gradle 构建早一步。

### 偏差 5：验证脚本加了「报告落盘」

`Write-Host` 走 PowerShell 的信息流，管道/`2>&1` 都捕获不到，
导致「脚本跑了但看不到明细」。脚本现在把全部明细写到 `$ReportFile`
（默认 `%TEMP%\verify_module_loading.report.txt`），顺带对 CI 有用。
