## 2026-11-14 · fix(scripts): W3-C 一键诊断 .bat 命令乱码修复（新门禁 85/85，含 cmd 端到端验证）

- **用户现象**：双击 `scripts/run_w3c_diag.bat` 报 `'杩囦竴娆★級' 不是内部或外部命令`、`'MODE_FULL' 不是内部或外部命令`、`AT 命令已弃用`、`绑定句柄无效`、`'KWORK"'`、`'FATWORKPROBE_SRC"'`、`系统找不到指定的路径`。
- **根因**：该文件是 **UTF-8 中文 + 裸 LF + 无 BOM**。cmd.exe 按 OEM 代码页 CP936 逐字节解析 `.bat`，UTF-8 三字节汉字被 GBK 双字节切分后吞掉相邻的 `"` / `%` / `(`，或解出 `&` / `AT` / 括号等命令元字符 ⇒ 提示文本被当命令执行、`set "WORK=..."` 被截断、`goto` 被拆行；裸 LF 还破坏 `if (...)` 多行块。`chcp 65001` 写在第 2 行无效（cmd 已完成词法解析），加 UTF-8 BOM 更会让首行命令名被污染。
- **修法**：`.bat` 降级为 **16 行纯 ASCII + CRLF 跳板**，只负责 `@echo off` → `powershell.exe -File "%~dp0run_w3c_diag.ps1" %*` → `pause >nul` → `exit /b`；中文四档菜单、门禁调用、探针编译运行全部迁到新建的 `scripts/run_w3c_diag.ps1`（**UTF-8 WITH BOM + CRLF**，PS 5.1 才能正确读中文，符合项目铁律）。跳板不含 `set /p`/`goto`/`if (...)`/`chcp`/非 ASCII/命令元字符。
- **配套**：新增 `.gitattributes` 锁 `*.bat text eol=crlf`（本机 `core.autocrlf=true` 但仓库原本无此文件，工作树仍是裸 LF；文本属性才是跨机器契约）；`mdk/mdk-example/build.bat` 同类隐患一并统一（中文 REM 改英文 + CRLF，**不动它的命令逻辑**）。
- **搬迁时踩到的两个独立坑**：① `$exitCode = Invoke-BuiltinProbe` 把函数内 `& $javaExe` 的 stdout 全吞进变量，探针 `NEO_LOAD=` 输出看不见 ⇒ native 调用一律 `| Out-Host`；② PS 5.1 管道输出是系统 ANSI(GBK)，门禁按 UTF-8 解码会中文假红 ⇒ GBK 优先 / UTF-8 兜底。另 `ValidateSet` 属性会拒绝空默认串（交互菜单需要），已去掉；`pause` 收敛到 `.bat` 一处，避免双击停两次。
- **验证**：新增 `scripts/verify_bat_launcher.py` **85/85** = 守卫层 52/52（`*.bat` 逐字节：无 BOM / 纯 ASCII / 全 CRLF / 零元字符 / 无 chcp；`.ps1`：BOM / 零裸 LF / 中文菜单与四档分支行首锚点）+ 行为层 19/19（`-Mode 4` 退出档、`-Mode 3` headless 探针档、以及 `CREATE_NO_WINDOW` + `stdin=DEVNULL` 让 **cmd 真的解析一次 .bat**，断言中文正常、退出码 0、5 种报错形态全部不出现）+ 变异层 14/14（9 个 `%TEMP%` 副本落盘变异全红且判红原因对应、编译路径自检、源文件字节级未变）。回归 `msr_w3c_c1_gen.py --check` = 25 文件/29 类/CHANGED=0、`verify_w3c_c1_events.py` 36/36 仍绿。

## 2026-11-01 · feat(g9): 模块懒加载落地——「不声明不加载」

- **范围**：新增 `io.mirage.loader.module` 包三个类（`ModuleDescriptor` / `ModuleGraph` / `ModuleRegistry`）；`ModManifest` 加 `requires` 字段；`TransformStage`（S3）接线；三个可选模块补描述符与桩入口类；新增 `scripts/verify_module_loading.ps1`；`docs/architecture.md` 补实际时序。不改 Mixin 注册、不改注册表语义、不改生命周期顺序。

- **机制**：
  - 模块 jar 内含 `META-INF/mirage-module.json`（`id` / `version` / `provides` / `requires` / `entrypoint`）；

## 2026-10-31 · fix: 退出游戏时 `glfwDestroyWindow` 原生崩溃（双 glfw.dll 实例 × 跨实例销毁）

- **现象**：正常进入标题界面后点「退出游戏」→ 进程无 MC crash-report，直接落 `hs_err_pid*.log`；`latest.log` 最后一行只有 `Stopping!`。
- **现场**：`hs_err` 崩溃线程为 `Render thread`，Native 帧 `C [glfw.dll+0x77a0]`；Java 栈 `GLFW.glfwDestroyWindow → blaze3d Window.close → Minecraft.close+135 → exitWorldAndClose+53 → Main.main`；`RCX=0`、`RBX` 指向全零内存。
- **定位过程**（可复用的方法论）：
  1. 解析 `glfw.dll` 导出表定位函数：`0x7720..0x7800 = glfwDestroyWindow`，崩溃指令 `0x77a0: mov rax,[rcx]` —— 正是「从窗口链表摘除自己」的遍历循环（`while (prev->next != window) prev = prev->next;`），`rcx` 取自 `_glfw.windowListHead`。
  2. 静态排除：全 MC jar 只有 `Window.close()` 调 `glfwDestroyWindow`、只有 `Minecraft.close()` 调 `glfwTerminate`，且 `Minecraft.close()` 本次只跑一次（`Stopping!` 仅 1 行、无 `Shutdown failure!`）→ 排除「重复 close」。
  3. 反查 `hs_err` 的已加载模块列表 → **关键证据：`glfw.dll` 被加载了两份**（`...\natives\lwjgl\glfw.dll` 与 `...\natives\lwjgl\3.4.1-snapshot\x64\glfw.dll`），崩溃 PC 落在后者。
  4. 结论：早期窗口由 Launcher（App 侧 GLFW）创建，登记在**实例 A** 的窗口链表；MC 的 `Window.close()` 走 `MirageClassLoader` 侧 GLFW（**实例 B**），B 的链表是空的 → 摘链遍历把空 head 当节点 → 读 `0x0`。
- **为什么平时不炸**：`glfwSetWindowTitle` / `glfwPollEvents` / `glfwSwapBuffers` 等只操作传入的结构体指针（两份 dll 同版本、布局一致），所以整局游戏正常；只有 `glfwDestroyWindow` 需要访问**链表**，退出时才暴露。
- **改动点**：
  - `MirageEarlyWindow.destroyWindow(long handle)`（新增）：句柄等于早期窗口时，用**创建时那套 GLFW 实例**销毁，并把 `window` 置 NULL 保证幂等；其他句柄原样 `GLFW.glfwDestroyWindow`。
  - `MirageTransformer.transformWindow`：除既有的 `createGlfwWindow` 织入外，新增把 `Window.close()` 内的 `glfwDestroyWindow(J)V` 改道到 `MirageEarlyWindow.destroyWindow(J)V`（打印 `[Mirage] 织入 Window.close() -> 早期窗口销毁改道`）。
  - 该改道顺带覆盖了 `Minecraft` 构造期「后端创建失败 → `window.close()` 重试下一个 GpuBackend」的路径（`Minecraft` 偏移 1325）。
- **验证方式**：构建 `:launcher:mirage-launch:fatJar` → 备份并部署到 `mc-shili/libraries/io/mirage/mirage-launch/0.1.0/`（备份 `.bak-20261031-prequitfix`）→ 实机启动进标题界面再退出，日志依次为
  `Stopping!` → `[Mirage] 早期窗口由创建方 GLFW 实例销毁 (handle=0x14b84402050)` → `[LS] stage S7 Loaded done` → `[LS] pipeline finished` → `游戏已退出。`；**无 `hs_err_pid*.log`、无新 crash-report**。

## 2026-10-25 · fix: 早期窗口渲染线程未绑 GLCapabilities，首帧 glViewport 触发 JVM FatalError

- **范围**：`launcher/mirage-launch`（早期窗口，第四轮 Forge 式窗口的冒烟修复）。
- **背景**：用户双击 `启动 26.2-mirage.bat` 冒烟，现象为「早期窗口刚显示出来 → 日志走到 `[Mirage] 扫描 4 个 jar` → 进程无声退出，无 crash report」。控制台末尾：
  `FATAL ERROR in native method: Thread[#26,Mirage-EarlyDisplay,5,main]: No context is current or a function that is not available in the current context was called. The JVM will abort execution. at org.lwjgl.opengl.GL11C.glViewport(Native Method) at MirageEarlyWindow.renderFrame(MirageEarlyWindow.java:226)`
- **根因**：LWJGL 的 `GLCapabilities` 是 **ThreadLocal**（`GL.capabilitiesTLS`，已 javap 实证），`GL11C.glViewport` 是 native 方法，JNI 侧按**当前线程**取函数指针表。`MirageEarlyWindow.initWindow()` 只在主线程调了一次 `GL.createCapabilities()`，`renderTick()` 只做了 `glfwMakeContextCurrent(window)` 就直接画，**渲染线程上没有任何 capabilities** → 渲染线程第一条 GL 调用 `renderFrame` 的 `glViewport` 就被判成 "No context is current"，走 `JNIEnv->FatalError` 直接 abort JVM（所以没有 Java 异常、没有 crash report）。对照 Forge `fmlearlydisplay/DisplayWindow.java:219` 同样在渲染循环里调 `createCapabilities()`。
  - 旁证：`Mirage-EarlyDisplay` 线程在窗口显示后 50ms 才跑第一帧，与 mod 扫描日志几乎同时发生，故现象看起来像"扫描时崩"，实际是首帧就崩。
  - 顺带排除的一条假说：`io.mirage.earlydisplay`（AppClassLoader）与 MC（MirageClassLoader）各有一份 `org.lwjgl.*`，是否会撞 "Native Library already loaded in another classloader"？**用双 URLClassLoader 最小实验（`.tmp_dbg/DualLoad.java`，两套 loader 各 `glfwInit()` + 加载 `GL11C`）实测：两次都正常返回 true，LWJGL 3.4.1 不触发该错误**，双副本目前可用。

## 2026-10-18 · docs: AGENTS.md 技术注意事项追加 6 节——Mixin 编写 API 误区

- **范围**：`AGENTS.md` → "MC Mod 工程技术注意事项" 章节。
- **背景**：复盘 paging-fix 方案设计时发现的一批 Mixin API 误解和字节码假设漏洞。
- **改动点**：
  - **第 10 节 @Shadow vs 继承**：mixin 访问目标类 protected 字段必须用 `@Shadow`，继承父类写法 javac 直接报错；
  - **第 11 节 @Redirect 不能假设调用链**：写 @Redirect 前先 `javap -c` 反编译，确认所有调用路径都经过拦截点，漏一条就是点击穿透 bug；
  - **第 12 节 @Invoker/@Accessor 签名严格**：写错静默失败，不报错；
  - **第 13 节 ASM 版本校验位置**：`Unsupported class file major version` 只在 ClassReader 阶段抛出，ClassWriter 不再校验；maxCompatibilityLevel 不校验目标类版本——两个常见误区；
