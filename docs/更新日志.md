- **问题**（P0 遗留，roadmap 缺陷表 1/3/6 + 一条盘点时未列出的）：
  1. mod 构造里一句 `System.exit` 杀的是 **launcher 进程本身**（同 JVM），录制还没收尾整个启动就没了；
  2. 超时只 `join(2000)` 不 `interrupt`，线程带着 `setDaemon` 继续跑，且**半成品 `touched_apis` 照常写进缓存**；

  4. `.mid-cache` 只校对 `agVersion/jarSha256/mcVersion`，fake 表面扩充后老 `recorded` 仍命中（数据与现实不符）。
- **改动点**：
  1. **退出拦截**（新增 `SandboxKillException` / `SandboxGuard` / `SandboxBytecodeGuard`）：`SandboxClassLoader` 重写 `findClass`（挂点是 `findClass` 不是 `defineClass`——mod 类由继承的 `URLClassLoader.findClass` 定义），用 ASM 只替换调用：`System.exit(I)V`→`SandboxGuard.exit(I)V`、`Runtime.exit|halt(I)V`→`SandboxGuard.exitRuntime|halt(Ljava/lang/Runtime;I)V`。**栈形状不变 ⇒ 不重算帧**（`ClassWriter(cr, 0)`），避开"ASM 改写丢帧后 Mixin 二次转换失败"的老雷。先探测后改写，未命中原样返回原数组。
  2. **超时**：`join` 后补 `interrupt`，置 `failed=true, incomplete=true, error="timeout"`；`incomplete` 时 `touched_apis`/`registered_events` 清空、`deferred_register_count=0`；`ModDiscoverer` 只写 detected 不写 recorded（半成品一旦入库会被后续启动当有效数据，错误永久固化）。
  3. **全局态**：录制前快照 / `finally` 恢复 `Locale`、`TimeZone`、`System.getProperties()`（删掉 mod 新加的键、原有键逐个写回）。
  4. **fake 指纹**：`SandboxRecorder.fakeVersion()` = fat jar 内 `mirage/sandbox-fake/**` 的 `name:size:crc` 排序摘要（16 位 hex）。`Entry.fakeVersion` 落盘，`lookup` **只在 `recorded != null` 时**校对（检测结果不依赖 fake 表面，不该被连坐失效）；`specVersion` 0.2 → 0.3。
  5. **补 `defineClass` 保护域**：接管 `findClass` 后默认保护域会丢 `CodeSource`，而少数 mod 靠 `getProtectionDomain().getCodeSource().getLocation()` 定位自己的 jar → 显式构造 `ProtectionDomain`（指向 mod jar）。
- **顺带修的 P0 坑**：P0 的 fake 包枚举把 `jar:file:/x.jar!/mirage/sandbox-fake/` 的 `getPath()` 直接喂 `new File(...)`，Windows 上是非法路径、异常被 `catch(Exception ignore)` 吞掉 → **fake 扫描一直静默失败**，靠写死的 `net.minecraft./net.neoforged.` 兜底才"看起来正常"。这也意味着 P0 的 fake 表面从没有过按内容判定的能力，指纹因此一直无法实现。现改为「先取本类 code source（生产 = fat jar，dev = classes 目录）再扫，资源枚举只作补扫」，且 `file:` 前缀先切掉再转 `File`。

## 2026-10-31 · test(log): 补 MirageLog 回归用例 `scripts/verify_logging.ps1`

- **范围**：验证脚本 + 文档，不改运行时代码（`MirageLog` 一行未动）。
- **缘由**：AGENTS.md 规则 7.3 要求本轮新特性当场补验证。项目无 JUnit 依赖，验证产物统一是
  `scripts/verify_*.ps1`；`MirageLog` 只依赖 JDK 标准库，可以脱离 gradle 与游戏直接测。
- **做法**：脚本用 `javac` 现场编译 `MirageLog` + 一个检查程序到临时目录，跑 **5 个独立 JVM**
  （级别在静态初始化时读取，一个进程只能测一个级别）：默认 / `level=warn` / `level=debug` /
  `level=off` / `stack=none`。检查程序放在 `io.mirage.api.log.check` 包内，使栈帧命中
  `io.mirage.` 前缀，才能真正验到 smart 模式的"项目帧保留"。
- **断言 41 项**，四条契约：① 异常链展开（`InvocationTargetException` /

## 2026-10-31 · fix: 退出游戏时 `glfwDestroyWindow` 原生崩溃（双 glfw.dll 实例 × 跨实例销毁）

- **现象**：正常进入标题界面后点「退出游戏」→ 进程无 MC crash-report，直接落 `hs_err_pid*.log`；`latest.log` 最后一行只有 `Stopping!`。
- **现场**：`hs_err` 崩溃线程为 `Render thread`，Native 帧 `C [glfw.dll+0x77a0]`；Java 栈 `GLFW.glfwDestroyWindow → blaze3d Window.close → Minecraft.close+135 → exitWorldAndClose+53 → Main.main`；`RCX=0`、`RBX` 指向全零内存。
- **定位过程**（可复用的方法论）：
  1. 解析 `glfw.dll` 导出表定位函数：`0x7720..0x7800 = glfwDestroyWindow`，崩溃指令 `0x77a0: mov rax,[rcx]` —— 正是「从窗口链表摘除自己」的遍历循环（`while (prev->next != window) prev = prev->next;`），`rcx` 取自 `_glfw.windowListHead`。
  2. 静态排除：全 MC jar 只有 `Window.close()` 调 `glfwDestroyWindow`、只有 `Minecraft.close()` 调 `glfwTerminate`，且 `Minecraft.close()` 本次只跑一次（`Stopping!` 仅 1 行、无 `Shutdown failure!`）→ 排除「重复 close」。
  3. 反查 `hs_err` 的已加载模块列表 → **关键证据：`glfw.dll` 被加载了两份**（`...\natives\lwjgl\glfw.dll` 与 `...\natives\lwjgl\3.4.1-snapshot\x64\glfw.dll`），崩溃 PC 落在后者。
  4. 结论：早期窗口由 Launcher（App 侧 GLFW）创建，登记在**实例 A** 的窗口链表；MC 的 `Window.close()` 走 `MirageClassLoader` 侧 GLFW（**实例 B**），B 的链表是空的 → 摘链遍历把空 head 当节点 → 读 `0x0`。
- **为什么平时不炸**：`glfwSetWindowTitle` / `glfwPollEvents` / `glfwSwapBuffers` 等只操作传入的结构体指针（两份 dll 同版本、布局一致），所以整局游戏正常；只有 `glfwDestroyWindow` 需要访问**链表**，退出时才暴露。

  - `MirageEarlyWindow.destroyWindow(long handle)`（新增）：句柄等于早期窗口时，用**创建时那套 GLFW 实例**销毁，并把 `window` 置 NULL 保证幂等；其他句柄原样 `GLFW.glfwDestroyWindow`。

  - 该改道顺带覆盖了 `Minecraft` 构造期「后端创建失败 → `window.close()` 重试下一个 GpuBackend」的路径（`Minecraft` 偏移 1325）。

## 2026-10-25 · fix: `MirageTestMixin` 回调非 static 织入 static 方法 → SharedConstants 转译失败 → S4 FATAL

## 2026-10-25 · fix: 早期窗口渲染线程未绑 GLCapabilities，首帧 glViewport 触发 JVM FatalError

- **范围**：`launcher/mirage-launch`（早期窗口，第四轮 Forge 式窗口的冒烟修复）。
- **背景**：用户双击 `启动 26.2-mirage.bat` 冒烟，现象为「早期窗口刚显示出来 → 日志走到 `[Mirage] 扫描 4 个 jar` → 进程无声退出，无 crash report」。控制台末尾：
  `FATAL ERROR in native method: Thread[#26,Mirage-EarlyDisplay,5,main]: No context is current or a function that is not available in the current context was called. The JVM will abort execution. at org.lwjgl.opengl.GL11C.glViewport(Native Method) at MirageEarlyWindow.renderFrame(MirageEarlyWindow.java:226)`
- **根因**：LWJGL 的 `GLCapabilities` 是 **ThreadLocal**（`GL.capabilitiesTLS`，已 javap 实证），`GL11C.glViewport` 是 native 方法，JNI 侧按**当前线程**取函数指针表。`MirageEarlyWindow.initWindow()` 只在主线程调了一次 `GL.createCapabilities()`，`renderTick()` 只做了 `glfwMakeContextCurrent(window)` 就直接画，**渲染线程上没有任何 capabilities** → 渲染线程第一条 GL 调用 `renderFrame` 的 `glViewport` 就被判成 "No context is current"，走 `JNIEnv->FatalError` 直接 abort JVM（所以没有 Java 异常、没有 crash report）。对照 Forge `fmlearlydisplay/DisplayWindow.java:219` 同样在渲染循环里调 `createCapabilities()`。
  - 旁证：`Mirage-EarlyDisplay` 线程在窗口显示后 50ms 才跑第一帧，与 mod 扫描日志几乎同时发生，故现象看起来像"扫描时崩"，实际是首帧就崩。
  - 顺带排除的一条假说：`io.mirage.earlydisplay`（AppClassLoader）与 MC（MirageClassLoader）各有一份 `org.lwjgl.*`，是否会撞 "Native Library already loaded in another classloader"？**用双 URLClassLoader 最小实验（`.tmp_dbg/DualLoad.java`，两套 loader 各 `glfwInit()` + 加载 `GL11C`）实测：两次都正常返回 true，LWJGL 3.4.1 不触发该错误**，双副本目前可用。
- **改动点**：`MirageEarlyWindow` 新增 `renderThreadCaps` 标记，`renderTick()` 在 `glfwMakeContextCurrent` 之后、首帧渲染之前调一次 `GL.createCapabilities()` 并打一行 `[Mirage] 早期窗口渲染线程已绑定 GL 能力: true`；`finally` 里 `glfwMakeContextCurrent(NULL)` 的行为不变（同一线程下一帧重新 current 时 capabilities 仍在）。
- **验证方式**：`gradle build` 基线先跑（BUILD SUCCESSFUL，47 tasks）；改动后 `:launcher:mirage-launch:build` + `:launcher:mirage-launch:fatJar` BUILD SUCCESSFUL；解包 fat jar 校验 `MirageEarlyWindow.class` 内含新日志串（命中 1）；已部署到 `..\mc-shili\libraries\io\mirage\mirage-launch\0.1.0\`（旧包备份 `.bak-20261025-earlycaps`）。**运行时冒烟待用户双击 bat 复验**——判据：控制台出现"渲染线程已绑定 GL 能力"，且能看到早期界面（红底/内存条/铁砧动画）真正在动，随后 `Window.createGlfwWindow` 交接后进入资源重载。
