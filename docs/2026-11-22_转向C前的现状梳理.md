## 0. 一句话结论

Mirage 目前是一个**能启动 MC 26.2、带 Fabric/NeoForge 双兼容层雏形、35 个 headless 门禁把关的独立加载器**，
内核（M0–M7、AG Phase 1 离线部分）基本成型，但**没有任何真实 mod 通过完整兼容性验收**；
按当前 clean-room 补类路线（W3-C）无法达成「全部加载器 mod 互通」——规模上追不上、架构上无事件注入点、
且 D11 与目标数学上互斥。因此转向路线 C（统一调度层），本文档记录转向前的完整基线。

## 1. 项目定位与目标

### 1.1 原始定位（PLAN.md）

- **Mirage Loader**：介于 Fabric 与 NeoForge 之间的轻量现代加载器，目标 MC 26.2 / Java 25。
- 差异化四件事：零依赖其他加载器运行时（D11）、核心只做类加载/织入/发现/生命周期、
  模块按需懒加载、吃 Fabric 生态（目标 50%+ 纯客户端 Fabric mod 免改运行）。
- 指标：启动 <2s、核心 jar <3MB、一行注解的开发者体验。

### 1.2 终极目标（2026-11-22 用户裁定，本次转向依据）

> **全部加载器 mod 全部互通** —— 不只 Fabric，也不只 NeoForge，而是三个生态的 mod 都能在 Mirage 上跑。

这条把"兼容率"从优化目标变成存在性目标，直接触发本次路线裁决。

### 1.3 术语

- **MG**：加载器核心（`io.mirage`，`launcher/`、`core/`、`api/`）。
- **AG**：整个项目（MG + Fabric/NeoForge/Forge 兼容层 + 工具链 + MDK）。

## 5. 兼容层现状（为什么路线 A 走不通）

| 层 | 覆盖 | 关键缺口 |
|---|---|---|
| NeoForge | 170 类 + 114 UOE pack；6 mod 扫出 **56 个唯一静态缺口** | `FMLLoader.getDist()` 语义缺口卡死 JEI；ScreenEvent 族 27 类无注入点；FluidStack/IItemExtension 等 4 大类需真实子系统 |
| Fabric | 16 类 + 8 Mixin 实机触发 | 20+ 回调、registry 桥、AW 未做 |
| Forge | **0**（无目录、`refs/forge` 只读） | 全部 |

**规模账**：NeoForge universal **1741 类** / MC client **10964 类** / Fabric 全 API 面；6 个测试 mod 就 56 缺口。
逐个 clean-room 补类 = 无限追不上，且补了类没有注入点 = 假覆盖（C84）。这是转 C 的第一性理由。

真实缺口机制已由 11-22 四次实机验证：探针链路可用（真启动 CNFE → `findClass` 记账 → shutdown hook 落盘），
但 8 个 mod 中 4 个在初始化早期被语义缺口打断，没走到 neo 引用路径——**语义缺口优先于链接类**。

## 8. 转向 C 的影响面与风险（本次决策重点）

> **【本节已作废·2026-11-22 13:xx】** 本节描述的"路线 C：多运行时统一调度 / 松动 D11"方向，
> 经反面教材（Forbrick 纪要）逐条对照证实为**已证伪路线**（焊接 / 事件桥 / 试错时间表 / 静默跳过）。
> 决策日志与 PLAN.md D11 已追加修正；最终方向改为"clean-room API 语义层 + mod 原生跑 + 干净字节码 + 冲突时 mod 优先"。
> 本节原文保留作决策过程追溯，**不要按本节实施**。最新决定见 `docs/plans/2026-11-22_C决策复盘与计划补丁.md`。

### 8.1 要推翻什么

- **D11 零依赖**：从"绝不引用其他加载器运行时"改为"按 mod 原生类型调度真实运行时"。
- **D9 单层隔离**：多运行时共存必须多层隔离与命名空间划分。
- 项目对外定位：从"第四个独立加载器"改为"统一启动/调度层"——README/PLAN/AGENTS 的措辞都要同步。

### 8.2 核心风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| LGPL 合规 | NeoForge/Forge 是 LGPL 2.1；动态调度与"链接"的边界需法务级确认 | 独立进程/动态加载、不把 LGPL 代码打进本体、留 NOTICE；出合规评估文档 |
| 注册表统一 | 多运行时共享 MC 实例时，注册表/事件总线的归属与冲突 | 先做单一运行时（NeoForge）跑通，再谈共存 |
| 启动时序 | 多个加载器都想在 MC 主类前初始化 | 统一调度层统一入口，加载器降级为被调度的插件 |
| 假覆盖回归 | 转向后不能把"调度成功"误当"功能兼容" | 沿用 C84/UOE 铁律 + 门禁变异检验；明确"互通"判据（先定 Q1） |

### 8.3 转向的前置条件

1. **先定 Q1「跑通」判据**（L1 能启动 / L2 进世界无 ERROR / L3 核心功能可观察）——否则"互通"不可验收。
2. **法务/合规边界评估**：动态加载 LGPL 运行时的许可影响（独立文档，不在代码里拍脑袋）。
3. **单一运行时 PoC**：先只调度 NeoForge，跑通 1 个真实 mod 的完整生命周期，证明调度层可行，再扩展 Fabric/Forge。
4. **保留现有资产**：35 个门禁、C1 的 29 类、MSR 工具链都是可复用资产，不推倒重来。

### 8.4 明确不做的

- 不再扩建 clean-room 穷举补类（路线 A）；P0 的 2 个类做完作为模式证明后收尾。
- 不为了转向而静默删除任何历史记录——旧计划/旧结论按"只标不删"加"（已被路线 C 取代）"标注。
